# Agent Note: 给流式 fan-out 加背压、把事件写入批量化，让繁忙的宿主不再被自己的负载拖死

Status: implemented

[English](2026-11-03-stream-fanout-backpressure.md) | 中文

## Problem

一个生产环境的租户宿主在三个 turn 运行期间被自己的存活探针重启，这三个 turn 都没有留下已持久化的 `turn/end`：工作丢了，客户端只看到流突然停住。从集群侧重建出的经过是：

- 一个 case 十五分钟写入了 572,231 条会话事件——流式轮次每个 token 追加一条 `assistant/chunk`，而每一条都会被持久化——峰值接近 1,900 条/秒。
- 峰值期间，进程应答 `GET /openapi.json` 比探针的 3 秒超时更慢，于是 kubelet 重启了它。它其实从未死掉：一直到 SIGTERM 之前它都在写事件，空闲后同一个端点只用半毫秒。

探针阈值是部署事实（租户宿主的清单现在带了一套能扛住慢响应的阈值），但让机器先饱和的是 harness 内部的两个放大器，而且两者都能在代码里直接看到，不是推测：

1. **两个 SSE 阶段都在推、而不是拉。** `toFetchHandler` 的 `sseResponse` 与 `agent-http` 的 `scopedSseBody` 都是 `start()` 循环，源产出多快就 `controller.enqueue` 多快。`enqueue` 从不阻塞，所以慢套接字前面的队列会无界增长：套接字层确实施加了背压，但它能做的只是停止读取，而这恰恰是让队列长大的原因。于是一个挂起的浏览器标签就足以撑满宿主堆、把 GC 停顿拉长到同一事件循环上的每个请求——包括探针。
2. **每条订阅的帧队列是无界的。** 每条 `events.mux`/`events.host` 订阅都持有一个 `FrameQueue`，所有广播都往里推，只有消费者会把它取空。一个不关闭就停止读取的读者——挂起的标签页、休眠的笔记本——套接字仍然开着，于是这个队列会永远保留它所附每个会话的每一条事件。
3. **每条被持久化的事件都是一次独立往返。** `PostgresSessionStore.appendBatch` 与 `commitRepair` 在 flush 事务里按事件逐条执行单行 `INSERT`。coordinator 会把一次 flush 合并到 `writeBatchMaxDelayMs`（200 毫秒）以内，于是 1,900 条/秒的突发变成每次 flush 约 380 条串行语句，同时还有多个 flush 在跑，全部在同一个还要应答 HTTP 的事件循环上等待。

## Decision

两个阶段的 SSE 响应体都改为按需求驱动（pull）。`pull` 每得到一个空闲队列位就向源索取恰好一帧（`ReadableStream` 默认只握有一个 chunk），因此停止读取的订阅者只会让源停住，而不会把它缓冲起来，两个阶段也就无法把各自的队列叠成一条无界流水线。消费方取消时仍在途中（in flight）的那一帧会被丢弃而不是入队（`detached`）；`cancel` 也不等待源的 `return()`：源可能正停在一条永远不会到来的帧上，真正结束 impl 迭代的是请求信号，而不是这个流。

每条订阅的队列以 `MAX_BUFFERED_FRAMES`（20,000）帧为界。超过之后宿主就不再服务它：积压被释放、迭代器结束，SSE 响应体随之关闭。这与任何一次断流的恢复方式相同——客户端重新打开发流，拿到新的基线以及重放的审批与提问——而且这是唯一能把落后的读者错过的那些「可应答帧」重新放回用户面前的恢复方式。溢出会被记录到日志，使运维者能看到某个订阅者已经停止读取。

`appendBatch`/`commitRepair` 现在按每条语句 `EVENT_ROWS_PER_STATEMENT`（200）行的多行 `INSERT` 追加事件——每语句 800 个参数，远在协议上限之内——仍在同一个事务内，因此一次 flush 跨分块依然是全有或全无，撕裂尾部保证不变。

## Alternatives considered

**只放宽探针阈值。** 必要，且已随部署清单一起落地，但并不充分：它把「过载 90 秒后被杀死」换成「过载持续多久就不可用多久」，而无界队列仍在向堆上限增长。它是对慢响应的容忍，不是对慢响应的修复。

**不再持久化 `assistant/chunk`。** 这些增量对 UI 可见、对模型不可见，因此日志原则上可以只保留最终的 `assistant/message`。否决：流式文本将无法再从日志重放，这会在客户端依赖的方向上破坏「模型可见 ⟺ 已记录」，而且它是为一个批量化已经解决的写放大问题改动磁盘格式。

**保留逐事件语句、改为加宽合并窗口。** 它只能靠让持久化更晚来减少语句数量；每次 flush 的往返次数不变，而更宽的窗口会把每一次 `turn/end` 的写入一起推迟。

**用丢弃最旧帧的方式来给队列设界，而不是结束订阅。** 丢弃能让流保持打开，客户端也能检测到 seq 跳号，但最旧的帧恰恰是订阅基线与待处理的审批/提问请求——那是读者绝不能静默丢失的可应答状态。结束订阅会在重连时把这一切重新建立起来。

**把两个流都换成 `TransformStream`。** 默认的 transform 队列同样只握一个 chunk，但作用域阶段需要丢弃帧并重新切分字节单元，`TransformStream` 只能用内部缓冲来表达这件事——正是这里要移除的东西。

## Consequences

代价：读得慢的订阅者现在会拖慢投递，而不是从内存里被服务，因此它的滞后表现为滞后，而不是宿主内存增长；而一个停得太久的订阅者会被断开——这是一个客户端可见的失败，被选来替代整个宿主范围的失败。取消之后 `controller.enqueue` 变得不可达（`detached` 标志），意味着一帧在取消期间产出会被静默丢弃——这是正确的，因为没有人能接收它。

收益：fan-out 的开销被消费者真正读取的量所限，而一次 flush 从「每个事件一次往返」变成「每 200 个事件一次往返」——流式突发期间的语句数下降约两个数量级，且落在同一个也要服务其他请求的事件循环上。

## Testing

`packages/host/apiproxy/tests/fetch-carrier.spec.ts` 与 `packages/tenant/agent-http/tests/agent-http.spec.ts` 直接钉住这个上界：源上有 200 帧可用而无人读取时，产出停在每阶段一个队列位之内（分别为 `<= 1` 与 `<= 2`），随取走的 chunk 跟随需求，并在取消时停止——另外还覆盖两条取消在途路径（在途的一帧、消费方离开后才失败的源），它们都以 `done` 结束，而不是让流复活。`packages/host/apiproxy/tests/frame-queue.spec.ts` 负责队列上界：帧按顺序到达直到队列结束，而超过 `MAX_BUFFERED_FRAMES` 一帧即结束订阅、释放积压（下一次拉取得到 `done`，而不是 2 万帧的回放），并把溢出报告一次。`packages/tenant/session-persistence-postgres/tests/store.spec.ts` 钉住写入形态：一次 flush 一条语句，450 个事件切成 `[200, 200, 50]`，每个 seq 都按顺序恰好落一次。

同一起事故的部署侧应对（探针阈值、启动预算、资源 requests）在租户宿主清单里，不在本仓的 packages 中。
