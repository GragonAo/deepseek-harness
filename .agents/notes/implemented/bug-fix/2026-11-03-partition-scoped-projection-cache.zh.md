# Agent Note: 投影缓存按请求分区惰性加载，冷列表读检查点而不是整篇日志

Status: implemented

[English](2026-11-03-partition-scoped-projection-cache.md) | 中文

## 问题

一台生产租户宿主（171，租户 `fifiijshmsvi_soopxedqg`）的 `session.list` 分别用 32.5、33.1、34.9 和 87.9 秒返回，前面那层 Java 桥把它们全部折进 30 秒读超时，案件页面因此报 `upstream-unreachable`。宿主本身是健康的：同一 socket 上 `host.describe` 0.02 秒、`workspace.list` 0.7 秒，一次 33 秒的列表在 32 核机器上给进程 cgroup 记了 53 CPU 秒，而把 884 个会话文件从 cephfs 读一遍只要 81 毫秒。该宿主上三个租户的代价按事件总量排序、而不是按会话数排序——0 条 / 0.42 秒、527,201 条 / 4.37 秒、4,521,054 条（2.14 GB `jsonb`）/ 32.5–87.9 秒——它们落在同一个吞吐上，约每秒 12 万–13 万条事件，这一点指明了机制：列表把每个冷会话的整篇日志都过了一遍投影注册表。

投影系统本来就有对症的手段。`session-projection-cache` 为每个会话存一条检查点记录，`cachedSnapshot(meta)` 用它直接服务列表里那一列，网关的冷列表也是先读它；未命中那条路（`readFrom(id, 0)` 加一次注册表折叠）本来是留给没挂缓存的部署的。租户组合没挂：`packages/tenant/tenant-app/src/spine.ts` 停用了那一行，理由是缓存在 `Service.init` 里就开它的存储域，而租户存储后端是每次操作才解析租户与用户（调用入口的 `currentTenant()` / `requireUser()`）。开机时没有环境分区，开域会得到一张进程内全局共享的表——一个租户能读到另一个租户的检查点。停用是当时唯一安全的组合方式，于是未命中那条路成了唯一的路。

## 决定

`session-projection-cache` 不再在 init 时开域，而是按环境请求分区惰性加载。`partition()` 以 `currentPartition(ctx)` 报告的 `(tenantName, userName)` 对为键维护一张 `Map`（没有分区作用域时键是空串，即单用户形态），未命中时才开域并把该分区的 `sessions` 表绑上去；同一分区的并发第二次调用并入同一次开域，因为域设施拒绝重复打开。`Config.maxLoadedPartitions`（必填、无默认值）限定同时驻留的分区数：每个驻留分区把该租户与用户的整张检查点表放在内存里，所以这个数是组合里明写的内存预算。超出预算再加载时关闭最近最少使用那个分区的域——检查点是持久的，之后用到它再加载即可，不丢数据——插件释放时关闭全部已加载的域。

因此 `cachedSnapshot` 变成异步：一个分区里的第一次调用要从介质解析出该分区的表，之后的调用只读内存。`coldSnapshot` 与写回路径同理，都按调用入口那一刻的环境分区解析。

租户组合挂上缓存（`writeEveryEvents: 200`、`writeIntervalMs: 5000`、`maxLoadedPartitions: 8`），浏览器组合写 `maxLoadedPartitions: 1`。单用户形态没有变化：没有分区作用域、一个域、一张表。

网关冷列表那一列补上阶梯的最后一步：存储行未命中时，对这一个会话继续走缓存的 `coldSnapshot(id, signal)`——从注册表的锚定下界读尾部、并把刷新后的检查点 fail-soft 写回。因此一个原本没有检查点的会话只付一次折叠，而不是每次列表都付一次，它的下一次列表就是读存储行。没挂缓存的部署仍按原样直接折叠日志。

## 考虑过的其他方案

**在网关里按持久化 revision 记忆派生行（曾实现、量过、已回退）。** `listSnapshots()` 顺手把每个冷会话的持久化 revision 交给列表，按该 revision 记忆的行可以完全不再读日志；在 130 上它把重复的一次 8.6 分钟列表降到 50 毫秒。但它是缓存本来职责的第二份实现：进程一重启记忆就没了，所以每次重启后的第一次列表仍要全量折叠；它给每个网关实例加了一张有上限的摘要行表；它继承的跨租户安全性依赖某个持久化后端的 revision token 里带了 schema 名，而不是一条写明的约定。检查点存在租户自己的 Postgres schema 里、跨重启存活，所以检查点这条路一通，记忆层就回退了。

**init 时按裸单元名开域。** 那会得到一张所有租户共用的进程内表，而行的键是会话 id、不带租户前缀，列表里就可能读到别人的行。

**让存储域的表同步地按分区解析。** 域的表是由一次 `loadAll()` 建出来的内存快照；分区只能靠读介质才知道，所以这个读天然是异步的。硬把 `cachedSnapshot` 保持同步，要么得接受一张可能过期的表（缓存被悄悄关掉），要么得在开机时加载所有分区，而那正是惰性设计要避免的内存增长。

**开机时给所有已存会话补检查点。** 每次启动都单独扫一遍全部日志，代价一样，而且由一个还没被要求服务列表的宿主来付，同时与阶梯自己的写回重复。

**调大桥的读超时，或者让运维等。** 代价是宿主侧在同一条事件循环上的派生，而那条循环还服务其他所有请求；超时调长只是让一次 33 秒的列表占用它更久。

## 结果

一次冷列表在一个分区里只付一次表加载，之后全是内存：没有逐会话的 `session_event` 读、没有注册表折叠，也不随租户历史总量放大。检查点早于缓存、或写节流还没落盘的会话仍要折叠一次——171 上的历史案件在引入本改动的这次部署之后第一次列表时付一次，此后不再付，重启也不算。

内存被 `maxLoadedPartitions` 张表限定，每张是一个租户与用户的检查点行；淘汰会关闭最近最少使用的域，所以服务很多租户的宿主不会把它们堆起来。跑在请求分区之外的检查点写入（例如关闭时的会话释放）会被分区化后端拒绝并保持 fail-soft：记一条警告，下一次在作用域内的写入把它补上。

列表读变成异步，牵动了两处调用：网关等它，`subagent` 的子会话列表在它的冷身份解析里等它。

## 测试

`packages/session/session-projection-cache/tests/cache.spec.ts` 覆盖分区策略：每个请求分区各开一个域并用它自己的表服务、超出预算时关闭最近最少使用的分区并在下一次使用时重新加载、插件释放时关闭全部已加载分区。原有的阶梯测试仍覆盖写回、身份绑定与版本不匹配路径，只是现在经过异步的列表读。

`packages/subagent/subagent/tests/list-children.spec.ts` 与网关的冷列表、投影套件钉住那两处改动过的调用点。

130 上那个 652 会话、17,798,462 条事件的租户在部署后只付了一次折叠——669.8 秒，写入 652 个检查点——之后每次列表都是读存储行：同一进程 0.17 秒，三个新进程分别是 0.19、0.35、0.19 秒。该租户 `session_event` 的 `seq_scan`/`idx_scan` 在上述每次重启后的列表前后都是 30/3330，说明没有一次列表读过日志；响应体始终逐字节一致，902,727 字节。
