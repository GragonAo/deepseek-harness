# Agent Note: A tenant's terminals are sessions in its own sandbox

Status: implemented

English | [中文](2026-10-08-tenant-terminal-in-the-container-sandbox.zh.md)

> `ctx.containerRuntime` gains one interactive operation, `openPty`, implemented once in `container-transport` under a real host-allocated terminal and reused by both providers; a new tenant package, `dsh-terminal-container`, registers it as the `ctx.terminals` backend so `tool-terminal` and `tool-bash-persistent` give a multi-tenant deployment persistent terminals inside the tenant's own sandbox.

## Problem

The multi-tenant stack had one execution surface per (tenant, user): a sandbox container that answers `POST /exec` with a completed result. `packages/tenant/tenant-app/src/spine.ts` mounted neither `tool-terminal` nor `tool-bash-persistent`, and it could not: both consumers reach the model through `ctx.terminals`, whose only shipped provider, `dsh-terminal-bash`, opens a PTY on the host process. Mounting it in the tenant stack would have put every tenant's shell on the shared host — outside the isolation the rest of that stack is built on — while `bash`'s whole value (one shell reused across commands, so `cd`, exported variables, and an activated virtualenv survive) needs a shell that outlives a single command.

`ctx.terminals` is a capability seam that already had a Consumer (`tool-terminal`, six tools) and a Definition (`packages/terminal/terminal`), missing only a Provider for the tenant shape. The premise that Provider has to keep is the seam's central promise: every operation binds the **exact initiating Agent**, so one Agent can never read, signal, or close another's terminal. The tenant shape must not weaken it — the sandbox is shared per (tenant, subject), so two Agents of one subject reaching the same sandbox is normal, and only the session registry can tell their terminals apart.

The blocking fact was that the container runtime offered only that one-shot `exec`. A persistent terminal needs duplex stdin/stdout, a window size, and signal delivery, none of which a request/response `POST /exec` carries.

## Decision

**The Service Definition owns the interactive operation.** `packages/tenant/container/src/index.ts` gains `openPty(options): Promise<ContainerPtySession>` next to `exec`, with `ContainerPtyOptions` (`command`, `args`, `rows`, `cols`, `maxOutputBytes`, `disposeGraceMs`, `signal`) and a session handle (`pid`, `done`, `read`, `write`, `foreground`, `signal`, `close`). It belongs in the Definition because it is backend knowledge every provider must supply and no Consumer can fake: whichever process attaches a terminal to a sandbox knows how, and both current providers answer to the same runtime choice. Providers do **not** gain a PTY-shaped public API of their own, and the terminal provider does not learn a single runtime CLI flag.

`openPty` deliberately carries no `cwd` and no `env`: those are runtime CLI flags (`docker exec -w/-e` has no `kubectl exec` counterpart), and putting one provider's flags into the Definition would make them every provider's obligation. A caller that needs a working directory brackets the command with `sh -c`, which is what the new provider does.

**Both providers implement it through one shared body.** `container-transport` gains the third transport form its README already anticipated: `ptyRunner(binary)` allocates a real terminal on the host (`node-pty`) and runs the runtime CLI's `exec -i -t` under it, and `openContainerPty` implements the session once — write a handshake, read the session id and foreground group out of the sandbox's own `/proc`, retain a bounded output tail, and end the session with `SIGTERM` → `disposeGraceMs` → `SIGKILL` plus verification that the process groups are gone. `container-k8s` contributes `['-n', namespace, 'exec', '-i', '-t', pod, '--', …]`, `container-docker` contributes `['exec', '-i', '-t', container, …]`, and each passes a one-shot `exec` closure bound to the sandbox it already resolved. A real local terminal is not a preference: `docker exec -i -t` with a piped stdin is refused by the Docker CLI's own `CheckTty`, so a host that cannot allocate one fails loudly at startup instead of silently handing back a session without a TTY.

**A new tenant package provides the backend.** `packages/tenant/terminal-container` (`@deepseek-ai/dsh-terminal-container`) implements `ctx.terminals`' backend contract over `ctx.containerRuntime.openPty`, registering type `shell` by default (`backendType` is validated configuration). It opens `/bin/sh -c '<bracket>' <shellPath> <shellArgs…>`, where the bracket enters the session's `cwd` (exiting 126 with a message when it cannot) and passes `TERM=dumb`, `PAGER=cat`, `GIT_PAGER=cat`, `DSH_SHELL=1`, `DSH_SESSION_ID=<owning Agent>` and `DSH_PTY_SESSION_ID=<terminal session>` before `exec`-ing the shell, then owns the rest of the session: retained scrollback with line-based paging, the readiness rule below, and teardown.

**Readiness is silence plus one probe, and the outcome is named.** An attached interactive shell reports no command boundary, so `send` settles on the first of four outcomes: `stdin_read` (quiet for `idleSilenceMs` *and* a live process group still holds the terminal), `inferred_idle` (quiet, but no group holds it), `session_exit`, or `timeout`. Exactly one `foreground()` probe per send, never one per poll. This is deliberately not "silence means done": `tool-bash-persistent` returns early only on `stdin_read`, so settling a silent send as idle would make its 25 ms poll loop hammer the sandbox with probe round trips and would report a finished command before it finished.

**Session lifetime is the sandbox's, and its end is visible.** Terminals do not survive a sandbox that is replaced, evicted, or exited on idleness: the container-side `done` settles, the session's `status()` reports an exited session, and the next `send` settles as `session_exit` instead of hanging. Closing is verified rather than assumed — `SIGTERM` to the foreground group, a grace period, then `SIGKILL`, then a re-probe that fails the close if a group survived.

**Assembly appends, and configuration stays in `Config`.** `tenant-app/src/spine.ts` gains four rows after the existing ones (`terminal`, `terminal-container`, `tool-terminal`, `tool-bash-persistent`), with `deps.ts`, `package.json`, and the tsconfigs updated together.

**The local CLI runner settles a command whose stdin the child stopped reading.** `container-transport`'s `cliRunner` — the seam both providers reach a runtime binary through — treats a stdin write failure caused by the child closing its own input as a completed call: the child's exit code and captured streams stand, and the process is left without an unhandled stream error. The closed-input codes are the ones the in-container `/exec` server already names (`EPIPE`, libuv's `EOF`, `ECONNRESET` — one predicate over one `ReadonlySet`), because the reason is the same: the command that travels over stdin is `kubectl create -f -`, and reporting "the pipe could not be written" as a failure would send a caller to retry a creation that already succeeded. Any other write error rejects, naming the binary. Leaving that stream unattended is not a plain rejection: an unhandled stream error takes the host process down.

## Alternatives considered

- **A resident shell inside the in-container tool-exec server.** Rejected: `POST /exec` is request/response, so the server has no duplex channel back to the host, cannot report a window size, and has no way to deliver `SIGINT` to a running child. It would also make the server a second owner of session state — session ids, scrollback, and process-group bookkeeping would live in two places, and the host's notion of "the session" would be a proxy for the container's.
- **Let the terminal provider call `kubectl`/`docker` itself.** Rejected: it creates a second owner of backend knowledge. The provider would have to know namespaces, pod names, container names, and flag spelling — everything `container-k8s` and `container-docker` already own — and every future backend would need a matching branch in a package that is not about backends at all. It is also the only reason the new provider is a thin session layer rather than a runtime reimplementation.
- **A pseudo-TTY faked over the one-shot exec (`script`, `socat`, `unbuffer`).** Rejected: what the sandbox hands back is still a completed result, so the session would have no stdin between commands, no signals, and no window size; it also adds a requirement on whichever binary the image happens to carry.
- **`docker exec -i -t` with piped stdio, without a local terminal.** Rejected by the tool, not by us: the Docker CLI refuses `-t` when stdin is not a terminal (`CheckTty`). A session without `-t` has no job control, no foreground process group to signal, and a shell that cannot be interrupted.
- **Run the terminal in the host process and copy files into the sandbox as needed.** Rejected: it puts tenant shells outside the tenant's sandbox — the isolation the rest of the stack exists to provide — and `cd` would resolve against host paths.
- **Make the tenant terminal a `tool-terminal` configuration instead of a provider.** Rejected: `tool-terminal` is a Consumer of the seam and stays backend-agnostic; teaching it about sandboxes would move backend knowledge into the tool schema and leave `tool-bash-persistent` and every future terminal consumer to re-learn it.
- **Signalling a group with the `kill` program the image resolves from `PATH`.** Rejected by measurement: a negative operand is what addresses a process group, and procps-ng's `kill` — the `kill` of Debian bookworm, version 4.0.2 — does not take one. `/usr/bin/kill -s SIGNAL -- -PGID` exits 1 with a usage error and leaves the group running; dropping `--` does not help, because `-s SIGNAL -PGID` is refused the same way and `-SIGNAL -PGID` exits 0 without signalling the group at all. Only a shell's own `kill` builtin accepts `kill -s SIGNAL -- -PGID`, so the delivery runs `/bin/sh -c` and the interpreter is named by absolute path — the builtin that parses the operand list is chosen by the host, not by whichever shell the image installs.
- **Wait for a command-boundary signal from inside the sandbox (shell integration).** Deferred, not rejected: it needs an in-container participant (a `PS0`/prompt-command hook or a wrapper) and an image change, and it would replace the readiness rule rather than extend it. The current rule is a bounded heuristic whose two wait reasons are visible to the caller.

## Consequences

- **A terminal deployment needs `pods/exec`.** One-shot commands still never use `kubectl exec`; only `openPty` does. The host's Role must grant `pods/exec` in the sandbox namespace, and a deployment that does not offer terminals should not grant it: the failure is confined to `terminal_open`.
- **The host process now needs a real-terminal library.** `node-pty` (already a workspace dependency of `subprocess-local`) is required, with `/dev/ptmx` available to the host process and to the sandbox image's side of the attach. `container-transport` reports the load failure with its reason rather than degrading.
- **The sandbox image's contents become part of the contract.** The session's identity is read from `/proc` (`/proc/self/stat` and `/proc/<pid>/stat`) directly rather than through `ps`, and a signal reaches a process group through the `kill` builtin of the image's `/bin/sh`, which is named by absolute path. An image with no readable `/proc` opens no terminal at all, which fails at `terminal_open`; one with no POSIX shell at `/bin/sh` cannot be signalled, which fails at the operation that signals.
- **The readiness rule cannot prove an input wait.** A silent long-running command is indistinguishable from a child waiting for input; both settle as `stdin_read`. Callers see the named wait reason and can send more input, and the deadline still bounds the send.
- **Terminal I/O is bounded at three points**: the session's retained tail (`maxOutputBytes`), the provider's scrollback (`scrollbackMaxBytes`, `scrollbackLines`), and one read (`readMaxBytes`). A model reading a long build sees a bounded tail with `truncated` set rather than the whole stream, and large intermediate output can be dropped from the retained history.
- **Window size is fixed per session; there is no resize.** A full-screen program reads its size once at start. Adding `resize` needs a new operation on the Definition and a delivery path to the runtime CLI that no current consumer requires.
- **`terminal_open`'s `type` argument and the registered type must agree.** The default (`shell`) follows `tool-bash-persistent`'s own default; a deployment that renames one must configure both. Mounting `terminal-bash` and this provider together fails at load with `DUPLICATE_BACKEND`, which is the intended behavior of a single-provider type.
- **Idle sessions are reclaimed by Agent lifetime and sandbox idle exit, not by the provider.** A terminal whose Agent is still live keeps its sandbox session open; there is no idle timer in the provider because `ctx.terminals` gives no "still in use" signal to key one on.

## Verification

- `packages/tenant/container-transport/tests/session-probe.spec.ts` pins both ends of the session's identity: the handshake accepts the CR LF a terminal translates its newline into (and the plain LF a pipe would send), ignores the shell's echo of the handshake line, and `parseState` reads live groups, `-1` as "no foreground group", and unknown lines. It also pins the argv `signalArgv` builds verbatim — `/bin/sh` by absolute path, with the signal and the group as positional parameters. That procps rejects the program form is a measurement, not something a unit test establishes.
- `packages/tenant/container-transport/tests/pty-session.spec.ts` drives the session against a fake terminal and a scripted sandbox: the argv and window size handed to the runtime, boot-noise removal, retained-tail bounds, refusal of a command that never reported a session (naming the tail it printed), the wait bound, `/proc`-derived `pid`, group-wide signalling, the `SIGKILL`-while-the-leader-holds-the-terminal refusal, `TERM`→`SIGKILL` escalation with a surviving-group failure, retry after a failed close, and cancellation before and during startup.
- `packages/tenant/container-transport/tests/transport.spec.ts` pins the CLI runner's failure semantics: a child that exits without reading the 1 MiB it was fed still settles with its exit code and leaves no `uncaughtException`/`unhandledRejection` on the process, and a start that fails rejects naming the binary it could not run. The first of the two is non-vacuous — unwiring the stdin listener makes it fail on `Error: write EOF { code: 'EOF' }` reaching the process-level listener.
- `packages/tenant/terminal-container/tests/backend.spec.ts` drives the registered backend through the real `ctx.terminals` registry with only `ctx.containerRuntime` faked: spawn payload (cwd quoting, environment, `exec`), banner adoption, all four readiness outcomes, paging and truncation, cancel-through-`SIGINT`, close through the registry, and a runtime that cannot open a session publishing nothing.
- `packages/tenant/container-k8s/tests/runtime.spec.ts` and `packages/tenant/container-docker/tests/docker.spec.ts` each assert the provider's own contribution: the `exec -i -t` argv addressing the right sandbox, the window size and grace period reaching the host terminal, and the identity probe travelling over the same tool-exec endpoint as every other command.
- A real cluster is still the only place these hold: `pods/exec` in the sandbox namespace, a `kubectl exec -i -t` that keeps `Tty: true`, `node-pty` and `/dev/ptmx` in the host image, remote exit-code propagation, session-leader/session-group behavior under `setsid`, and what a client sees when a sandbox is replaced mid-session.
