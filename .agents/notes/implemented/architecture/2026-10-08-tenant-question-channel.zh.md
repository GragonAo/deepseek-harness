# Agent Note: 租户提问通道经由业务面作答

Status: implemented

[English](2026-10-08-tenant-question-channel.md) | 中文

## 问题

模型可以通过 `ctx.userQuestions` 向人提问，但租户栈只挂了这条 seam 的组合行，没有挂任何 provider，于是每次 `ask_user_question` 都以 `no user-questions provider is registered` 失败——装配声称这个能力存在，却没有人能应答。工具本身也没有挂上，所以模型连 `ask_user_question` 都没有。

租户栈另有一个应答者已经在用的业务面：带 bearer 认证的 `/api` 面以及它的 `events.mux` 流。提问两边都到不了。它只存在于那次工具调用的参数里，也没有任何方法接收答案；于是本该作答的那一方——在租户业务客户端里工作的数据挖掘分析师——既看不到问题，也无法回复。

## 决定

提问与它的结局都是持久会话事件，由租户侧的 provider 为既有 seam 追加；答案则作为业务面自己的两个方法抵达。

### `@deepseek-ai/dsh-tenant-questions` 提供这条 seam

该包继承 `Service`，并通过 `ctx.effect` 注册一个 `UserQuestionProvider`，因此 seam 每次注册只有一个 provider，注销时随之移除。它只注入 `userQuestions`；它需要的租户权威来自当前请求作用域，不是注入进来的服务。

一次提问绑定到 (租户, 主体)，也绑定到它来自的会话：`ask` 读取 `requireTenant()` / `requireUser()` 与提问 agent 的会话，对没有 agent 的提问报 `ASK_MISSING_AGENT`，对不在已认证请求内的报 `NO_QUESTION_SCOPE`，对不在开放轮次内的报 `NO_OPEN_TURN`，对重复问题 id 报 `DUPLICATE_QUESTION_ID`，然后记录这次提问，并让 provider 调用停在原地，直到业务作答、自己的期限到达，或提问被撤回。

### 这一对记录为 `user-question/asked` + `user-question/decided`

两个成员都是 log-only、持久、可回放，沿用 `approval/*` 审计对的做法：没有 `surfaceOp`，绝不进入模型记录，也不带 `ignorable`。`questions` 就是工具调用提交时的原始提问，所以业务订阅方仅凭该事件即可呈现问题，不需要第二次读取。`decided` 带 `outcome`（`'answered' | 'timed-out' | 'cancelled'`），并且恰在结果为 `'answered'` 时带被接受的答案。

没有新的推送通道。`MuxFrame` 本来就把每个会话事件作为 `session/event` 帧投递，因此订阅既有流的业务客户端会在两个事件被追加时就看到它们。

### `list` 与 `answer` 是通道自己的业务方法

`TENANT_QUESTION_METHODS` 给出它们的名字（`tenantQuestion.list`、`tenantQuestion.answer`），并把每个协议名与方法对 `ctx.tenantQuestions` 的调用配对。`agent-http` 在委派给网关之前先应答该表里的方法，用的是它为该请求已经建立的权威，以及网关自己的两级解析：媒体类型不是 JSON 报 415，请求体不是 JSON 报 400，信封读不出来或路径与方法不匹配是 200 的 `bad-request` `ServerResponse`，载荷被拒也是同样的 200 `bad-request` 并附字段级 issues。通道内部崩溃是载体自己的 500，通道没挂是 503，而不是静默的 404。

作答载荷按当前主体的**在途提问**校验，因此它无法指向别人的、过期的或不存在的问题：schema 按本 (租户, 主体) 的每条在途提问各出一支，每支要求精确的会话 id、精确的问题 id，以及一份恰好覆盖该次提问每个问题一次的答案——不得有未知 id、不得重复、不得给出问题没提供过的标签，每一项也不得既无标签又无文本。指向其他任何东西的载荷都会带着具体字段路径校验失败。

答案只有在其结局被记录之后才算被接受。通道把「从在途表中移除」当作认领——于是作答、期限、中止、注销中第一个认领它的那个决定唯一结局——并追加 `user-question/decided`；当日志拒绝这次追加时（提问与作答之间轮次已关闭，事件对便不再被轮次包住），业务客户端会被告知该失败，停等的工具调用以日志自己的失败（而不是期限）被释放，且不会为一个会话日志并不承载的判定回报「已接受」。

### 期限是配置，到期是错误

`answerTimeoutMs` 是经过校验的 `Config` 字段（默认 60000）。到期时提问以 `ANSWER_TIMEOUT` 拒绝——说明没有答案到达、期限就是原因，并要求模型陈述自己的假设继续推进而不是再问一次——同时这一对以 `'timed-out'` 结算。不会编造答案，也不会替它选中任何默认选项。

租户组合清单把通道的窗口配在 seam 自己的窗口之内（`user-questions` 行是 `360000`，通道是 `300000`），因为一旦到达 seam 的期限，提问会被中止：模型届时只会看到 seam 的 `NO_ANSWER`，丢掉这条通道存在的理由。五分钟是办案分析师在轮次自行推进之前作答的窗口；它同时也是业务客户端渲染出的那张提问卡片的可作答时限——过期的提问会离开 `list()`，`answer` 也不再受理。

### 装配

两行加入租户组合清单：`tool-ask-user`（面向模型的工具）与 `tenant-questions`（通道，显式带 `answerTimeoutMs: 300000`）。`compose.ts` 把 `userQuestions` 与 `tenantQuestions` 都当作必需服务探测，各自以对应组合行是否启用为条件，因此启用了通道行却没有 seam 时，启动会按名字失败，而不是留下一个静默缺席的面。

## 被否决的备选

**为提问新增推送通道。** 否决：负责人的决定把通道固定为会话事件加一个作答方法，而 mux 流本来就把每个会话事件投递给每个订阅方。第二条通道会重复投递，并需要自己的认证。

**把方法加进共享网关的方法表。** 否决：那张表是封闭的，按 `RpcMethodMap` 编译，且在每种部署里完全一致；只属于多租户的方法放进去，就等于给单用户面一个它必须拒绝的方法。载体先应答自己的方法，其余全部委派。

**把提问记成 `approval/*` 事件。** 否决：审批是依附于工具调用、结果词汇封闭的权限判定，且审批服务会消费自己那一对。面向业务用户的提问带的是问题批和可含自由文本的答案；共用事件类型只会让双方去解析对方的载荷。

**由 seam 自己作答（`ctx.userQuestions`）。** 否决：seam 拥有的是单个进程内应答者的提问／作答协议；让它感知租户会把租户权威与持久化推进一个被 Web、TUI 和 ACP 组合原样共用的能力定义里。

**把在途表放进 PostgreSQL。** 已交付的租户服务是单副本，不需要这张表；它会给一条在途集合本质是进程内等待的通道加上一张表和一个 schema。多副本部署需要对「问过的那个副本」做粘性路由；这条限制写在包的 README 里。

**无限等待而不设期限。** 与编造默认答案同属一个负责人决定：一轮永远等一个不在场的分析师，与卡死在现象上无法区分，而模型也无法报告它从未得知的东西。

**增加 `tenantQuestion.wait` 长轮询方法。** 暂不采纳：流已经在投递提问，再加一个等待方法只会为同一个事件增加第二条投递路径，还会引入「一个业务请求能占住套接字多久」的上界。

## 后果

模型现在要么拿到真实答案，要么拿到它没拿到的明确原因。业务客户端在承载会话其余部分的同一条流里持久地看到每一次提问与每一个结局，并通过它已经在调用的同一个已认证面作答。

通道的期限必须留在 seam 的期限之内。加载时不检查这个顺序：两个取值属于不同插件的配置，而失效方式是静默的——模型收到一个正确但更含糊的错误。租户组合清单把两个取值并排写出，包 README 记录了这个耦合。

在途表是进程内的，因此多副本时必须把某个主体的答案路由到持有该提问的那个副本，否则答案找不到任何东西，提问最终超时。两个方法不在 `/api/openapi.json` 里，因为那份文档描述的是网关的方法表，业务客户端应通过本笔记、载体的模块文档或包 README 发现它们。

`user-question/asked` 与 `user-question/decided` 是读取必需的事件：不认识租户提问通道的构建会拒绝含有它们的会话日志。它们是 `SessionEventMap` 的追加成员，不改变 `SESSION_FORMAT_VERSION`。

### 验证

`packages/tenant/tenant-questions/tests/tenant-questions.spec.ts` 在真实会话存储上跑真实 seam：一次提问被记录、出现在该主体的列表里、经通道调用被作答，并以与事件对记录相同的答案唤醒停等的 provider；覆盖了自由文本与多问题提问；别人的主体、别的租户、过期 id，以及对已认领提问的第二次作答都被拒绝；十一种畸形载荷以 `ZodError` 被拒，且提问仍留在原地等待；期限以 `ANSWER_TIMEOUT` 拒绝并记录 `'timed-out'`；被撤回与已提前中止的提问分别不记录任何东西／记录 `'cancelled'`；seam 自己更短的期限以中止的形式抵达 provider；审计 invariant 拒绝的结算——提问与作答之间轮次已关闭——无论来自作答还是来自期限，都以该拒绝释放停等的轮次，并让事件对保持未闭合，而不是为一个日志不承载的判定回报结果；不经插件 schema 直接构造的通道也能用自己的期限完整服务一次提问；注销会拒绝停等的提问并不再提供 seam；两个协议名确实到达 `list` 与 `answer`。

`packages/tenant/tenant-questions/tests/invariant.spec.ts` 钉住这一对的关系：没有对应提问的结算、重复的在途 id、重复的问题 id、没有问题的提问、未知结局、结果非 `'answered'` 却带答案或反之、未曾提出的 id、被回答两次的问题、以及被漏答的问题，都会被拒绝；从日志回放的会话会重新接纳一条在途提问。

`packages/tenant/agent-http/tests/agent-http.spec.ts` 用真实 bearer 令牌在载体上跑这两个方法：无凭据 401；列表加作答确实唤醒了模型的提问；别人主体的作答被拒并附载荷细节；信封读不出来与路径／方法不匹配是 200 `bad-request` 且可回收的 `rpcId` 被回显；载体层的失败是 415 与 400；非 POST、以及同一个方法名出现在 `/api` 前缀之外，都是 404；信封无法描述的通道失败是 500；通道未挂载是 503。

`packages/tenant/tenant-app/tests/app.spec.ts` 证明装配：两行以 `answerTimeoutMs` `300000` 与 `360000` 挂上各自的插件，且测试断言通道的窗口是两者中较短的那个；`ask_user_question` schema 已注册；启用通道行而没有 seam 时，启动会因按名指出的缺服务而失败。

仓库测试未覆盖、需负责人在集群上验证的部分：订阅了 `events.mux` 的业务客户端端到端呈现一次提问及其结局；真实分析师的作答抵达停等的工具调用；以及多副本的行为与 README 所述一致。仓库的 Web 与 ACP 组合挂的是各自的应答者，不受这条通道影响。
