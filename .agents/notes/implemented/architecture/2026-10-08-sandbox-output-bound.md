# Agent Note: A sandbox caps each captured output stream

Status: implemented

English | [中文](2026-10-08-sandbox-output-bound.zh.md)

> The container-owned budgets of [Container-owned sandbox lifetime](2026-10-08-container-owned-sandbox-lifetime.md) gain a second member: like the idle budget, the output bound is injected by the provider and enforced by the in-container tool-exec server, because the container holds a command's whole stream before the host can bound anything.

## Problem

The tool-exec server spawns each command with piped stdio and pushed every arriving chunk into a `Buffer[]`, concatenated once the child closed; nothing bounded that array. The server's own module comment deferred bounds to `ctx.subprocess` — "Bounds and timeouts remain the subprocess capability's concern" — and that is true only of the result returned to the model: `packages/tenant/subprocess-container` bounds what it hands on, after the container has already held every byte. Between the command and that bound sits a buffer with no ceiling beyond the container's memory, so the size of one command's output decided whether the sandbox survived it.

That is what happened on the multi-tenant deployment. Two `find /` commands each made a sandbox Pod vanish: `kubectl get events` shows `Killing … Stopping container tool-exec` at 01:55:27 and again at 02:03:30, ~15 s later a same-name Pod was recreated, and the model saw `Error: container-k8s: sandbox … entered phase=Missing ready=false, a phase it cannot leave without being replaced`. A sandbox that dies with its Pod costs the subject its next call to a cold start, and the model sees a sandbox failure rather than the output of a command that was working. `container-docker` had the same exposure — the capture is bounded nowhere in the container, and the example deployment sets no `memoryLimit` — with a smaller blast radius, because a killed container is rebuilt in milliseconds where a Pod is not.

## Decision

`ToolExecServerOptions` gains `maxOutputBytes`, the byte bound **per captured stream**, and `runCommand` enforces it through a `BoundedCapture` that keeps draining a stream past the bound while retaining only its last `maxOutputBytes` bytes. Draining is not optional: a reader that stops leaves the child blocked on a full pipe, so the command never finishes and the sandbox holds its in-flight request forever. Retaining the tail matches what the host already does — `ctx.subprocess`'s per-stream budget keeps the tail too — so a result truncated at both layers carries the same bytes as one truncated at either. The result reports it: `stdoutTruncated` / `stderrTruncated` appear on `ToolExecResult` (and on its mirror in `container-transport`) only when that stream lost bytes, so no caller has to guess whether the text it holds is the whole output.

The bound is deployment configuration, not a constant in the server: `docker/entry.mjs` reads `DSH_TOOL_EXEC_MAX_OUTPUT_BYTES` with the same validation as the idle budget, and both providers expose a `Config.maxOutputBytes` field injected as that variable — `docker run -e` for one, the Pod environment for the other. Its named default, `DEFAULT_MAX_OUTPUT_BYTES = 64 * 1024 * 1024`, keeps the bound above everything a deployment can legitimately read back: the host's own per-stream bound is 64 KB (`dsh-bash-local`'s `maxOutputBytes`, 64000), and `dsh-code-runtime-container`'s payload bound is 64 MiB. A stream the sandbox cuts is therefore one the host would have bounded anyway, while raising that payload bound now has to raise this one with it, which the constant's JSDoc states. The value is validated positive, and an absent variable means no bound — the server imposes none of its own, exactly like the idle budget, and the providers always inject one.

Every consumer gained the flag rather than a new failure mode. The k8s provider carries it out of the transport, `CapturedReader.settle(full, containerTruncated)` in `subprocess-container` marks the read `lossy` so `bash` and `pwsh` render their existing truncation notice instead of presenting a tail as the whole result, and `fs-container`'s `readText` / `readBytes` / `listDir` throw `FS_TOO_LARGE` — a silently truncated file read would hand `editText` a wrong `before`, and a truncated listing would report a partial directory as complete.

### The server also survives a stdin the command never reads

The same server has a second way to lose the whole exec channel, and it has nothing to do with the bound: `runCommand` writes a request's `stdin` into a pipe the command may close before reading it, as when a large script goes to an interpreter that exits on its first line. The write then fails with `EPIPE` — `EOF` on Windows through libuv, and `ECONNRESET` once both ends are gone — and with no listener on `child.stdin` that is an unhandled stream error, which takes the tool-exec process with it. That is the outcome the bound exists to prevent, reached from the input side rather than the output side. It is recorded here instead of in a note of its own because this note owns `runCommand` and `ToolExecServerOptions`: one record for that function's failure modes, not two.

`runCommand` treats those three codes as a normal completion — the child has exited, and its exit code and captured output are the answer, so a stdin that could not be fully delivered does not become a failed call. The listener attaches to `child.stdin` alone rather than wrapping the flow: any other write error rejects with the command named, because that is this process failing to write its own pipe rather than the command declining input. The other rejection paths are unchanged, and a spawn failure keeps priority, since a command that never started has no exit code to report: `ENOENT` still answers as a `500` when the request carried `stdin`.

## Alternatives considered

- **Kill the command once its output exceeds the bound.** Rejected: it invents a failure for a command that is working, and the model learns nothing about why — while a `find /`-scale listing is exactly the case where truncation is useful and killing is not. The bound's purpose is to keep the sandbox alive, not to police the command.
- **Bound the capture on the host, where the result is already bounded.** Rejected: the host's bound is applied to bytes the container has already accumulated, so it cannot prevent the accumulation that kills the sandbox. Bounding the consumer of a stream says nothing about the cost of holding it.
- **Rely on `memoryLimit` (and, later, Pod `resources`) instead.** Rejected as the answer to this problem: a memory ceiling converts runaway capture into an OOM kill, which is the sandbox death being fixed here, and one subject's legitimately heavy job should not decide when that happens. The ceilings of [Tool-exec sandboxes carry memory and CPU ceilings](2026-09-22-sandbox-resource-ceilings.md) stay the bound on how much a sandbox may take from its host; this bound keeps the capture from reaching that ceiling by accident.
- **Stop reading the stream at the bound.** Rejected: the child blocks on a full pipe and never exits, so a large-output command turns into a hung request. Whatever the server does with the bytes, it has to keep consuming them.
- **Keep the head of the stream instead of the tail.** Rejected: it disagrees with the host's own capture, so the same command would show different bytes depending on which bound cut it — the head when the container's is smaller, the tail when the host's is.
- **Truncate without reporting it.** Rejected: the flags are the whole reason the two layers can differ safely. A caller that cannot tell a tail from a whole value would corrupt a file read and misreport a result's completeness.
- **One bound covering stdout and stderr together.** Rejected: the host's own budget is per stream, and a shared bound makes the two layers incomparable while letting a chatty stderr shrink the stdout a caller reads in full.

## Consequences

- Nothing a deployment reads today changes: the default bound sits above the host's per-stream bound and above every current single-command payload budget, so streams the model sees are truncated in the host layer exactly as before. A stream past 64 MiB is cut in the container, reported as truncated, and read back as a failure rather than as a wrong value: the filesystem adapters reject it, and a `run_code` payload cut this way fails its frame parse instead of returning a partial value. Raising `dsh-code-runtime-container`'s own payload bound past this one is therefore the one configuration change that has to move both values together.
- A running command can retain up to `maxOutputBytes` per stream — twice the field's value for a command writing both — for as long as it runs, which is what the sandbox now holds instead of the whole stream.
- The k8s sandbox carries a new environment variable, so its Pod spec fingerprint changes: a Pod started by an earlier build of this provider is refused as `/runs a different spec/` and is deleted and recreated once by the first call that finds it. The docker provider's start arguments change the same way, with no equivalent cost because a container is rebuilt from a cached start.
- `packages/tenant/tenant-app/src/config.ts` validates the `sandbox` key set with `rejectUnknown`; a tenant-app deployment sets `maxOutputBytes` there under the provider's own field name, as it does for the rest of that provider's `Config` ([tenant tool presentation and concurrency](2026-10-08-tenant-tool-presentation-and-concurrency.md)).
- The bound protects capture, not a command's own memory: a command that allocates the container's memory by itself still dies, and only `memoryLimit` (docker) or Pod `resources` (not yet implemented) bounds that.
- A bare `docker run` of the tool-exec image without the variable keeps today's unbounded capture, which is the same "omitted means unlimited" rule the idle budget uses; both providers always inject a value, so no configuration reaches that path by accident.
- Handing a large script to a command that exits without reading it no longer interrupts the channel: the command's own exit code and output come back as usual, and the stdin simply goes partly undelivered.

### Verification

- `packages/tenant/container-docker/tests/tool-exec.spec.ts` pins the bound's behavior without depending on a host shell — every command in the file, bounded or not, runs through `process.execPath -e`, so the suite also passes on a host with no `sh`: output below the bound and output of exactly the bound are returned unchanged with no truncation reported, one byte over keeps exactly the last `maxOutputBytes` bytes, a single 256 KiB write under a 1000-byte bound keeps its last bytes, a one-byte bound keeps the last byte, a multibyte stream is cut at 1000 **bytes** rather than characters, stderr is bounded separately from stdout, and no bound configured leaves a 512 KiB stream whole.
- The bound is exercised in combination with the other fields `ToolExecRequest` carries, not alone: a forwarded `cwd` resolves a 4 KiB relative read and still returns exactly the bound's tail, a command that consumes all of stdin reports its byte count inside the retained tail, and a command using both under an 8-byte bound returns exactly the stdin half — a capture that dropped stdin or ignored `cwd` fails these rather than passing them.
- The same file pins the stdin path: a command that exits without reading a 4 MiB stdin still answers `200` with its own exit code and output, and the request leaves no `uncaughtException` or `unhandledRejection` behind — the test attaches those two listeners for its own assertion and removes them in `finally`, so it never turns an unhandled error into a global swallow. A spawn failure carrying a `stdin` payload still answers `500` naming `ENOENT`. The rejecting branch for a non-`EPIPE` write error has no reachable input, so no test covers it.
- The same file proves draining rather than asserting it: a command writing 16 MiB against a 1024-byte bound still exits 0 and returns the bound's worth of tail, which a reader that stopped consuming could not reach (the child would block on the full pipe and the request would never settle).
- `packages/tenant/container-docker/tests/docker.spec.ts` and `packages/tenant/container-k8s/tests/runtime.spec.ts` assert the injected variable for a configured bound and for the default, so neither provider can stop handing the budget to the sandbox.
- `pnpm exec tsc -b tsconfig.host.json` is clean, and the suites of `container`, `container-transport`, `container-docker`, `container-k8s`, `subprocess-container`, `fs-container`, and `code-runtime-container` pass.
- The incident's evidence is the deployment's own event output (`Killing … Stopping container tool-exec` at 01:55:27 and 02:03:30 with the Pod recreated ~15 s later); reproducing `find /` against that cluster is the remaining end-to-end check, and it needs cluster access this change does not have.
