# Agent Note: The tenant app as the sole boot entry, onto a config-driven container layer

Status: implemented

English | [中文](2026-08-27-tenant-app-convergence.zh.md)

## Problem

The tenant stack had been assembled through DeepSeek Harness's own composition surface: `packages/bundle/multi-tenant` was a patch layer selected by `dsh --profile multi-tenant`, so starting a tenant meant starting the harness CLI and inheriting its bundle, profile, and cordis.yml machinery. Everything the tenant deployment varies — sandbox image, namespace, host roots — was reachable only through that bundle, which put the tenant's deployment policy in a file owned by the single-tenant product surface. The two execution backends had also grown apart: `container-k8s` declared its schema at module level, which cordis reads for a default-exported class plugin only from the static member, so its `Config` was never validated; the tenant composition then passed `toolTimeoutMs`, `kubeconfig`, `memoryLimit`, and `cpuLimit`, names the provider does not declare, and schemastery dropped them without complaint, so a deployment could configure a sandbox that silently ignored half of what it was told.

## Decision

**The tenant stack is its own application, not a harness profile.** `packages/tenant/tenant-app` owns the bin, the typed config (`src/config.ts`), the plugin inventory (`src/spine.ts`), and the hand-written composition (`src/compose.ts`); it consumes dsh core-layer packages as ordinary workspace dependencies and uses no Loader, cordis.yml, bundle, or profile. `packages/bundle/multi-tenant` and the `multi-tenant` profile template are deleted, along with the demo-only `api-http` and `tenant-demo` packages.

**The deploy plane splits the same way.** `docker/build-images.sh` builds the two images the stack runs — the per-(tenant, user) sandbox `dsh-tool-exec` from `packages/tenant/container-docker/docker/Dockerfile`, and the host `dsh-tenant` from `Dockerfile.tenant` — and each plane keeps its own assembly: `docker/docker-compose.tenant.yml` with `docker/tenant.config.example.yaml` is the local development shape (docker sandbox backend, host network because the sandbox's exec port is published on the host loopback, roots mounted at identical paths inside and outside the container), and `docker/k8s/tenant-host.yaml` is the production shape (k8s sandbox backend, ConfigMap, Deployment, Service). The profile-era deploy files — `Dockerfile.multi-tenant`, `docker/entrypoint.multi-tenant.sh`, `docker/docker-compose.multi-tenant.yml` — are deleted: they started the harness CLI with a patch layer and replayed deploy patches on every boot, which the tenant bin never does. Both images build from a clean checkout in a fixed order, because the Host project graph reaches Client projects whose `/remote` imports exist only after the Host tsdown pass: emit `lib/types` with tsc (this pass reports those imports as unresolved and is not the gate), run the Host tsdown pass that generates the Typert contracts, re-run tsc on both faces as the gates, then the Client tsdown pass that produces the runtime entries some packages (`typert-registry`, Client plugins) emit only there.

**The plugin inventory is one table with a closed module set.** `src/spine.ts` holds 103 rows `{ id, module, config?, disabled? }`; `src/deps.ts` exports `SPINE_MODULES` as a const tuple and `SpineRow.module` takes its element type, so a misspelled module name is a compile error rather than a failure at the row that first runs. Each row stays overridable from the tenant config by id (`plugins.<id>.enabled` / `.config`), and every mounted module is loaded by name, so a row that is disabled costs nothing.

**A module has one owner: either the inventory or a static mount, never both.** The blocks whose configuration comes from a named config section (web server, session store, tenant registry, authentication, administration, both HTTP carriers, PostgreSQL session persistence, container subprocess and filesystem, the container runtime) are mounted by `src/compose.ts` with typed config and do not appear as rows, because cordis refuses a second registration of the same service. After mounting, `assertMountedServices` verifies a short list of services that must exist (HTTP host, session store, tenant admission and administration, the business gateway and its `/api` carrier, the directory picker): cordis skips a plugin whose injections are unmet, so one missing provider silently removes a whole face while the process starts normally.

**One directory picker, the browsing backend.** The server stack mounts `host-directory-picker-browse` and keeps the adaptive `host-directory-picker-auto` disabled: a container has no native chooser, and business clients browse directories over the API.

**One container interface, two providers, one config surface.** `container-docker` (local development) and `container-k8s` (production) satisfy the same runtime interface, and `tenant-app` passes each provider only the fields that provider declares: the k8s backend requires the claim, the host roots, and the Python environment description (`workspaceClaim`, `claimRoot`, `systemRoot`, `pythonRoot`, `toolsRoot`, `pythonEnv`), while a docker-only resource limit or a k8s-only field is refused by the config reader with a named diagnostic instead of being dropped. `container-k8s` declares `static Config`, so cordis validates its schema.

## Alternatives considered

- **Keep the bundle and add a bin on top of it.** Rejected: the tenant deployment would still be configured through the single-tenant product's profile machinery, so tenant-only settings (namespace, claim, per-tenant roots) would live in a file that the harness product also owns and evolves.
- **Let the k8s provider accept the docker field names and ignore what it does not use.** Rejected: silently ignoring a configured value is the failure this change exists to remove; the config reader names the offending key and the provider's own schema is authoritative.
- **Keep `api-http` and `tenant-demo` as documentation of the tenant surface.** Rejected: the admin and agent HTTP carriers plus their tests already demonstrate the surface, and a second demo assembly drifts from the real boot path.

## Consequences

**Bought:** a tenant starts with one command from one package that owns its configuration; the sandbox backend is a deployment choice expressed in that same configuration, and a value the chosen backend cannot honour fails at startup with a named key. The k8s schema is validated, and `tenant-app`'s own composition test mounts the whole spine with every row disabled and asserts the business route answers 404, so a missing carrier is a fail-closed default rather than an open door.

**Cost and deferred work:** the spine table must be kept in step with the composition by hand — a new core plugin is added as a row plus a `SPINE_MODULES` entry, not discovered from a bundle. A block that reads an optional provider once at construction is order-sensitive even though composition states no row order: `tenant-admin` read `tenantRecordStore` once while hydrating, so a store mounted later left the live registry empty and a persisted tenant disappeared across a restart; hydration now runs when the service key appears. The k8s backend requires a Python environment description even though the provider treats it as optional, because the tenant stack's Python tier is not optional in the deployment shapes this package serves. One non-relative `.ts` subpath import in `packages/workflow/workflow-container/src/transport.ts` had to become a package-root import for any consumer that compiles the core layer from source.

**Evidence:** `pnpm exec vitest run packages/tenant` → 26 files / 265 tests pass; `pnpm exec tsc -b packages/tenant/{tenant-app,container-k8s}/tsconfig.json` → exit 0. A live run on the Kubernetes deployment (namespace `dsh`, PostgreSQL and the tool-exec image as independent workloads) proves the path end to end: the service boots with no Loader, profile, or bundle; `POST /admin/tenants.create` writes a tenant and `tenants.get` returns it after a pod restart; `POST /api/session.create` and `session.prompt` run a turn whose `bash` tool executes inside a per-tenant sandbox pod created from the configured image, and the session log persists in PostgreSQL. The production image follows that same path: built from `Dockerfile.tenant`, imported with `ctr -n k8s.io images import`, and rolled out as `dsh-tenant:latest`, the service boots from the built `packages/tenant/tenant-app/lib/bin.js` — no tsx, no source launch — and runs the same turn end to end, with the `dsh-tenant` Service reaching the API in-cluster.
