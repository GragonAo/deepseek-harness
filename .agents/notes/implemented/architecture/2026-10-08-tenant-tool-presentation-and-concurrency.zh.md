# Agent Note：租户的工具呈现与并发是配置

Status: implemented

[English](2026-10-08-tenant-tool-presentation-and-concurrency.md) | 中文

## 问题

业务侧通过 MCP 访问自己的数据挖掘后端，大约 180 个工具，而一个案件的会话预期在一轮里查询其中许多个。租户栈在 `packages/tenant/tenant-app/src/spine.ts` 里写死 `mode: 'both'` 装配 `@deepseek-ai/dsh-tools`，于是每个租户服务既在系统提示词里下发每个工具的原生 schema，**又**下发生成的 `run_code` SDK 面；想要其中单独一种的部署没有任何值可以表达这件事：呈现方式是装配的属性，不是部署的属性。

那份原生列表的提示词成本同样没有部署侧的答案。租户栈挂了 `tools-tier`（案件级、用户全局、系统级三个工具目录）与 `tools-manifest`（把这些目录里的 `*.yaml` 清单变成带 rank 的工具），但两者都只会**新增**一个工具或遮蔽同名的那个。谁都删不掉东西，租户栈里也没有任何地方调用注册表的按作用域限制 API，因此 180 个 MCP 工具对每个案件都保持可见，schema 列表随部署的工具总数增长，而不是随案件真正用到的那些增长。

执行侧则是相反的缺陷。租户读取器拒绝它不认识的字段名，于是两个容器 provider 的若干 `Config` 字段根本无法从租户配置里设置——写一个就带着「未知字段」加载失败。最清楚的是 `maxOutputBytes`：`container-docker` 与 `container-k8s` 都把它默认成 64 MiB，也都写明它必须高于宿主自己的结果预算（见[沙箱输出上限](2026-10-08-sandbox-output-bound.md)），而需要另一个值的租户只会静默拿到默认值。`dsh-tools` 的 `maxParallelSubCalls` 默认 10，会把 180 个工具的扇出摊成十八个波次，而每条 MCP server 的行根本没有携带任何并发值。

## 决策

工具呈现方式、案件级可见工具清单、`run_code` 的重叠窗口、容器 provider 的每个字段，以及每条 MCP server 的调用上限，在租户栈里都是配置或案件数据，并在它既有的默认值所在之处解析。

### 租户默认的呈现方式是 `both`

`tools.mode` 默认 `both`，`tools.maxParallelSubCalls` 默认 32；`tools` 那行推导出这两个值，因此插件的默认值在租户服务里从不生效。`both` 让直接形态一直可用：读一个文件、问一句的会话直接调用它想调用的工具，而一次跨上百张表的扇出仍然可以写成一段 `run_code` 程序。`native` 与 `code` 各自只差一个配置值，而程序里的每个子调用都会重新进入完整的工具管线，因此权限、超时与结果边界都不取决于呈现方式。

`code` 并非不需要装配，这也是不让它当默认值的另一个原因：除非挂上一个注册了 SDK 渲染器的 `ctx.codeRuntime`，提示词组装会失败；租户栈通过 `code-runtime-container` 提供它（`language = 'typescript'`）。把那一行换成语言未注册的一行，会在第一次组装提示词时失败而不是在加载时——这对一个主动要 `code` 的部署可以接受，对一个没要的部署是多余的暴露。

### 案件可见工具声明在案件自己的工具层级目录里

提示词成本的杠杆是可见集合，不是呈现方式。`ctx.tools.restrict()` 已经按作用域表达了它，层级目录也已经存在，缺的是一个消费者：`@deepseek-ai/dsh-tools-restriction` 读取每个层级目录里保留的 `restriction.yaml`（`allow` 与/或 `deny`，各自是一份全局工具名与末尾 `*` 前缀的列表），并在 `agent/created` 窗口里把它应用到刚创建的 agent 的作用域上。

案件层写 `allow` 加前缀。第三方 server 日后新增一个工具时，两个方向以相反的方式失效：`allow` 只放行它点名的，所以新工具在有人把它加进文档之前一直不可见；`deny` 只挡它点名的，所以新工具会直接出现在每个案件面前。案件文档因此写出它用到的组——某个案件类型整组保留的工具写成 `mcp__icac-bill__*`——而 `deny` 文档留给相反那件事：运营方遮盖绝不能到达的操作，并在对方加工具时重新核对。前缀形态是让 `allow` 在这个工具数量下还可用的原因：没有它，整组保留一个 server 的案件就得列出那三十来个名字，并在 server 每次变更时重列一遍。

前缀就是一个字面前缀后面只跟一个 `*`。`mcp__*__search`、`?`、字符类与正则都在加载时被拒，并在消息里点出文件与那一条，因为这套语法要能当名字来复核，而不是当一门模式语言。精确名与前缀可以混在同一份文档里，而到达 `restrict()` 的永远是精确名：前缀在同一个 `agent/created` 窗口里对着注册表当时持有的全局名字展开（它自己的 `schemas()` 视图，减去保留的 `run_code` 呈现通道——它不是可限制的名字），所以限制机制本身没变，展开是按次而不是按文档。匹配不到任何已注册全局名的前缀会让那次创建失败并点出文件与前缀——在 `allow` 下写错前缀会让全部工具都可见——一次展开超过 512 个名字同样被拒。展开结果不写进会话日志：它是对工具列表做过滤的输入，而不是自己进入模型请求的输入，模型看到什么本来就能从注册表提供的 schema 还原。

这个插件不接收层级根目录。它从 `ctx.toolTiers` 解析——那是 `@deepseek-ai/dsh-tools-tier` 用自己的 `usersRoot` 与 `systemToolsDir` 配置、加上当前租户的 `workspaceRoot` 建出来的 provider——因此清单加载器与限制读取器不会对某个层级属于哪个目录产生分歧。它在租户组合清单里挂在 `tools-tier` 与 `tools-manifest` 之后，这也让它能在加载时解析系统层那份文档：provider 在没有租户与用户作用域时只解析系统层；案件层与用户全局层的文档需要 (租户, 用户) 作用域，因此在该作用域下创建 agent 时才解析。每份文档在那时都会再解析一次，所以一份写错的系统文档也会让此后每个 agent 的创建失败，无论组合怎么处理某一行自己的加载失败。

一份可见集合同时喂给组装的 schema、生成的 SDK 面与执行解析，因此这份声明让两种呈现形态一起变小，而被挡掉的名字既不在提示词里，**也**会被执行器当作未知工具拒绝。这份声明过滤的是作用域**继承来的**表面——全局层与每一个祖先作用域，也就是每一个插件工具和每个 MCP 服务器的工具——从不影响分层清单注册进 agent 自己作用域的那些，因此案件的 `allow` 列表不必列出它自己的清单，也藏不住它们。名字在创建 agent 时对着注册表校验，而被拒绝时会连带写出肇事的那份文档，所以一个案件写了当时还没注册的工具——一个还在连接的 MCP 服务器，或者一个拼错的名字——会让创建失败并指名那个文件，而不是静默退回整份列表。

### 三层的文档取交集，近层不能重新放行被挡掉的名字

这些文档按交集合成，这正是注册表对作用域链上多条限制的规则，所以部署方可以用它已经从 `ctx.tools.restrict()` 知道的规则来推理三层。`tools-tier` 的 rank 只剩一个作用：决定文档应用的顺序，也就是诊断里写出哪个文件。

取交集是刻意选的，而不是让提供文档的最近一层单独说了算。案件目录对租户可写，系统目录归运营方所有，所以「近层覆盖」会让案件重新放行运营方移除过的工具；取交集把这个决定留在运营方手里，同时案件仍能继续收紧。那条备选还得在调用 `restrict()` 之前先把三份文档合并成一份过滤器，这会把合成规则变成这个插件的属性，而不是它所应用的那个机制的属性。

`run_code` 是保留的呈现通道而不是能力：文档不能写它，它在 `code` 与 `both` 两种呈现下都保持可见。

### 32 是默认的重叠上限

`maxParallelSubCalls` 限制一段 `run_code` 程序里有多少子调用可以重叠；只有被工具自己归类为并发安全的调用才会重叠，而这个上限不改变提示词。32 是照着业务负载定的，不是照插件自己的 10：数据挖掘的扇出是按分片或表撒开的一批调用，所以 32 路让 180 个工具在六个波次里跑完，同时在途的集合停在几十条并发 HTTP 请求、结果缓冲与被重新进入的管线执行这个量级。

### 沙箱段承载两个 provider 的 Config 字段

`maxOutputBytes`、`cliTimeoutMs`、`readyTimeoutMs` 与 `readyPollMs` 并入共享沙箱字段（`container-docker` 与 `container-k8s` 都定义了它们），`command` 与 `env` 并入仅 Kubernetes 的字段集。每个都按 provider 自己的字段名透传，只有租户段本来就改名的三个例外：`image` → `toolExecImage`、`imagePath` → `toolExecImagePath`、`toolTimeoutMs` → `transportTimeoutMs`。读取器逐个校验，所以类型写错或名字拼错会带着字段路径加载失败。

### 挂上的块加载失败就让启动失败，并指名那一块

`createTenantApp` 留住每一块挂上的插件的 fiber——静态挂载的那几块、每一行启用的组合行与每一条 MCP 行——在所有块都挂完之后用 `Fiber.await()` 统一收口，失败包装成 `组合行 <id>（<模块>）启动失败`，原始错误放在 `cause` 里。挂载时注入就已经满足的块不需要这一段：`ctx.plugin()` 会等出结果并重抛。需要它的是那种注入的服务由**后面**某一行提供的块：它的 apply 被推迟到那个服务出现时的 epoch，那时 `ctx.plugin()` 早已返回，Cordis 把失败记在 fiber 上、打一条日志，什么都不会失败。收口之所以必须放在所有挂载之后，也是同一个原因——那一刻注入都已提供，被推迟的 apply 要么跑完了、要么已经在途，`await()` 才看得见它。注入永远不满足的块是 PENDING 而不是失败，仍然由 `assertMountedServices` 指出缺哪个服务。

备选做法是把它留给 Cordis 已经打出的那行日志，而它恰好丢掉最不能静默的失败：被挡掉的 `tools-restriction` 那一行挂不上，模型就看到全部 160 个挖掘工具；鉴权行挂不上，接口就是敞开的。一个服务端跑不出它配置里声明的能力时，不该报成功，所以它同时把已经挂上的块释放掉：调用方拿到的是一次拒绝，而不是一个开着监听端口、连着数据库池的半成品；释放本身出错只记日志，不替换掉那条指名了哪一块的信息。

### 每条 MCP server 的行只透传，不给默认值；部署逐行写明它

这一段只承载一种传输形态，不是两种。`mcpServers[]` 接受客户端 Streamable HTTP 那一支（`serverName`、`transport: streamable-http`、`url`、`headers`、`toolConcurrency`）；stdio 那一支无法从租户配置表达，因为子进程 server 是宿主组合的决定而不是每个部署的地址，也没有部署挂过它。所以一行 stdio 配置在加载时就以未知字段（`command`）失败，而不是被静默忽略。

转发的是客户端判别联合的 `Config` 真正声明的东西——`serverName`、`transport: streamable-http`、`url`、`headers`、`toolCallTimeoutMs`、`failOnStartupError`，以及 `toolConcurrency` 的全部十二个键（`policy`、`maxConcurrentCalls`、`exclusiveTools`、`retryTools`、`mode`、`decreaseFactor`、`recoveryStep`、`recoveryQuietMs`、`countTimeouts`、`retryAttempts`、`retryBaseDelayMs`、`retryJitterRatio`）——每个都用客户端自己的字段名，每个都在这里按类型与取值域校验（策略或模式取自它自己的取值、正整数或非负整数、0..1 的比例、布尔、非空名字数组、字符串表），所以一个拼错的子字段会加载失败，而不是以被忽略的键的身份到达客户端。读取器不重述客户端更细的边界——`decreaseFactor` 严格落在 0 与 1 之间、`retryAttempts` 最多 5、两个定时器的上界——因为插件自己的 resolve 步骤会重新判定每个取值并让那一行的挂载失败、指名那一行；在这里再抄一份就是第二份边界，迟早和第一份漂移，而越界的取值怎么算都是响亮的。`headers` 就是认证路径：客户端把它作为 `requestInit.headers` 附在每个 MCP 请求上。读取器只接受客户端真有的传输方式，因此 `sse` 已经不在接受的取值里：它从来不是客户端的传输方式，接受它只是把失败推迟到那一行挂载的时候。客户端自己的 `reconnect` 段是唯一刻意不透传的字段：这里的部署用不到它，而未透传的字段按客户端自己的默认值生效，不在这里再写一个默认值。

两份部署示例的每一条都写了 `failOnStartupError: true`，因为客户端的 `false` 是唯一会藏住配置错误的那个默认值。取值 `false` 时，地址写错、端口不通或对方还没起来只留一条日志，那一行挂上却没有工具——读起来就像一个本来就不提供工具的 server；取值 `true` 时，同一次失败会让那一行的挂载被拒，从而打挂启动，并指名那一行（`组合行 mcp-<序号>-<serverName>`）。它还决定案件文档对缺失的组会怎样：匹配不到注册表任何名字的前缀会让 agent 创建失败，所以一个悄悄少了一条 server 的部署最迟在第一个案件上就会失败，而不是在启动时。

`headers` 也是 Kubernetes 示例把整份租户配置从 Secret 而不是 ConfigMap 挂进来的原因。请求头的值只能来自配置文件——`applyEnvOverrides` 的环境变量覆盖清单是固定的，`mcpServers` 不在其中，所以在文件里放占位符、靠环境变量替换并不成立——而 ConfigMap 是任何持有 `get configmap` 权限的主体都能读的。那份文件由与工作负载并列指名的 Secret 以 `0400` 权限只读挂进容器。这不需要改 RBAC：卷挂载的 Secret 由 kubelet 取，Pod 的 ServiceAccount 从不读它，命名空间的 Role 依旧不授予任何 `secrets` 权限。代价是仓库里那份清单带的是占位符，而应用的那份不能带：把仓库这份 apply 到已经装着真 token 的 Secret 上会把它们换回占位符，所以文档给出的流程是应用一份本机填好的副本。

上限有两个，区别决定共用后端看到什么。`tools.maxParallelSubCalls` 是天花板，按 run_code 程序算，所以并发的每个会话各有一份；`mcpServers[].toolConcurrency.maxConcurrentCalls` 是分配，是每条 server 一道全宿主共用的闸，所有会话、所有程序一起走它。在客户端默认的 `mode: adaptive` 下这个数同时是起步值与它的上界：闸真正执行的上限由每个插件实例按这条 server 自己的被拒情况学出来、且不持久化，所以一行写的是一个起点而不是量过的常量，量过的部署写 `mode: fixed` 把它固定住。一批入口共用同一个后端进程时（`host:port` 相同、只有路径不同），它的并发就是各条 cap 之和，于是天花板设成那个后端扛得住的总量，再把这个总量分给各组。

但那些默认值对这组 server 是错的，所以租户的部署示例逐行写明这一项。这里的每个 MCP server 都是第三方且不可改：它不声明 `readOnlyHint`，也不声明 `idempotentHint`，于是客户端默认的 `annotations` 策略没有可读的意图——一个对谁都不像只读的工具就这么被放行。部署方的回答是 `policy: parallel`——并发的判断与责任都落到我们这边——加上按组分下去的 cap：没人量过的那一组起步就是串行。吞吐由此来自**跨 server** 而不是单条内部：不同服务之间没有共享状态，N 条串行的 server 照样给出 N 个在途调用，而这是扇出里无风险的那部分。调高某一组的数是一件单独的事，要在那一组被验证扛得住之后才做；从那一刻起它收到的提交顺序不再有任何保证，所以写数据的工具写进客户端自己那条 server 的 `exclusiveTools` 名单——它们不与任何别的调用重叠。重复执行在客户端是另一个答案：只有声明了 `readOnlyHint` 的工具、或部署方加进 `retryTools` 的工具，其被拒调用才会被重发；把写工具写进 `exclusiveTools` 只规定了顺序，本身并不阻止第二次尝试。

## 被否决的备选

**整个部署默认切成 `code`。** 它会一次性收回原生列表，而且这是最初做出的决定。否决它的理由是这种收敛会对它帮不上的工作收税：以 `code` 为租户默认值时，读一个文件、问一句的会话必须先写一段程序才能调用工具，模型在每一个小任务上都要付这笔开销。提示词膨胀是工具**数量**的属性，不是呈现方式的属性，而 `both` 加上案件级可见工具清单能在它出现的地方消掉它——案件的清单让原生列表与 SDK 声明一起变小，同时直接形态对那些从不需要它消失的会话保持可用。真想要这种收敛的案件写 `tools.mode: code`。

**把 `mode` 写死在装配里。** 字面量 `mode` 正是问题描述的缺陷：一个只有几个工具、模型又能好好调用它们的部署想要另一种形态，而仓库约定本来就禁止把随部署变化的取舍放在装配里。这个 Note 的两次尝试之间变的只是取值——写死从来都站不住。

**只部署一种呈现形态并接受它的成本。** 单独发任何一种都会让租户服务丢掉它需要的东西：只有 `native` 时每次请求都付整份列表，只有 `code` 时琐碎任务也被迫写程序。两者只差一个字段，所以由装配说出兼顾两者的那个值，由案件级清单处理数量。

**让 `dsh-tools` 保留自己的默认值（native、10）。** 那么租户栈对呈现方式什么都不说，每个部署都得覆盖一行配置才能到达预期行为。租户栈是知道这份负载的装配方，所以默认值归它；插件的默认值留给什么都不说的装配。

**用分层清单来隐藏工具。** 清单把工具注册进 agent 自己的作用域并遮蔽同名的那个，所以案件可以替换某个全局工具的定义或加上自己的——但永远删不掉一个，而且无论案件提供什么都改不了 180 个 MCP 工具的可见性。把这个机制复用到可见集合上不可能：从视野里移除一个名字的是注册表的限制 API，所以这次改动是给它补一个消费者，而不是在它旁边再立一套机制。

**让清单加载器顺手读那份限制文档。** 加载器本来就在同一个 `agent/created` 窗口里遍历这些目录，一个插件可以做两件事。两份文档是关注点不同、合成规则也不同的东西：清单带 rank 且只做加法，限制取交集且只做减法；把它们放进一个包会让限制绑定到清单加载器的发布节奏与配置上。加载器只保留对另一份文档的一处耦合——跳过那些保留文件名，因为限制文档不声明任何工具，把它当清单解析会让每一个做了限制的层级都失败——而限制读取器拥有格式、合成与诊断。

**让提供文档的最近一层覆盖更远的层。** 见上面的决策：它会把运营方系统层挡掉的工具的交还权交给对租户可写的案件目录，而且会把合成规则放进这个插件里，而不是放进它所应用的机制里。

**让案件层反过来 `deny` 它不想要的东西。** 那会是更小的一份文档，否决它的理由是：第三方 server 演化时，两个方向以相反的方式退化。

**让文档表达通用通配或正则。** `mcp__*__search` 这种形态、字符类或正则能用一条覆盖更多形状，否决它的理由是复核成本：写成名字的文档可以被人拿去对着 server 的工具列表核，而一门模式语言会把这次核对推给最后一个编辑文档的人。末尾的 `*` 覆盖了工具数量真正要求的那一种形状——一整个 server 的组——其余每一条都是同一次复核会拿去和 `tools/list` 对照的精确名。

**前缀在进程里展开一次，而不是每次创建 agent 都展开。** 插件加载时注册表已经有名字，把展开结果缓存起来能把这份工作移出 `agent/created` 窗口。否决它是因为那样一来展开就对更晚才连上的 server 无效：一条在限制插件加载之后才完成工具同步的 MCP 行，会从每一份点名它那组的文档里消失，而且失败形态是一个静默变窄的 `allow`，而不是一条诊断。按次展开读的是注册表当时的名字，而那正是注册表会拿去校验这些名字的那个集合。

**把可见工具清单放进租户配置或案件记录。** 案件是运行时创建的，它的工具需求随数据变化，因此部署级的清单表达不了它；把一份文件形态的数据放进数据库字段则是把数据放错了地方。层级目录本来就承载案件的声明式工具面，而案件的目录正是它的运营方写东西的地方。

**把沙箱段开放给任意字段名。** 接受未知键会让拼错的 provider 字段静默失效——正是 `rejectUnknown` 存在的目的——并把真正的检查推到 provider 恰好注意到的地方。这个段改为逐一枚举每个 provider 的 `Config`，字段与 provider 字段一一对应。

**给 `mcpServers[].toolConcurrency` 一个默认值。** 见上面的决策：租户侧无从知道哪条第三方 server 扛得住重叠，所以默认值要么遮蔽 MCP 客户端的那个，要么与它不一致；每个部署自己逐行写明它真正验证过的那一个值。

**让 MCP server 声明它们的工具注解。** 那样客户端自己的 `annotations` 策略就能在不写任何租户配置的前提下做出判断，但这些是我们改不了的第三方 server：一个不声明 `readOnlyHint`、也不声明 `idempotentHint` 的 server 不是可以等它补的 server，而把它的沉默当作「只读」正是会出事的那种假设。部署方改为自己写明策略。

**接受部署方那种以 server 名为键、带 `enabled` 开关的 MCP 映射。** 那是某个部署已有的形状，而租户这一段保留列表：映射的键会变成 `serverName` 的第二种写法，而工具命名空间、重名检查与所有诊断读的都是同一种；`enabled: false` 也没有表达列表表达不了的东西——没列出来的 server 就不会挂。转换是机械的，租户示例里直接给出转换后的那些行。

**在同一次改动里让呈现方式按案件或按 agent 不同。** 机制是有的——`@deepseek-ai/dsh-agent-tool-presentation` 允许一个 preset 为自己的作用域声明 `ctx.tools.presentAs(mode)`，于是同一个进程里 code 模式与 native 的 agent 可以共存。它没有挂在租户栈里，也没有任何租户配置能指名一个 preset，所以按案件差异化是另一次改动，而不是这次改动里的一个取值。这次改动关掉的是那个缺口里「按案件限制可见工具」这一半。

## 影响

在出厂的默认值下模型同时看到两种形态。带几百个工具的案件必须提供一份限制文档，否则每次请求都要付整份原生列表；而文档是在创建 agent 时读取的，所以编辑它影响的是此后创建的 agent，不是正在跑的那些。

可见集合属于案件，不属于工具：案件藏不住它自己分层清单注册进来的工具，因为限制只过滤作用域继承来的东西；而共享同一个层级目录的两个案件也没法对同一个名字有不同意见。这条豁免同时意味着清单加载器与限制读取器之间的监听器顺序不决定任何事——清单工具注册进 agent 自己的作用域，从不进入可限制的名字集合，所以一份写明它的文档无论哪个监听器先跑都会被当作未知全局工具拒绝，测试把这一点固定下来。它也是前缀替代不了一份清单工具的原因：前缀只对全局名字展开。一个案件写了注册表里还没有的名字——比如启动时仍在连接的 MCP 服务器——就完全无法创建 agent，直到那个名字存在为止；这是有意的响亮失败，而不是静默退回整份列表。

前缀让文档的边界外移，所以它的影响不只是一条的。它在创建 agent 时解析，意味着在一条新 MCP server 连上之后创建的 agent 会看到那个 server 加进来的组，而更早创建的不会；一个 server 不再暴露某个工具时，每一处前缀都静默变窄——而精确名消失会让那份文档下的下一次创建失败。所以维护案件文档的人要把它和它点名的组放在一起，在这个 server 改工具列表时复核它。匹配不到任何东西的前缀是同一个性质响亮的那一端：它没法冒充成一个「放行得很少」的 `allow`，而部署最迟在第一个案件上就知道那条 server 不见了。

因此每个租户服务每个层级目录要读两份保留文档，而限制读取器是案件能被限制的前提：只挂 `tools-tier` 与 `tools-manifest` 而不挂它，所有工具都保持可见。既然挂不上的块现在会让启动失败，这一种组合——以及配置里声明的每一块——要么起来、要么让服务起不来；一直带着某一行静默缺席在跑的部署，装上这一步之后会拒绝启动，修的地方是那一行自己的配置或模块。

`sandbox` 段镜像了两个 provider 的 `Config` 定义。某个 provider 改名、删除或新增字段时，必须在同一次改动里更新租户读取器与透传表，否则那个值就从租户配置里够不着了。

租户栈对它自己拥有的每个旋钮只留一个默认值，对挂载插件拥有的旋钮一个都不留，因此每条 server 那一行的含义以客户端的 README 为准。照租户示例写的部署逐行写明策略、分配与写工具：cap 分给共用同一后端的那些组，没人量过的组起步串行。让某一行保持沉默的部署拿到的是客户端自己的默认值——先 `annotations`、再 10、再空名单——那等于拿 server 从来没写过的注解做了一次并发决定。

### 验证

`packages/tenant/tenant-app/tests/app.spec.ts` 对着真实装配固定推导出的 `tools` 行配置：未配置的租户以 `mode: 'both'` 与 `maxParallelSubCalls: 32` 挂载 `ToolRuntime`；配置的值到达同一个插件；`tools.mode` 拒绝三种呈现方式之外的值，`tools.maxParallelSubCalls` 拒绝 `0` 与 `1.5`；某行 server 的 `headers`、`toolCallTimeoutMs` 与 `toolConcurrency` 的全部十二个键都到达该行挂载的 `mcp-client` 实例（`exclusiveTools` 与 `retryTools` 各自独立），而另一行保持沉默时客户端自己的默认值留在原位（`annotations`、10、两个空名单、`adaptive`、0.5、1、2000、true、0、200、0.2、客户端的超时、`failOnStartupError: false`）；一行的 `transport` 不是客户端真有的取值、`headers` 的值不是字符串、`exclusiveTools` 有空的项、或带了 stdio 字段时，配置加载失败并指明那个路径。同一个文件还逐条固定新键的拒绝：单数的未知键 `retryTool`、`mode: fast`、`decreaseFactor: 2`、`retryAttempts: -1`、`recoveryQuietMs: 1.5` 以及非布尔的 `countTimeouts` 都在配置加载时失败，消息里带键路径。

同一个文件对着一个连不上的 server 用真实启动固定 `failOnStartupError` 决定什么：写了 `true` 时 `createTenantApp` 以 `组合行 mcp-0-mining（@deepseek-ai/dsh-mcp-client）启动失败` 加上客户端自己的信息拒绝启动；不写时同一行照常挂上，并报出客户端的默认值。这就是「地址写错会打挂启动」与「地址写错看起来像一个没有工具的 server」的区别。

同一个文件在真实组合上固定启动期失败的行为，而且选在延迟执行这条路径真的会出现的地方：提供 `tools` 的那一行排在 `tools-restriction` 之后，所以限制行的 apply 要等 `tools` 存在才跑。给限制行一个未知配置键、以及在系统层级目录里放一份格式不合法的 `restriction.yaml`，两种都会让 `createTenantApp` 以 `组合行 tools-restriction（@deepseek-ai/dsh-tools-restriction）（注入满足后才执行）启动失败` 加上插件自己的信息拒绝启动；把收口那一步去掉，这两条断言就会失败。同一批行正常启动时能挂上。

两份部署示例是把 `mcpServers` 段按部署方会做的那样取消注释、再经真实读取器加载验证的：十二行、同一个宿主、各条 cap 之和等于文档里写的天花板、每行都带 `headers` 与 `failOnStartupError: true`、导入组带更长的调用超时。Kubernetes 示例同样按它自己的结构读了一遍：三份文档，租户配置在 `Secret` 的 `stringData` 里，那份配置既按挂载时的样子、也把 `mcpServers` 段取消注释之后都能被读取器接受，卷来自那个 Secret 且权限是 `0400`，整个工作负载里不再有任何 `configMap` 卷。

`packages/tenant/tenant-app/tests/app.spec.ts` 用真实组合挂上 `tools-tier` 与 `tools-restriction` 两行，固定限制那一行在不带配置时也能挂上，且它读取的 provider 报出的就是这次启动的系统层级目录。

`packages/tenant/tools-restriction/tests/tools-restriction.spec.ts` 对着真实注册表、provider 与租户/用户作用域固定限制读取器：一份案件文档在十二个已注册全局工具里放行十个，该 agent 的 `ctx.tools.schemas(agent)` 就只剩那十个，另外两个从执行器拿到 `unknown tool`，而全局视图仍然持有全部十二个；三份文档合成为交集，因此案件层与用户全局层的 `allow` 都不能重新放行系统层挡掉的名字；`both` 模式的提示词同时从原生工具列表与生成的 SDK 声明里丢掉被挡掉的名字；写了未注册工具的文档会让 agent 创建失败，并带上注册表的信息与文档路径；格式错误的系统层文档与任何配置键都在加载时失败；同一层级的清单工具与被挡掉的全局工具并存，而写明那个清单工具的文档会被拒绝；dispose 掉插件的 fiber 之后限制停止生效。

同一个文件既把前缀语法与展开当成纯函数固定，也穿过注册表固定。`parseRestriction` 把末尾的 `*` 认成前缀，允许精确名与它在同一份文档里并存，并以「文件 + 那一条」否决 `mcp__*__search`、裸 `*`、`?`、字符类、竖线与反斜杠转义；`expandRestriction` 把前缀变成它匹配到的名字，对匹配不到任何东西的前缀报出文件、前缀与注册表当时真正持有的名字，并拒绝一次展开超过上限的那一条、接受正好等于上限的。穿过一个真的挂起来的注册表时，案件的 `allow: [mcp__icac-bill__*, mcp__icac-case__search]` 让那个 agent 只看到两个账单工具与点名的那一个案件工具，其余从执行器拿到 `unknown tool`，而前缀匹配不到任何名字时那次 agent 创建会失败；一个与前缀同前缀的清单工具在组被放行的同时保持可见；系统层文档里的非法前缀在加载时失败。

`packages/tenant/tools-manifest/tests/tools-manifest.spec.ts` 固定清单加载器这一侧的保留文件名约定：一个同时放着清单与 `restriction.yaml` 的层级目录注册清单、忽略那份限制文档，而不是在它上面失败。

仓库测试没有覆盖、由 owner 在集群上验证的部分：`both` 模式的提示词能对着挂载的容器运行时组装出来；180 个子调用的挖掘扇出按配置的上限而不是插件的 10 排空；以及每条 server 的上限确实在限流某一个 MCP server 的调用。这里没有测试打到真实 MCP 服务器——仓库的 MCP 客户端测试拥有那个面。
