# Agent Note: Session delete tombstones the identity for the life of the process

Status: implemented

English | [中文](2026-10-19-session-delete-tombstones-the-identity.zh.md)

## Problem

Putting a session away is not removing it: `workspace.archiveSession` hides one from the grouping surfaces and an unarchive restores its place, so no host call erases a conversation ([archive decision](../feature/2026-07-31-session-archive-global-set.md)). The storage seam removes a stored log ([log-deletion decision](2026-10-19-session-log-deletion.md)) and the workspace registry forgets one session's accounting ([forget decision](2026-10-19-session-forget-removes-registry-accounting.md)), but neither operation stops an identity from being a session, and three facts about a removed identity belong to the gateway:

- **An ordinary session stays attached after its turn ends.** The gateway holds its `Session` in memory, and nothing tears that Session down: `AgentRegistry` states no eviction, the only teardown path is the `AgentHandle.dispose()` capability that `create()`/`resume()` hand to the consumer which created the agent, and this gateway keeps only `handle.agent` ([the measurement that recorded the retained lifecycle](2026-08-03-per-session-agent-presets.md)).
- **`session.list` merges two sources**: the sessions attached in memory and the cold sessions the persistence service lists. Removing the log alone therefore leaves the id listed from the memory half — a removed conversation keeping its sidebar row, with `session.search` searching exactly the rows `session.list` returns.
- **Workspace accounting is a third store**: the `sessionIds` slot of every workspace record that accounts the id, plus the registry-global `archivedSessionIds` set. Both outlive the log.

The state that closes this cannot be durable: after a restart nothing is attached, so no writer remains that could re-create the log, and the durable absence the backend reports is the whole truth ([log-deletion decision](2026-10-19-session-log-deletion.md)). What is missing is per-process.

## Decision

**`session.delete` composes the two removals and relies on the persistence backend's process-local deleted state to stop the identity from being addressable.**

Wire: `session.delete({sessionId}) → {deleted: true}`, registered as a `session.*` unary method — `SessionsApi.delete` as the signature of record, `sessionDeleteRequestSchema`/`sessionDeleteValueSchema` as its wire validation, the `RpcMethodMap` entry, the `UNARY_ROUTES` dispatch entry, and the carrier client's unary method.

- **Irreversible, and a different gesture from archiving.** The log is the authoritative source of everything a session shows, so a delete has no return path. `workspace.archiveSession` hides a session and keeps its registry place so that an unarchive restores it; a caller that needs that reversible gesture has that method, and `session.delete` does not promise its return.
- **Refusals.** A session whose turn is running rejects with `agent-busy` and `details.reason: 'TURN_RUNNING'`, touching neither store, so the caller cancels first. A session behind subagent routing rejects with the shared subagent-ownership `agent-busy` (`use subagent delivery for this child session`) — the rejection every other session-addressed method returns for such an id. A deployment composing no session persistence answers `internal` naming the missing service, because removal is the backend's capability to state. A durability failure is not a business answer: the operation rejects, and through the carrier that is a 500, never a `session-not-found` a client could read as an answer about the session.
- **Commit order: log first, workspace account second.** `SessionPersistence.delete` is the step that fails on durability, and `forgetSession` is idempotent, so a failed attempt leaves the session existing, accounted, and findable, and a retry finishes the removal. The reverse order would have destroyed the accounting of a session that still exists, and would have published archive and grouping snapshots derived from that removal.
- **What the deleted state closes.** `session.list` and `session.search` drop the id, so the memory half of the listing cannot revive it; the reads that resolve a session fall through to the log read and answer `session-not-found`, the log being gone, both where the read goes through `readSessionState` (`session.fork`, `session.attachment`) and where it goes through `historySourceFor` (`session.history`); `session.prompt` refuses at its turn gate before any agent lookup, so the leftover Session admits no turn whose log write the tombstone would refuse; `ensureSession` refuses the id at its entry instead of resuming or creating it; and the still-attached Session's later log writes are refused by the backend rather than materializing the deleted log again.
- **The carrier gates the method before the gateway.** `@deepseek-ai/dsh-agent-http` adds `session.delete` to the `sessionId`-addressed method set it resolves against the ambient `(tenant, user)` before delegating, so a foreign id is answered `session-not-found` and never reaches the shared gateway.

## Why the composition lives in `dsh-host-apiproxy`

The gateway owns both sources an identity has to leave — the attached sessions in memory and the persistence listing — and it is already the one place that resolves an id to a session or an agent, so the deleted-state check and the commit order sit where `ensureSession`, `readSessionState`, and the listing merge live. `@deepseek-ai/dsh-workspace` owns registry state, and its `forgetSession` deliberately leaves the deletion to its caller ([forget decision](2026-10-19-session-forget-removes-registry-accounting.md)); a persistence backend knows nothing about attached sessions, so it cannot decide when an identity stops being addressable.

## Why the carrier must gate it

The gateway scopes a request through the ambient `(tenant, user)` authority its providers read, but `session.delete` names an identity that is live in the process-wide agent registry, and the multi-tenant carrier serves one shared gateway for every tenant ([multi-tenant slice](2026-08-24-multi-tenant-slice.md), [user-membership decision](2026-08-26-tenant-user-membership.md)). Ungated, one tenant's request could delete another tenant's live session, and the removed log is that other tenant's data. The carrier therefore resolves the id before delegating, exactly as it does for the other `sessionId`-addressed methods, and the same pass filters `session.list`/`session.search` items to sessions the tenant did not archive: an archived session keeps its registry place for an unarchive, but a listing that still showed it would offer a session its tenant put away.

## Alternatives considered

- **Delete the log and let the listing settle.** Rejected: the Session stays attached, so the memory half of `session.list` keeps its row and the session looks live while refusing every write.
- **Evict the live Session instead of relying on the deleted state.** Not the shipped mechanism, and the deferred improvement: this gateway holds no `AgentHandle` to dispose, and `AgentRegistry` states no eviction for an agent another consumer entered, so a delete path cannot tear down a Session it does not own ([preset decision](2026-08-03-per-session-agent-presets.md)).
- **A durable marker for a deleted identity.** Rejected: a crash between the marker and the log removal leaves a session listed but unreadable, and after a restart the durable absence already answers the question ([log-deletion decision](2026-10-19-session-log-deletion.md)).
- **Refuse to delete an attached session.** Rejected: an ordinary session stays attached after its turn ends, which is exactly the session a user asks to erase, so the guard would make the operation unusable in a web host.
- **Gate ownership in the gateway instead of the carrier.** Rejected: the gateway's scoping comes from ambient request authority, which answers for the request rather than for the identity it names, and a destructive method needs the address check before the shared registry is reached.

## Consequences

- The deleted state is per-process, so the durable absence is what makes a deletion final across a restart, and a restarted host can create the same id again ([log-deletion decision](2026-10-19-session-log-deletion.md)).
- The gate covers the reads that resolve a session, the turn gate, `ensureSession`, and both listing surfaces. It is not universal: `session.models`, `session.selectModel`, `session.rename`, the queue edit and `session.cancel` controls, the goal verbs, the agent-preset switch, and `skill.list` resolve the leftover agent by identity instead of through the turn gate, so they still reach that Session — the log-writing ones are refused by the persistence tombstone, the reading ones answer as if the session existed — because deleting an identity does not evict its live Session.
- The deleted Session keeps its memory until the process exits, because nothing evicts it — stated for consumers in the [package README's known limitations](../../../../packages/host/apiproxy/README.md#known-limitations-and-deferred-work).
- The deleted-state read lives on the service definition, not in the gateway. `SessionPersistence.isDeleted(id)` is the tombstone set the coordinator already keeps for its write refusal, forwarded by each backend, so the gateway asks the one place that owns the fact instead of keeping a second deleted set of its own; like `delete` it is process-local, and a restart leaves the durable absence as the whole truth, which is why it answers `false` after one ([log-deletion decision](2026-10-19-session-log-deletion.md)).

## Testing

`packages/host/apiproxy/tests/api-proxy-delete.spec.ts` pins the refusal fences (running turn, origin-marked subagent, a live child a parent agent owns, no persistence mounted), the commit order as one ordered log of `persistence.delete` before `workspaceRegistry.forgetSession`, a durability failure rejecting through the impl and answering 500 through the carrier, the dropped row in `session.list` while the live neighbour stays, the transcript read (`historySourceFor`) and the `readSessionState` read each answering `session-not-found`, the turn gate refusing a turn for a tombstoned but still-attached session, `ensureSession` refusing to re-create the id, and the residual model directory of such a session observed as it stands. Registration of the method is pinned beside its siblings in `packages/host/apiproxy/tests/fetch-carrier.spec.ts`, `client-handler.spec.ts`, and `rpc-schemas.spec.ts`. The storage removal and its in-process deleted state are the persistence package's own contract ([log-deletion decision](2026-10-19-session-log-deletion.md)); the workspace-accounting half is `packages/workspace/workspace/tests/workspace.spec.ts` ([forget decision](2026-10-19-session-forget-removes-registry-accounting.md)); the carrier's address check and its archived-item filter are `packages/tenant/agent-http/tests/agent-http.spec.ts`.
