# Agent Note：新会话的第一条消息可能看不到用户层 MCP 工具，而「在步骤里等」修不了这件事

状态：已实现

[English](2026-11-17-first-message-tool-list-ordering.md) | 中文

## 问题

[启动时挂载](2026-11-16-mcp-mounting-at-startup.md) 把每一次 MCP 握手都挪出了请求路径：系统层在插件激活时连，用户自己的行在会话创建时连，任何一步都不等。上线后现场又看到一个很像回归、其实不是回归的现象：客户端把「建会话」和「发第一条消息」做成一口气调用（`session.create` 紧接 `session.prompt`，或者网页端「新建对话→立刻输入」），这条消息的工具清单里只有系统层，没有用户自己加的那批服务器。模型于是回答「工具没挂上」——正是两层挂载要防的那种失败。

挂载本身不慢：租户宿主上，全新会话的用户层在 `agent/created` 之后约 80ms 落定，在热宿主上连测三次都是这个数，宿主重启后也一样。

## 实测到的事实

`agent-loop` 的 `preStep` 先调 `systemPrompt.assemble()`（工具清单在这里定下来），再派发 `agent/pre-step` 瀑布。也就是说插件最早的钩子，已经在那一步的工具清单**之后**了。给挂载路径加日志后，其余部分也实证了：步骤开始时这次挂载早已完成（挂载表里两个名字都在，实验用的 1500ms 预算还剩 1.4s），而那一步发出的清单依旧是旧的。

由此有两条结论，它们一起决定了这条 note：

- 在 `agent/pre-step` 里等，改不动「它所在那一步」的工具清单——它能补上的是**下一步**，这正是「停几秒再问就有了」的原因，也是「再问一次就好了」的原因。
- 第一条消息能看见刚挂上的服务器，只有在「消息的步骤装配工具之前」挂载就完成，也就是在提问之前，而不是在提问之中。

「在 `agent/pre-step` 里有上限地等」这个版本实现过、部署到校验集群量过、然后删掉了：它让持有坏行的会话每次开头最多白等整个预算（默认 1500ms），而对它瞄准的那个场景一次也没改变结果。只会付出成本、不产生效果的机制，比一条写清楚的次序事实更糟。

## 决定

任何一步都不等 MCP 端点，插件也不提供让它等的开关。

- 用户层在 `agent/created` 时、以及每次登记表写入时挂载，所以人打字之前挂载就已经开始，也远早于他们的第一次敲键就落定。
- 晚连上的服务器中途加入对话，在下一次挂载对账时生效，不拖任何一步。
- 剩下的这场竞争写在包 README 和模块 JSDoc 里，不粉饰：在挂载的头一百毫秒里发出的第一条消息看不到用户层，这个会话的第二条消息就有。

## 考虑过的其他做法

**在 `agent/pre-step` 里等（`firstMessageWaitMs`，默认 1500ms）。** 做过、上过集群、健康端点和死端点都量过，然后删掉：它改不动所在那一步的清单，买不到任何东西，却让持有坏行的会话每次开头都被拖住。

**把工具装配挪到 `agent/pre-step` 之后。** 那是 `agent-loop` 的改动而不是插件的，而且会让工具清单取决于监听者做了什么——包括发起网络请求，正是上一条 note 拆掉的那种耦合。只有当将来的调用方确实无法容忍这场竞争时，它才是正确的修法。

**从 `agent/inbox/inserted` 按住消息直到挂载落定。** 那是通知类事件，派发不 await，挡不住回合。改成暂停 agent 则是跟循环自己的状态机对着干。

**在 `session.prompt` 这个 RPC 里等。** 它是装配之前唯一的切口，真做是能成的；但它需要一条跨包的就绪服务（`apiproxy` 去问 MCP 插件某个会话挂好没有），而这场竞争已经被人的打字延迟覆盖住了——80ms 的挂载对几百毫秒的敲键。等出现真正比这更快地把 create 和 prompt 串起来的调用方再说。

**用户行只在每个用户一个作用域里挂一次。** 上一条 note 给的理由仍然成立：用户身份是 `AsyncLocalStorage` 的 ambient，不是 Cordis 作用域。

## 后果

**换到的。** 没有任何 MCP 端点能拖住任一步，坏行的代价是持有它的那个会话里一次后台连接尝试加一行告警。

**接受的。** 全新会话如果第一条消息落在挂载的头一百毫秒里，这条消息没有用户层工具；这个会话的第二条消息有。重启宿主不会放大这个窗口。

**那次尝试留下的。** 两个事实留在测试和夹具里：作用域事件按作用域键派发，所以 `agent/pre-step` 的监听必须登记在会话自己的作用域上（`agent.ctx`，其键就是 agent），不能挂在宿主上下文；因此测试夹具用 `createScope(ctx, agent)` 给 agent 建作用域。

## 测试

`packages/tenant/mcp-external/tests/mcp-external.spec.ts` 钉住仍然成立的行为：步骤边界既不会被永不回应的连接器堵住，也不会自己发起挂载；会话自己的行挂进该会话的作用域；登记表写入会给活着的会话重新挂载。为那个被删掉的「有上限地等」写的两个测试随机制一起删了。
