# Agent Note: Tenant tool presentation and concurrency are configuration

Status: implemented

English | [中文](2026-10-08-tenant-tool-presentation-and-concurrency.zh.md)

## Problem

The business side reaches its data-mining backends over MCP — roughly 180 tools, and a case session is expected to query many of them in one turn. The tenant stack assembled `@deepseek-ai/dsh-tools` with `mode: 'both'` written into `packages/tenant/tenant-app/src/spine.ts`, so every tenant service sent each tool's native schema in the system prompt **and** the generated `run_code` SDK surface, and a deployment that wanted either form alone had no value to say so: the presentation was a property of the assembly rather than of the deployment.

The prompt cost of that native listing had no deployment-side answer either. The tenant stack mounts `tools-tier` (the case, user-global, and system tool directories) and `tools-manifest` (which turns the `*.yaml` manifests in those directories into ranked tools), but both only ever ADD a tool or shadow a same-named one. Neither can remove anything, and nothing in the tenant stack called the registry's per-scope restriction API, so all 180 MCP tools stayed visible to every case and the schema listing grew with the deployment's tool count rather than with the case's needs.

The execution side had the opposite defect. The tenant reader rejects field names it does not already know, so several `Config` fields of the two container providers could not be set from tenant configuration at all — writing one failed the load with "unknown field". `maxOutputBytes` is the clearest case: `container-docker` and `container-k8s` both default it to 64 MiB and both document it as a bound that must stay above the host's own result budgets ([sandbox output bound](2026-10-08-sandbox-output-bound.md)), yet a tenant needing another value silently got the default. `dsh-tools`'s `maxParallelSubCalls` defaults to 10, which spreads a fan-out over 180 tools across eighteen waves, and every MCP server row carried no concurrency value at all.

## Decision

Tool presentation, the per-case visible-tool list, the `run_code` overlap window, every container-provider field, and a per-server MCP call cap are configuration or case data in the tenant stack, resolved where its other defaults already resolve.

### The tenant default presentation is `both`

`tools.mode` defaults to `both` and `tools.maxParallelSubCalls` to 32; the `tools` spine row derives both, so the plugin's own defaults never apply inside a tenant service. `both` keeps the direct form available: a session that reads one file or asks one question calls the tool it means, while a fan-out over a hundred tables can still be written as one `run_code` program. `native` and `code` are each one configuration value away, and every sub-call of a program re-enters the complete tool pipeline, so permission, timeout, and result bounds do not depend on the presentation.

`code` is not free of wiring, which is another reason not to make it the default: prompt assembly fails unless a `ctx.codeRuntime` with a registered SDK renderer is mounted, and the tenant spine supplies one through `code-runtime-container` (`language = 'typescript'`). A deployment that swaps that row for one with an unregistered language fails at the first prompt, not at load — acceptable for a deployment that asked for `code`, needless exposure for one that did not.

### A case's visible tools are declared in its own tool tier directory

The lever for prompt cost is the visible set, not the presentation. `ctx.tools.restrict()` already expresses it per scope, and the tier directories already exist, so what was missing was a consumer: `@deepseek-ai/dsh-tools-restriction` reads each tier directory's reserved `restriction.yaml` (`allow` and/or `deny`, each a list of global tool names and trailing-`*` prefixes) and applies it to the created agent's scope in the `agent/created` window.

A case tier is written as `allow` with prefixes. The two directions fail in opposite ways when a mining server later ships another tool: `allow` admits only what it names, so the new tool stays out until someone adds it, while `deny` masks only what it names, so the new tool arrives visible to every case. A case document therefore states the groups it uses — `mcp__icac-bill__*` for a group whose tools this case type keeps as a whole — and a `deny` document is reserved for the opposite job, masking operations an operator must keep unreachable, re-checked whenever the far side adds tools. The prefix form is what keeps `allow` usable at this tool count: without it a case that keeps a whole group would have to list that group's thirty-odd names and re-list them on every server change.

A prefix is a literal string followed by `*` and nothing else. `mcp__*__search`, `?`, character classes, and regular expressions are rejected at load, naming the file and the entry, because the syntax has to be reviewed as a name rather than as a pattern language. Exact names and patterns mix in one document, and what reaches `restrict()` is always exact names: the pattern expands in the same `agent/created` window against the global names the registry holds at that moment (its own `schemas()` view, minus the reserved `run_code` transport, which is not a restrictable name), so the restriction mechanism is unchanged and the expansion is per creation rather than per document. A pattern matching no registered global name fails that creation naming the file and the pattern — under an `allow` a mistyped prefix would otherwise leave every tool visible — and one pattern expanding past 512 names is refused for the same reason. The expansion result is not written to the session log: it is the input to a filter over the tool list rather than an input of its own to a model request, and what the model sees is already reconstructable from the schemas the registry serves.

The plugin takes no tier roots. It resolves them from `ctx.toolTiers`, the provider `@deepseek-ai/dsh-tools-tier` builds from its own `usersRoot` and `systemToolsDir` config and the ambient tenant's `workspaceRoot`, so the manifest loader and the restriction loader cannot disagree about which directory a tier owns. It is mounted after `tools-tier` and `tools-manifest` in the tenant spine, which also lets it parse the system tier's document at load, where the provider resolves that tier without an ambient tenant or user; a case or user-global document needs an ambient (tenant, user) and is parsed when an agent is created under it. Every document is parsed again at that point, so a malformed system document also fails the creation of each agent under it, whatever the composition does with a row's own load error.

One visible map feeds the assembled schemas, the generated SDK surface, and execution resolution, so the declaration shrinks both presentations at once and a masked name is absent from the prompt **and** rejected by the executor as an unknown tool. The declaration filters what a scope INHERITS — the global layer and every ancestor scope, which is every plugin tool and every MCP server's tools — and never the tools a tier manifest registers into the agent's own scope, so a case's `allow` list does not need to name its own manifests and cannot hide one. Names are checked against the registry when the agent is created, and a rejection is rethrown with the document that caused it, so a case naming a tool that is not registered yet — an MCP server still connecting, or a typo — fails creation naming that file instead of silently keeping the whole listing.

### Three tier documents intersect; a nearer tier cannot re-admit a masked name

The documents compose by intersection, which is the registry's own rule for more than one restriction on a scope chain, so a deployment reasons about the three tiers with the rule it already knows from `ctx.tools.restrict()`. The ranks of `tools-tier` survive only as the order the documents are applied in, which decides which file a diagnostic names.

Intersection is the deliberate choice over letting the nearest tier that ships a document decide alone. The case directory is tenant-writable and the system directory is operator-owned, so an override would let a case re-admit a tool the operator removed; intersection keeps that decision with the operator while a case still narrows further. The alternative would also have to merge the three documents into one filter before calling `restrict()`, which makes the composition rule a property of this plugin rather than of the mechanism it applies.

`run_code` is the reserved presentation transport rather than a capability: a document cannot name it and it stays visible under the `code` and `both` presentations.

### 32 is the default overlap cap

`maxParallelSubCalls` bounds how many of a `run_code` program's sub-calls overlap; only calls the tool itself classifies as concurrency-safe overlap at all, and the cap does not change the prompt. 32 was chosen against the workload rather than the plugin's own 10: a data-mining fan-out is a batch spread over shards or tables, so 32 drains 180 tools in six waves while the in-flight set stays at tens of concurrent HTTP requests, result buffers, and re-entered pipeline executions.

### The sandbox section carries both providers' Config fields

`maxOutputBytes`, `cliTimeoutMs`, `readyTimeoutMs`, and `readyPollMs` join the shared sandbox fields (`container-docker` and `container-k8s` both define them), and `command` and `env` join the Kubernetes-only set. Each is forwarded under the provider's own field name, except the three the tenant section already renames: `image` → `toolExecImage`, `imagePath` → `toolExecImagePath`, `toolTimeoutMs` → `transportTimeoutMs`. The reader validates each one, so a wrong type or a misspelled name fails the load with the field path.

### A mounted block that fails to load fails the boot, naming the block

`createTenantApp` keeps every mounted block's fiber — the static mounts and every enabled spine row and MCP row — and drains them with `Fiber.await()` once everything is mounted, wrapping the failure as `组合行 <id>（<module>）启动失败` with the original error as `cause`. A block whose `inject` is already satisfied when it mounts needs none of this: `ctx.plugin()` awaits the load and rethrows. A block whose injected service is provided by a LATER row is the case this exists for: its apply is deferred to the epoch that service appears in, `ctx.plugin()` has long returned by then, and Cordis records the failure on the fiber and logs it without failing anything. The drain has to run after all mounts for the same reason — at that point every injection is available and a deferred apply has either finished or is in flight, so `await()` sees it. A block whose injection is never satisfied is PENDING rather than failed, and stays the business of `assertMountedServices`, which names the missing service.

The alternative — leaving it to the log line Cordis already writes — loses exactly the failures that must not be silent: a masked-off `tools-restriction` row leaves all 160 mining tools visible to the model, and a failed auth row leaves the API open. A boot that cannot serve what its configuration declares should not report success, so it also disposes what it had mounted: the caller gets a rejection rather than a half-built host holding a listening port and a database pool, and a failure to dispose is logged instead of replacing the error that names the block.

### A per-server MCP row is forwarded, not defaulted; the deployment states it per row

The section mirrors one MCP transport shape, not two. `mcpServers[]` accepts the client's Streamable HTTP branch (`serverName`, `transport: streamable-http`, `url`, `headers`, `toolConcurrency`); the stdio branch is not expressible from tenant configuration, because a child-process server is a host-composition decision rather than a per-deployment URL, and no deployment mounts one. A stdio row therefore fails at load as an unknown field (`command`) instead of being quietly ignored.

The section forwards what the client's discriminated `Config` actually declares for its Streamable HTTP branch — `serverName`, `transport: streamable-http`, `url`, `headers`, `toolCallTimeoutMs`, `failOnStartupError`, and all twelve `toolConcurrency` keys (`policy`, `maxConcurrentCalls`, `exclusiveTools`, `retryTools`, `mode`, `decreaseFactor`, `recoveryStep`, `recoveryQuietMs`, `countTimeouts`, `retryAttempts`, `retryBaseDelayMs`, `retryJitterRatio`) — each under the client's own name and each validated here for type and domain (a policy or a mode from its own values, a positive or non-negative integer, a ratio in `0..1`, a boolean, a non-empty name array, a string map), so a misspelled sub-field fails the load rather than reaching the client as an ignored key. The reader does not restate the client's finer bounds — `decreaseFactor` strictly inside `0..1`, `retryAttempts` at most 5, the two timer ceilings — because the plugin's own resolve step re-judges every value and fails that row's mount naming the row: a copy here would be a second boundary drifting from the first, and an out-of-range value is loud either way. `headers` is the authentication path: the client attaches it as `requestInit.headers` on every MCP request. The reader accepts only the transports the client has, which is why `sse` is gone from the accepted values: it was never a client transport, and accepting it deferred the failure to that row's mount. The client's `reconnect` section is the one field deliberately left un-forwarded: no deployment here needs it, and an un-forwarded field takes the client's own default rather than a second default written here.

`failOnStartupError: true` is stated on every row of both deployment examples, because the client's `false` is the one default that hides a misconfiguration. At `false` a wrong URL, a closed port, or a server that is not up yet leaves a log line and a row that mounts with no tools — which reads exactly like a server that exposes none — while at `true` the same failure rejects that row's mount and so fails the boot, naming the row as `组合行 mcp-<index>-<serverName>`. It also decides what a case document does about a group that is missing: a prefix matching none of the registry's names fails agent creation, so a deployment that silently lost a server would fail at its first case rather than at boot.

`headers` is also the reason the Kubernetes example mounts the whole tenant configuration from a Secret rather than a ConfigMap. A header value can only come from the configuration file — the environment-override list in `applyEnvOverrides` is fixed and `mcpServers` is not in it, so a placeholder in the file plus an environment variable cannot substitute for the token — and a ConfigMap is readable by any subject holding `get configmap`. The file is mounted read-only with mode `0400` from a Secret named beside the workload. That needs no RBAC change: the kubelet fetches a volume-mounted Secret, so the pod's ServiceAccount never reads it, and the namespace Role keeps granting no `secrets` permission at all. The tradeoff is that the manifest in the repository carries placeholders while the applied one must not: applying the repository copy over a Secret that holds real tokens would replace them with the placeholders, so the documented procedure applies a local copy that has been filled in.

There is one ceiling and one allocation, and the difference decides what a shared backend sees. `tools.maxParallelSubCalls` is the ceiling and is per run_code program, so concurrent sessions each hold their own; `mcpServers[].toolConcurrency.maxConcurrentCalls` is the allocation and is one host-wide gate per server, shared by every session and every program. Under the client's default `mode: adaptive` that number is also the starting cap and its upper bound: the cap the gate enforces is learned per plugin instance from that server's own refusals and is not persisted, so a row states a starting point rather than a measured constant, and a deployment that has measured one sets `mode: fixed` to hold it. A deployment whose entries share one backend (`host:port` constant, only the path varies) therefore reads its concurrency as the sum of the per-server caps, sets the ceiling to the total that backend tolerates, and divides that total among the groups.

Those defaults are nevertheless wrong for this deployment's servers, which is why the tenant examples state the row explicitly. Every MCP server here is third-party and unmodifiable, so it declares no `readOnlyHint` and no `idempotentHint`, and the client's `annotations` policy therefore has no declared intent to read: a tool that looks read-only to nobody in particular is simply admitted. The deployment answers that with `policy: parallel`, which puts the concurrency judgement and its responsibility on us, and per-group caps that start at serial for a group nobody has measured. Throughput then comes from ACROSS servers rather than inside one: distinct services share no state, so N serial servers still give N calls in flight, and that is the risk-free part of the fan-out. Raising a group's number is a separate act, taken after that group is verified to take it — and from that point on its submission order carries no guarantee, so the tools that write data are named in the client's own `exclusiveTools` list for that server, which keeps them from overlapping any other call. Repetition is a separate answer on the client side, where a refused call is re-sent only for a tool that declares `readOnlyHint` or that the deployment adds to `retryTools`: naming a write in `exclusiveTools` orders it, and does not by itself prevent a second attempt.

## Alternatives considered

**Default the whole deployment to `code`.** It would reclaim the native listing outright, and it was the first decision taken. It is rejected because the collapse taxes work it does not help: with `code` as the tenant default, a session that reads one file or asks one question must write a program before it can call a tool at all, and the model pays that on every small task. The prompt bloat is a property of the tool COUNT, not of the presentation, and `both` plus a per-case visible-tool list removes it where it appears — the case's list shrinks the native listing and the SDK declaration together, and the direct form stays usable for the sessions that never needed it gone. A case that genuinely wants the collapse sets `tools.mode: code`.

**Hardcode `mode` in the assembly.** A literal `mode` is the defect the problem describes: a deployment with a few tools and a model that calls them well wants a different form, and a repo convention already forbids a deployment-varying choice living in the assembly. Only the value changed between the two attempts at this note — hardcoding was never defensible.

**Keep only one presentation deployed and accept its cost.** Either form shipped alone gives up something a tenant service needs: `native` alone pays the full listing on every request, `code` alone forces programs for trivial tasks. The two are one field apart, so the composition states the form that serves both and the per-case list handles the count.

**Let `dsh-tools` keep its own defaults (native, 10).** Then the tenant stack states nothing about presentation and each deployment must override a row config to reach the intended behavior. The tenant stack is the composition that knows this workload, so it owns the defaults; the plugin's defaults remain for compositions that state nothing.

**Hide tools through the tier manifests.** A manifest registers a tool into the agent's own scope and shadows a same-named one, so a case could replace a global tool's definition or add its own — but never remove one, and the 180 MCP tools would stay visible whatever the case shipped. Reusing that mechanism for the visible set is not possible; the registry's restriction API is the one that removes a name from view, and the change is a consumer for it rather than a second mechanism beside it.

**Let the manifest loader read the restriction document too.** The loader already walks those directories in the same `agent/created` window, so one plugin could do both. The two documents are different concerns with different composition rules: a manifest is ranked and additive, a restriction intersects and only narrows, and one package for both would tie the restriction to the manifest loader's release and config. The loader keeps exactly one coupling to the other document — it skips those reserved basenames, because a restriction declares no tool and parsing it as a manifest would fail every tier that restricts tools — and the restriction reader owns the format, the composition, and the diagnostics.

**Let the nearest tier that ships a document override the farther ones.** See the decision above: it would hand a tenant-writable case directory the power to re-admit what the operator's system tier masked, and it would put the composition rule in this plugin instead of in the mechanism it applies.

**Let a case tier `deny` what it does not want instead.** It would be the smaller document, and it is rejected because the two directions degrade in opposite ways as a third-party server evolves. `deny` names what it masks and therefore lets every tool the server adds next arrive visible, which is the failure a case tier exists to prevent; `allow` names what it admits and therefore keeps a new tool out until someone decides it belongs. Making the case tiers `allow` also keeps the operator's `deny` document meaningful: an operator masks operations that no case should reach, and a case that must list its groups cannot re-admit what that document removed.

**Let a document express a general glob or a regular expression.** A `mcp__*__search` form, a character class, or a regex would cover more shapes in one entry, and it is rejected on review grounds: a document that reads as a name can be checked against a server's tool list by a human, while a pattern language moves that check into whoever last edited the document. The trailing `*` covers the one shape the tool count demands — a whole server's group — and every other entry is the exact name that same review compares against `tools/list`.

**Expand the prefixes once for the process rather than per agent creation.** The registry holds the names when the plugin loads, and caching the expansion would take the work off the `agent/created` window. It is rejected because the expansion would then answer for servers that connected later: an MCP row that finishes its tool synchronization after the restriction plugin loads would be missing from every document that names its group, and the failure mode is a silently narrower `allow` rather than a diagnostic. Expanding per creation reads the registry's current names, which is the only set the registry would accept those names against.

**Put the visible-tool list in tenant configuration or in the case record.** A case is created at runtime and its tool needs change with its data, so a deployment-level list cannot express it, and a database column would put file-shaped data in the registry. The tier directories already hold the case's declarative tool surface, and the case's directory is where its operator writes.

**Open the sandbox section to any field name.** Accepting unknown keys would make a misspelled provider field silently ineffective — the failure `rejectUnknown` exists to prevent — and would push the real checking to wherever the provider happens to notice. The section instead enumerates each provider's `Config`, one field per provider field.

**Give `mcpServers[].toolConcurrency` a default.** See the decision above: the tenant side cannot know which third-party server tolerates overlap, so a default would either shadow the MCP client's or disagree with it, while each deployment states the one value it has actually verified per row.

**Ask the MCP servers to declare their tool annotations.** It would let the client's own `annotations` policy make the call without any tenant configuration, but these are third-party servers we cannot modify: a server that declares no `readOnlyHint` and no `idempotentHint` is not a server we can wait for, and treating its silence as "read-only" is the assumption that fails. The deployment states the policy instead.

**Accept a map of MCP servers keyed by server name, with an `enabled` flag.** That is the shape one deployment already has, and the tenant section keeps the list instead: the map key would become a second way to state a `serverName` that the tool namespace, the duplicate-name check, and every diagnostic already read, and `enabled: false` expresses nothing the list does not, since an unlisted server is not mounted. The conversion is mechanical, and the tenant examples carry the converted rows.

**Let a per-case or per-agent presentation differ in the same change.** The mechanism exists — `@deepseek-ai/dsh-agent-tool-presentation` lets a preset declare `ctx.tools.presentAs(mode)` for its scope, so code-mode and native agents coexist in one process. It is not mounted in the tenant spine, and no tenant configuration names a preset, so per-case differentiation is a separate change rather than a value in this one. Per-case visible tools are the part of that gap this change closes.

## Consequences

Under the shipped default the model sees both forms. A case with hundreds of tools must ship a restriction document or pay the whole native listing on every request, and the document is read when an agent is created, so editing it affects the agents created afterwards rather than the running ones.

The visible set is the case's, not the tool's: a case cannot hide a tool its own tier manifests register, because a restriction only filters what a scope inherits, and two cases sharing a tier directory cannot disagree about a name. That exemption also means listener order between the manifest loader and the restriction reader does not decide anything — a manifest tool is registered into the agent's own scope and never enters the restrictable names, so a document naming one is rejected as an unknown global tool whenever either listener ran first, which the tests pin. It is also why a prefix cannot stand in for a manifest tool: it expands against global names only. A case that names a tool no registry has yet — an MCP server still connecting at boot — cannot create agents at all until that name exists, which is a loud failure chosen over a silent return to the full listing.

A prefix leaves the boundary of the document, so its consequences are not the entry's alone. It is resolved when an agent is created, which means an agent created after a new MCP server connected sees the group that server added while one created earlier does not, and a tool a server stopped exposing leaves every pattern silently narrower — where an exact name that disappears fails the next creation under that document. Whoever keeps a case document therefore keeps it with the group it names and re-checks it when that server changes its tool list. A prefix that matches nothing is the loud end of the same property: it cannot pass as an `allow` that admits little, and the deployment learns about the missing server at its first case at the latest.

Each tenant service therefore reads two reserved documents per tier directory, and the restriction reader is the one that must exist for a case to be limited at all: mounting `tools-tier` and `tools-manifest` without it leaves every tool visible. Because a block that never loads now fails the boot, that combination — and every other block the configuration declares — either comes up or stops the service from coming up; a deployment that has been running with a row silently absent will refuse to start once this is in place, and the fix is in that row's configuration or module.

The `sandbox` section mirrors two providers' `Config` definitions. A provider that renames, removes, or adds a field needs the tenant reader and the forwarding table updated in the same change, or the value stops being reachable from tenant configuration.

The tenant stack keeps exactly one default per knob it owns and none for a knob a mounted plugin owns, so the per-server row means what the client's README says it means. A deployment following the tenant examples states the policy, the allocation, and the write tools per row: caps are divided among the groups whose entries share a backend, and a group nobody has measured starts serial. A deployment that leaves a row silent still gets the client's own defaults — `annotations`, then 10, then no excluded tool — which is a concurrency decision taken from annotations the server never wrote.

### Verification

`packages/tenant/tenant-app/tests/app.spec.ts` pins the derived `tools` row configuration against the real composition: an unconfigured tenant mounts `ToolRuntime` with `mode: 'both'` and `maxParallelSubCalls: 32`; configured values reach the same plugin; `tools.mode` rejects anything outside the three presentations and `tools.maxParallelSubCalls` rejects `0` and `1.5`; one server row's `headers`, `toolCallTimeoutMs`, and all twelve `toolConcurrency` keys reach the `mcp-client` instance that row mounts, `exclusiveTools` and `retryTools` included and independent, while another row's silence leaves the client's own defaults in place (`annotations`, 10, two empty name lists, `adaptive`, 0.5, 1, 2000, true, 0, 200, 0.2, the client's timeout, `failOnStartupError: false`); a row whose `transport` is not one the client has, whose `headers` value is not a string, whose `exclusiveTools` entry is empty, or which carries a stdio field, fails the config load with a diagnostic naming that path. The same file pins each new key's rejection: an unknown `retryTool` singular, `mode: fast`, `decreaseFactor: 2`, `retryAttempts: -1`, `recoveryQuietMs: 1.5`, and a non-boolean `countTimeouts` all fail at load with the key path in the message.

The same file pins what `failOnStartupError` decides, through a real boot against an unreachable server: written `true`, `createTenantApp` rejects with `组合行 mcp-0-mining（@deepseek-ai/dsh-mcp-client）启动失败` and the client's own message; left out, the same row mounts and reports the client's default. That is the difference between a wrong URL failing the boot and a wrong URL looking like a server that has no tools.

The same file pins the boot's failure behavior on the real composition, in the one place where the deferred path is live: the row providing `tools` sits after `tools-restriction`, so that row's apply runs only once `tools` exists. A restriction row given an unknown config key, and a system tier holding a malformed `restriction.yaml`, each make `createTenantApp` reject with `组合行 tools-restriction（@deepseek-ai/dsh-tools-restriction）（注入满足后才执行）启动失败` and the plugin's own message; disabling the drain makes those two assertions fail. A normal boot of the same rows resolves and mounts them.

Both deployment examples were validated by uncommenting the `mcpServers` block exactly as a deployment would and loading it through the real reader: twelve rows, one shared host, caps summing to the documented ceiling, the `headers` map, `failOnStartupError: true`, and the longer call timeout on the importing group. The Kubernetes example was read the same way through its own structure: three documents, the tenant configuration inside the `Secret`'s `stringData`, that configuration accepted by the reader as mounted and again with its `mcpServers` block uncommented, the volume coming from that Secret with mode `0400`, and no `configMap` volume left anywhere in the workload.

`packages/tenant/tenant-app/tests/app.spec.ts` boots the real composition with the `tools-tier` and `tools-restriction` rows enabled and pins that the restriction row mounts with no config while the provider it reads reports the system tier directory of the boot.

`packages/tenant/tools-restriction/tests/tools-restriction.spec.ts` pins the restriction reader against the real registry, provider, and ambient tenant/user scope: a case document that admits ten of twelve registered globals leaves that agent's `ctx.tools.schemas(agent)` at exactly those ten, calls the other two into `unknown tool` from the executor, and leaves the global view holding all twelve; three documents compose to the intersection, so a case and a user-global `allow` cannot re-admit the name the system tier denied; a `both`-mode prompt loses the masked name from its native tool list and from the generated SDK section together; a document naming an unregistered tool fails agent creation with the registry's message and the document path attached; a malformed system document and any config key fail at load; a tier manifest tool survives beside a masked global while a document naming that manifest tool is rejected; and disposing the plugin's fiber stops the restriction.

That file also pins the pattern syntax and the expansion, both as a pure function and through the registry. `parseRestriction` classifies a trailing `*` as a pattern, keeps exact names beside it in one document, and rejects `mcp__*__search`, a bare `*`, `?`, a character class, an alternation, and a backslash escape with the file and the entry in the message; `expandRestriction` turns a prefix into the names it matches, fails a prefix matching nothing with the file, the pattern, and the names the registry does hold, and refuses one entry expanding past the bound while accepting exactly the bound. Through a booted registry, a case `allow: [mcp__icac-bill__*, mcp__icac-case__search]` leaves that agent seeing the two bill tools and the one named case tool, calls the rest into `unknown tool`, and fails the creation of an agent whose pattern matches nothing; a manifest tool sharing a prefix stays visible beside the group the pattern admits, and an illegal pattern in the system document fails at load.

`packages/tenant/tools-manifest/tests/tools-manifest.spec.ts` pins the manifest loader's side of the reserved-name convention: a tier directory shipping both a manifest and a `restriction.yaml` registers the manifest and ignores the restriction document rather than failing on it.

Not covered by a repo test, and verified on a cluster by the owner: that a `both`-mode prompt assembles against the mounted container runtime, that a mining fan-out of 180 sub-calls drains under the configured cap instead of the plugin's 10, and that a per-server cap actually throttles one MCP server's calls. No test here runs against a real MCP server — the repo's MCP client tests own that surface.
