# Agent Note: 沙箱自己决定自己的死期

Status: implemented

[English](2026-10-08-container-owned-sandbox-lifetime.md) | 中文

## 问题

沙箱 Pod 没有控制器，所以创建它的东西也决定它什么时候结束。在这之前是宿主决定的：`container-docker` 与 `container-k8s` 各自在宿主进程里为每个 (租户, 用户) 挂一个空闲计时器，到点就删掉容器或 Pod。可宿主只看得见自己缓存的那个句柄，而每一个请求都要到达容器——两个宿主副本并存时，空闲的那个会删掉忙碌的那个正在用的沙箱：忙碌的请求失败，它的租户白付一次冷启动。

同一批计时器还留下第二类故障。`ensureSandbox` 会收养 `Running`/`Pending` 的 Pod，于是一个永远起不来的 Pod（例如 kubelet 完不成的 `subPath` 挂载）每次重试都被重新收养、永远不被删：宿主侧回收只对「它自己缓存过的句柄」生效，而失败的启动什么都不缓存。那个 (租户, 用户) 就此永久卡死，而裸 Pod 没有别的东西会来收它。

## 决策

沙箱自己决定自己的死期。`idleTimeoutMs` 作为 `DSH_TOOL_EXEC_IDLE_MS` 注入沙箱（k8s 走 Pod `env`，docker 走 `-e`），容器内的 tool-exec 服务在「距上一次请求超过预算、且当前没有请求在执行」时退出。「某个主体是否正在被使用」只有容器能观测到，所以这个判定不需要注册表、不需要数据库表、也不需要副本之间协商：宿主保持无状态，任何副本都可以服务任何主体。

在途请求不算空闲，因此判定同时看正在执行的请求：比预算更长的命令不会被自己打断，计时也在命令结束之后才重新开始，而不是从命令开始算。

宿主只保留自己的进程能知道的东西：句柄缓存 `sandboxCacheTtlMs`（`sandboxCacheTtlMs: 0` 表示从不信任句柄）。沙箱在句柄还活着时自行退出，代价是一次失败的 exec，由重试路径重建。此外每个 provider 会删掉自己用不了的沙箱：在 `startTimeoutMs` 里没就绪、或在 `readyTimeoutMs` 里答不上话的沙箱，在报出失败之前就被删掉，于是下一次使用是干净启动，而不是再次收养同一个坏 Pod。启动时每个 provider 按托管标签加阶段选择器收走自己那批终态沙箱（`Succeeded`、`Failed`），绝不碰 `Running`/`Pending`——那可能是另一个副本正在用的沙箱。

## 考虑过的其他方案

- **宿主按时器删除**（本次改动之前）：否决——宿主看到的是自己的缓存，不是主体的使用情况，于是第二个副本会删掉正在使用的沙箱。
- **把最后使用时间记进数据库再扫描**：否决——一个会与沙箱本身漂移的派生视图，每次工具调用热路径上多一次写入，而且扫描依然分不清「被遗弃但仍在运行的沙箱」和「正在使用的沙箱」。
- **把每个沙箱做成带 `ttlSecondsAfterFinished` 的 Job**：暂缓——那样集群能完全接管回收，但沙箱必须保持稳定名字才能跨副本收养，而 Job 生成的 Pod 名字不稳定；今天的标签收尸在没有控制器的情况下收掉同一批残骸。

## 后果

- 副本永远不会删掉另一个副本正在用的沙箱，因此多个宿主可以共同服务一个租户，不需要 leader、租约或共享状态。管理面之所以能保持无状态，靠的就是这一点。
- `idleTimeoutMs` 不再在宿主进程里回收任何东西：沙箱自己退出，所以下次使用要冷启动。预算的含义仍是「沙箱最多停多久」，但执行它的地方跟着沙箱走了。
- 终态沙箱会留在集群里，直到下一次启动收尸；一个仍在运行、而其 (租户, 用户) 之后再没被用到的沙箱会留到运维按标签删除。启动时删运行中的 Pod 会把本改动刚去掉的跨副本误删又请回来。
- 镜像必须读 `DSH_TOOL_EXEC_IDLE_MS`。不读它的旧镜像只是让空闲沙箱继续运行，也就是改动之前的行为，而不是坏掉的沙箱；容器自行退出会留下 `Succeeded` 的 Pod，因为 `restartPolicy` 是 `Never`。
- 两个 provider 里按作用域的宿主空闲计时器都已删除；`container-docker` 的 teardown 不再遍历它们。

### 验证

- `packages/tenant/container-docker/tests/tool-exec.spec.ts` 用真实监听的服务、注入的退出通道与时钟覆盖 watchdog：预算到点且无在途请求时退出；没配预算则永不退出；250ms 的命令在 30ms 预算下不被中断、命令结束后才退出；有请求进来时把期限往后推。该文件 10 个用例通过 7 个；另外 3 个 POST `sh -c` 的用例在 Windows 开发机上失败，因为被 spawn 的进程 `PATH` 里没有 `sh`（`spawn sh -> ENOENT`），与本改动无关。
- `packages/tenant/container-k8s/tests/runtime.spec.ts` 断言预算进入 Pod 环境、未配置时不注入任何变量；起不来的 Pod 会被删掉（集群里唯一的 Pod 消失，下一次 exec 建出第二个）；启动时按托管标签加阶段选择器先收 `Succeeded` 再收 `Failed`。23/23 通过。
- `packages/tenant/container-docker/tests/docker.spec.ts` 断言预算以环境变量进入容器，且启动时收走已退出的托管容器。33/33 通过。
- `pnpm exec tsc -b tsconfig.host.json` 无输出。
- 部署机实测（`192.168.138.130`，命名空间 `dsh`，把 `idleTimeoutMs` 临时降到 `60000`）：真实的一轮 agent 对话建出的沙箱 Pod 环境里带着 `DSH_TOOL_EXEC_IDLE_MS: "60000"`，那条工具调用也真的跑完（`tool/call` → `tool/result` 0.03s）。最后一次请求之后 100 秒，该 Pod 变成 `Succeeded`、容器退出码 `0`（`Completed`）——这是 watchdog 那条路径，被信号杀掉的 Node 进程会以 `143` 退出。此时重启宿主，托管 Pod 报「一个都没有」：启动收尸删掉了那个终态 Pod，而在这台集群上除了它没有别的东西会去删。随后把预算还原为 `900000` 并重启宿主。
