# Agent Note: 挂载式插件根目录

Status: implemented

[English](2026-09-23-mounted-plugin-roots.md) | 中文

## 问题

一个部署想多加一个工具，就得重新出镜像：每个插件都是镜像安装的 npm 包，而 cordis 行只能用裸标识符来指名它。案件平台的报告同步工具是部署产物，不是产品面 —— 它们只面向某一个后端的一个地址，而需要它们的运维没法重建 harness。

Loader 其实已经能导入绝对路径（`packages/boot/app-boot/src/index.ts` 用 `pathToFileURL` 转换绝对路径的行名），`scripts/verify-cordis-config.ts` 也把路径标识符豁免在 resolver manifest 依赖门之外。缺的是：不必每行都写一长串绝对路径就能指名挂载插件，以及部署路径写错时在加载期报错。

## 决策

`@deepseek-ai/dsh-plugin-roots` 依据经校验的 `Config.roots` 列表发布一个 `pluginRoots` 服务，根 Include 条目通过它解析 `local:` 行。

`local:` 前缀就是区分两类标识符的东西。裸名永远是已安装包；`local:` 名永远是挂载目录。两者之间不需要判断优先级，挂载插件也可以直接占用已安装包的名字而不产生歧义 —— 同一个部署可以挂一个改过的 `@deepseek-ai/dsh-tools` 目录，并用 `local:@deepseek-ai/dsh-tools` 访问它。

根目录默认是空列表，且每个配置的根目录在该行挂载时就被校验。加载挂载目录等于运行它的代码，所以这个信任决定必须由运维明确写下来，每个部署写一次；这里没有目录扫描、没有按约定的自动发现、也不会退回按包名找。

如果 `local:` 行之上没有挂载根目录服务，它会带着「请加那一行」的提示失败，而不是对着空无一物去解析。

## 考虑过的替代方案

**把同步工具做成发布包。** 被运维自己的约束否掉了：那样每次改工具都要重建镜像，而且地址只能进镜像发布的包，而不是部署方编辑的文件。

**裸名先按根目录解析，再走 npm 解析。** 否掉：优先级在行里看不出来，同一个名字在不同部署里含义不同。前缀让这个选择成为名字的一部分。

**自动扫描一个约定目录。** 否掉：隐式扫描意味着只要把文件放进去，不可信目录就变成可执行的；一个丢进来的文件会在没有任何配置改动可审的情况下成为运行中的代码。

**解析不到就跳过，其余照常启动。** 否掉：静默缺失的工具和正常工具无法区分，直到模型调用它为止 —— 而这正是运维查不出来的那种故障。

**把根目录列表放在根 Include 条目自己的 config 上。** 否掉：根 Include 是在任何 patch 层生效之前创建的 app 胶水，任何挂载出来的配置文件都够不着它 —— 运维自己的 `cordis.patch.yml` 正是被它所配置的那棵树应用的。

## 后果

导入了 harness 包的挂载插件，需要从它自己的目录能解析到那些包。位于 `$DSH_HOME/profiles/<name>/` 下的根目录可以从启动器维护的 `$DSH_HOME/profiles/node_modules` 兜底目录拿到；其他位置需要自备 `node_modules`，失败时是一条指出缺失包名的模块解析错误。

解析器在加载时读取目录，所以替换挂载插件的文件需要重启或 HMR 重载，而不是改配置。

挂载 `local:` 行的部署仍然带着能力前提：运行中的镜像必须包含本包以及根 Include 的 `local:` 分支。之后再加工具则不需要。
