# Agent Note: MCP 服务器在启动时挂载，而不是在回合里挂载

Status: implemented

[English](2026-11-16-mcp-mounting-at-startup.md) | 中文

## Problem

一次对话的外部 MCP 连接，是从打开它的那个请求里付的账。插件在 `agent/created` 时把每个生效的服务器挂进 `agent.ctx`，会话的第一个 `agent/pre-step` 最多阻塞 `firstStepWaitMs` 等这些挂载落定；一次登记表写入把会话标记为过期，下一步的重新核对也在同一份预算下被 await。于是第三方端点的延迟，直接挡在用户看到第一个字之前。

在生产集群上，这已经不是调参问题。集群 DNS 配的是 `ndots:5`，一个四个点的服务名因此要先撞四次 NXDOMAIN 才轮到真正的解析；十几个 MCP 主机在已经排满的 libuv 线程池上解析，耗时到几十秒。OpenAI 传输层的建连超时先到，请求以完全相同的节奏失败——无论流的超时怎么配——用户看到的是一个永远不出字的转圈。把 `timeoutMs` 和 `streamIdleTimeoutMs` 调大没有任何变化，因为那个截止时间在连接阶段，不在流上。由此得出的要求不是「等更久」，而是「不等」：连不上的服务器要跳过，连接属于启动、属于「加服务器的那次写入」，而组装模型请求绝不能是发生 MCP 握手的地方。

## Decision

挂载按两层拆分，各自放进「生命周期与这一行的归属相称」的最外层作用域。

- **系统清单在插件激活时挂一次，挂在插件自己的作用域里。** 激活在后台发起连接，不 await 它们。核心工具登记表按「就近作用域优先」解析名字，于是那些工具通过作用域链到达每个会话，不需要按会话挂载，部署对每个服务器只维持一条连接，而不是每个 agent 一条。
- **用户自己的记录在 `agent/created` 时挂进 `agent.ctx`**，同样在后台。环境用户只在该 agent 创建期间存在，而作用域注册正是「这一行对别人的会话不可见」的保证。它们挂在用户前缀的挂载名下（`mountNameFor('user', …)`），因此不可能和系统记录撞名。

请求路径上没有任何步骤在 await 一个 MCP 端点，因为这条路径上也没有任何东西去启动它。为「会话创建时发起的那次挂载」加过一版有上限的第一步等待，又删掉了：实测证明一步的工具清单在 `agent/pre-step` 之前就装配完成，等待改不动那一步的工具，见[为什么第一条消息可能没有用户层](2026-11-17-first-message-tool-list-ordering.md)。

一次登记表写入会**立刻**重挂两层——触发点是写入，不是步骤边界。每个挂载的 `failOnStartupError` 都保持 false，所以连不上的服务器记一条日志然后被放过；客户端自己的重连策略会把它带回来，且不挡住任何东西。从没连上的挂载不会被记成已挂载，因此下一次登记表写入会重试它。地址、请求头、超时或并发变了的挂载会被重建，指纹没变的一律不动。

旧名字 `firstStepWaitMs` 的步骤侧预算已经删掉。租户配置里由 `toolCallTimeoutMs` 取代它：那是挂载传给客户端的单次工具调用兜底超时，不是「一轮愿意为连接让路多久」的上限。后来一度加回过一处有上限的等待（`firstMessageWaitMs`），实测无效后又随机制一起删掉（[为什么第一条消息可能没有用户层](2026-11-17-first-message-tool-list-ordering.md)）。

每次挂载把结果上报给登记表（`McpServerStore.reportMount`），于是 `mcp.effectiveServers` 回答的是 `mounted`、`failed`（带原因）、`disabled` 或 `unknown`，而不是从「条目已启用」去推断健康状况。这份上报是进程内状态、从不落库：重试会覆盖它，条目消失就清掉它。没有它，配置界面会把一个连不上的端点显示成正常工作的服务器——因为它能看到的只有「已启用」这一个事实。而这正是用户在现网版本上添加第三方 MCP 服务器时真实遇到的情形。上报来自连接器而不是「激活成功」：`mcp-client` 会发出 `mcp/client-state`（`up`，或带原因的 `down`），每个挂载在落定之前就订阅它——因为 `failOnStartupError` 为 false，第三方端点绝不能导致 agent 激活失败；本设计的第一个构建正因为把激活当成证据，把一个被拒绝的端点上报成了 `mounted`。之后的重新连上会把上报改回 `mounted`。

## Alternatives considered

**把超时调大。** 对生产故障的第一个反应是把 `timeoutMs` 与 `streamIdleTimeoutMs` 设成三分钟。它什么也没改变：失败保持十秒的节奏，因为连接根本没建起来；而端点真的慢的时候，更长的截止时间只是把等待拉长。截止时间是对痛苦的限制，不是设计。

**保留按 agent 挂载，只缩短等待。** 把 `firstStepWaitMs` 调小，换来的是「一轮慢」变成「一轮经常缺它本该有的工具」。两种结果都是用户在替挂载付账。

**保留步骤边界上的核对，只把它改成不阻塞。** 这是改动最小的方案，但它是按要求被否掉的，不是按证据：用户刚存下的服务器，仍然要等到他下一次提问才开始连接。写入就是意图发生的时刻，所以写入就是触发点。

**把用户记录提到按用户的作用域里。** 做不到：用户身份走的是 `AsyncLocalStorage` 环境量，不是 Cordis 作用域，因此没有一个生命周期稳定的上下文可以托住某个用户的挂载。造一个出来，等于为同一个事实发明第二套权威。

**跨 agent 复用连接，同时保留按 agent 挂载。** 与「等待」这个问题正交，而且大得多：共用一条连接需要先定「一个 agent 里的工具调用能看到另一个 agent 的什么」这套策略，而且它并不能把握手从回合里拿走。系统层因为「归属是全部署的」而住进同一个作用域，顺带就拿到了复用连接的好处——那正是这一行归属的全部代价。

## Consequences

**买到的。** 一轮永远不会等一个 MCP 端点，所以慢的或已经死掉的服务器，代价是一次后台尝试加一行告警。系统层的连接每个进程只开一次，而不是每个 agent 一次；它的工具定义在宿主生命周期内稳定，因此它们占据的那段提示词前缀被跨请求、跨会话复用。每个会话的第一个请求就已经带着系统工具，而用户保存一个服务器时，它在他保存的那一刻开始连接。

**代价，删除。** 立刻重新核对会在一轮流式过程中移除工具。这表现为那一轮里一次失败的调用，而不是用户为自己已经完成的写入去等待。这正是上一版设计拒绝做的取舍，而现在它是写进文档的行为。

**代价，系统服务器只有一个客户端。** 每个访问某个系统服务器的会话共用同一个客户端，所以这一行携带的请求头必须对所有用户相同，它的 `toolConcurrency` 也是部署级上限而不是按 agent 计。需要按用户区分地址或凭据的服务器属于用户层，那一层是按会话挂载的。

**代价，没有步骤侧的就绪等待。** 自己那条记录还在连接中的会话，会不带该工具打开，并在后续某个请求里补上，届时付一次前缀失效。把请求推到挂载落定之后再发，正是这次改动要拿掉的东西。

## Testing

`packages/tenant/mcp-external/tests/mcp-external.spec.ts` 钉住两层划分和「回合里没有等待」：系统清单在激活时挂进插件作用域、此时还没有任何会话；自己没有任何记录的用户一个也不挂；另一个用户的记录不会进入第一个用户的作用域；步骤边界既不会被一个挂住的连接器阻塞，也不会发起任何挂载；一次登记表写入在不经过步骤的情况下完成挂载、卸载、重试与仅重连该重连的那个；销毁时关闭该层；挂载成功上报 `mounted`，端点拒绝则上报带原因的 `failed`，删掉条目后那份上报被清掉；`packages/host/apiproxy/tests/api-proxy-mcp.spec.ts` 钉住把它和 `mounted` 并列返回的接口字段。这套用例取代了原先按 agent 的旧用例——那些用例断言的正是本决策推翻的行为。
