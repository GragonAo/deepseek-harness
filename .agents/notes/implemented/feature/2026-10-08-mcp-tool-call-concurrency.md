# Agent Note: MCP tool-call concurrency from annotations, policy, an exclusive tool list, a retry allow-list, and a learned cap

Status: implemented

English | [中文](2026-10-08-mcp-tool-call-concurrency.zh.md)

## Problem

The MCP client registers each server's tools on `ctx.tools` without an `isConcurrencySafe` declaration, so the agent loop's scheduler classified every MCP call exclusive: one call at a time, each its own ordering barrier. A turn asking one server twenty questions pays twenty sequential round trips, even though MCP publishes annotations that answer exactly this question and both supported transports carry several requests over one connection. In the MCP SDK 1.29.0 the shared `Protocol.request()` takes no lock, the stdio transport sends one serialized message per `stdin.write()`, the Streamable HTTP transport issues one POST per message, and the server dispatches each received request without awaiting the previous handler, so no transport serializes a second call behind the first.

The opposite gap was the server's capacity. The harness bounds how many calls start — `maxParallelToolCalls` per agent step, `maxParallelSubCalls` per `run_code` program — but those budgets are shared by every registered tool, so they protect the host from the caller rather than one server from a fan-out. The deployment behind this work reaches roughly 180 tools across twelve `mcp-client` instances and raises `maxParallelSubCalls` to 32; with no per-server bound, one data-mining batch can put dozens of simultaneous requests on a single server process.

Every MCP server in that deployment is third-party: the fleet cannot be modified, so its tools cannot be made to declare `readOnlyHint` or `idempotentHint`, and the annotations route is unavailable as the source of a judgement. The deployer therefore judges each server itself, setting `toolConcurrency.policy: 'parallel'` in its own tenant configuration and owning the consequences. That answers capacity and read-only throughput but not ordering: a server whose tools are mostly read-only still has the few tools that write, and a parallel policy would let a write overlap the read that produced its input. Those tools need to stay serial without any cooperation from the server, so the deployment needs a client-side list of the tools that must not overlap — one server can then run at 20 concurrent calls while its five writing tools stay serial. This note records that mechanism as shipped.

Two gaps remained once the cap existed. The cap is a number the deployer must supply for a server that cannot be asked and is not observed: a value low enough to be safe wastes the throughput the fan-out was raised for, and a value high enough to be fast meets refusals that surface to the model as tool failures. The client already receives the evidence it needs to do better — a refusal is a failure it sees — but it discarded that evidence except as an error result. Second, a refused call is often worth re-sending: an overloaded server refuses one call out of a batch while serving the rest, and the model's answer is unchanged by one extra attempt. Nothing in the harness retries a tool call, and the bridge could not simply add retries because the same deployment has tools where a second attempt is a second write. Which tools those are is the deployment's knowledge alone: a third-party server that never declares `readOnlyHint` cannot be asked, and a list of tools to *exclude* from retrying is the wrong default, because an omission in it means the omitted write gets repeated.

## Decision

`packages/mcp/mcp-client` declares concurrency for every tool it registers, lets a deployment re-judge that declaration per server, holds each server's in-flight calls to a configured cap that learns the server's willingness to serve, and re-sends a refused call only when it is safe to repeat.

### The declaration comes from the tool's own annotations

`createDefinition` gives every MCP tool an `isConcurrencySafe` closure over that tool's static annotations and the server's resolved policy. A missing, false, or non-boolean hint classifies exclusive, so the declaration is always present and explicit rather than the scheduler's fail-closed fallback. Under the default policy a tool qualifies by advertising `readOnlyHint: true` or `idempotentHint: true`. `destructiveHint` and `openWorldHint` are not consulted: they warn that an operation is unsafe in ways unrelated to whether two calls may overlap.

The classifier ignores the call's arguments, unlike the first-party tools whose safety depends on the path or query they receive. An MCP input schema carries no read/write distinction the bridge could inspect, and MCP annotations are tool-level, so the tool-level answer is the complete one.

### `toolConcurrency.policy` re-judges a whole server

Both transports accept `toolConcurrency { policy, maxConcurrentCalls, exclusiveTools, retryTools, mode, decreaseFactor, recoveryStep, recoveryQuietMs, countTimeouts, retryAttempts, retryBaseDelayMs, retryJitterRatio }` with Schemastery defaults, plus an explicit resolve step (`resolveToolConcurrencyPolicy`) because programmatic construction can bypass the schema. `policy` takes one of three values:

- `annotations` (default) — trust `readOnlyHint` and `idempotentHint` as described above.
- `parallel` — every tool of this server may overlap, for a server whose annotations are absent or wrong while its tools are in fact safe.
- `exclusive` — no tool of this server may overlap, for a server whose annotations are optimistic or whose tools share state the protocol cannot describe.

The override exists because the operator knows the servers and the bridge can prove nothing about them. It is a per-server deployment value, so a server upgrade that adds tools inherits the judgement instead of silently escaping it. The tenant stack forwards this block unchanged and states no default of its own ([tenant tool presentation and concurrency](../architecture/2026-10-08-tenant-tool-presentation-and-concurrency.md)).

### `toolConcurrency.exclusiveTools` keeps named tools serial

A whole-server policy cannot separate the tools of a server that reads mostly and writes sometimes, which is the third-party case: `policy: 'parallel'` admits everything, `policy: 'exclusive'` forfeits the throughput the deployment raised the cap for. `exclusiveTools` is the per-tool answer, and it is deliberate deployment input rather than a reading of the server: it lists this server's own (raw) tool names — not the `mcp__<server>__<name>` form the model calls — and membership classifies a call exclusive whatever `policy` says and whatever the tool advertises, so a server lying about `readOnlyHint` on a mutating tool is corrected by naming it. The name says exactly which classification the field produces (`ToolExecutionMode`, `packages/core/tools/src/index.ts:380`) instead of a second vocabulary for the same fact.

A listed call reuses the loop's exclusive classification rather than a second scheduler inside the bridge. `createDefinition` answers the classifier from the server's resolved policy, so `ctx.tools.executionMode` returns `exclusive` and the existing scheduler takes over: in a native step, `packages/core/agent-loop/src/tool-calls.ts:88` classifies the next call, `:89` makes an exclusive call a group of one, `:203` stops filling a parallel pool at a call that reclassifies exclusive, `:220` drains in-flight work before that group returns, and `:245` consumes only what started — so the listed call runs alone; a `run_code` program follows the same rule inside its own pool (`packages/core/tools/src/code-mode.ts:353`, re-reading classification per start at `:532`). The scope is the dispatching step, not the server: sibling calls to other servers wait too, which is what makes a cross-server "read, then write the result" order hold, and the cost is that one listed call pauses unrelated read-only work of the same step. Other agents and later steps dispatch independently, and a listed call is alone when it starts, so it never queues behind the cap it is exempt from in practice.

The list is judged where the names first exist. Configuration loads before the server is asked for its tools, so no load-time check can see them; discovery cannot silently ignore them either. `syncTools` therefore validates the configured names against the names its `tools/list` pages returned, in the fetch phase whose documented contract is already "reject and leave the previous generation registered untouched": a startup sync fails the plugin instance and reports both the unknown names and the names the server does report, and a later re-sync (a server upgrade renamed the tool) is contained and logged while the last good generation keeps serving. An empty list is accepted as excluding nothing: Schemastery materializes a missing array key as `[]`, so an empty list and omission are the same value with no referent to judge, and a name that cannot refer to anything is rejected only when it is expressible — a blank entry fails at load (`resolveToolConcurrencyPolicy`), and a typo fails at discovery.

### Each server holds its own cap, and overflow waits

`maxConcurrentCalls` defaults to 10 and is enforced around the `tools/call` request alone: mapping the response, image admission, and materialization run after the slot is released, because they do not load the server. The default equals the harness-wide step default, so the cap binds exactly where a deployment raises the caller-side pools — the motivating stack's twelve servers at 10 hold a 32-wide fan-out to at most ten concurrent requests per server while the caller keeps its own budget.

A call over the cap waits in FIFO order instead of failing, for three reasons:

- The model asked for every one of these calls. The cap bounds one server's load, and rejecting a call the server could have served is an error the model cannot distinguish from a server failure.
- The SDK's per-call timeout starts inside `request()`, so queue time is not charged against `toolCallTimeoutMs`; [tool-call timeout policy](../architecture/2026-07-07-tool-call-timeout-policy.md) observes server time only. That policy is inert for MCP tools, which declare no `timeoutMs` of their own.
- Queue depth needs no bound of its own: the caller-side pools already bound how many calls can be in flight, and each queued call is accounted for there.

The limiter is created per plugin instance and shared by every generation, so a reconnect cannot widen the cap. Disposal closes it and fails calls still waiting — they never reached the server — so teardown reaches quiescence instead of stranding them, while a granted slot keeps its request on the wire and fails through the transport.

### `toolConcurrency.mode` learns the cap from the server's own refusals

`toolConcurrency` accepts `mode: 'adaptive'` (default) or `'fixed'`, plus the parameters of the rule below: `decreaseFactor` (0.5), `recoveryStep` (1), `recoveryQuietMs` (2000), `countTimeouts` (true), `retryAttempts` (0), `retryBaseDelayMs` (200), `retryJitterRatio` (0.2). Each is a validated Config field with a default constant, never a hardcoded value: how much a given server tolerates, and whether its latency means overload, is deployment knowledge. The rule itself is fixed, because it is the shape of the adaptation rather than a per-deployment number.

Adaptive is the default because the alternative default is a number nobody measured, and the repository's rule that a public default needs current-consumer evidence is satisfied here by the evidence that no such number exists: the twelve third-party servers behind this work publish no capacity, cannot be asked for one, and are not load-tested before a deployment points at them, so `maxConcurrentCalls: 10` is a guess with two failure modes rather than a value. A static guess that is too high produces exactly the refusals the learned cap absorbs, and one that is too low turns a raised fan-out into waves with nothing to show for it. Learning the value has no comparable failure mode: the effective cap stays inside `[1, maxConcurrentCalls]`, a granted slot is never revoked, and the decrease is bounded below by one call, so the worst case of the search is a slower batch — not a broken or unusable server. `maxConcurrentCalls` keeps its role as the ceiling for a deployment that measured its server, and `mode: 'fixed'` holds that number for the life of the connection when varying throughput is itself unwanted.

The configured `maxConcurrentCalls` becomes the starting value and the ceiling. A refused call multiplies the effective cap by `decreaseFactor` and floors it at one, so the multiplicative decrease is fast where the collapse is real: eight concurrent calls against a server that refuses everything reach one call at a time after eight refusals, and a refusal never stops calls from being sent. A call that completes adds `recoveryStep` back, but only once `recoveryQuietMs` have passed with no refusal and no earlier step, so recovery is one slot per quiet window and climbing from the floor to the ceiling takes at least `(ceiling - 1) * recoveryQuietMs`. The additive increase is deliberately slower than the multiplicative decrease, which is what keeps the cap near what the server accepted instead of oscillating over it.

A granted slot is never revoked: a drop only changes which waiting calls are admitted next, so a call already on the wire finishes and reports its own outcome. The learned value is per plugin instance and is not persisted or logged, which is stated in the README rather than approximated: a restart, an HMR reload, and each replica of a deployment start again at the ceiling, and independent replicas can therefore exceed what one server tolerates in aggregate. Coordinated limiting across replicas is out of scope.

### A refusal is a failure the client already sees

`packages/mcp/mcp-client/src/overload.ts` classifies the error thrown out of `callTool` instead of inventing a signal, so the predicate follows what the SDK and the runtime actually produce:

- HTTP 429 or any 5xx status, read from `StreamableHTTPError.code`; the SDK throws that error for any non-2xx POST to the endpoint (`@modelcontextprotocol/sdk/client/streamableHttp.js:364`, class at `:12`). Other 4xx statuses say the request was wrong, not that the server is loaded, and do not count.
- A closed connection, read from `McpError` code `-32000` (`ConnectionClosed`) — the code the SDK builds when its transport closes (`shared/protocol.js:263-268`) and also the code it surfaces when a JSON-RPC error response carries it (`:394-400`, `:459`), which is how a server whose overload path answers with that code is recognised.
- A refused or reset TCP connection, read from the `cause` chain of the runtime's `TypeError: fetch failed` (`ECONNREFUSED`, `ECONNRESET`, `EPIPE`, `EHOSTUNREACH`, `ENETUNREACH`, `UND_ERR_SOCKET`).
- A call that hit `toolCallTimeoutMs`, read from `McpError` code `-32001` (`RequestTimeout`) or an `ETIMEDOUT`/`UND_ERR_*_TIMEOUT` cause, and only when `countTimeouts` is true. The SDK reports a canceled call with the same `-32001` code (`shared/protocol.js:685-686`), so the call's own abort state gates the classifier: a call the harness canceled is never a refusal.

A JSON-RPC error the server chose for the tool, and a tool-level `{ isError: true }` result, are successful protocol responses: they fail the call without lowering the cap, and the tool's own error text reaches the model unchanged. The cause walk is bounded, so a self-referential chain terminates instead of hanging the classifier. Counting timeouts is on by default because an unresponsive server is the case the cap exists for; the README documents the cost, which is that a genuinely slow server is downgraded as if it were overloaded.

### Automatic retry is an allow-list, and it starts empty

`toolConcurrency.retryTools` names this server's raw tool names whose refused calls may be sent again, and `retryAttempts` re-sends such a call up to that many extra times, each delay `retryBaseDelayMs` doubling per attempt and scaled by `retryJitterRatio` to spread a batch that was refused together. A tool qualifies in one of two ways: its own annotations declare `readOnlyHint: true`, or the deployment names it in `retryTools`. Nothing else is retried, so an empty `retryTools` — the default — retries only tools the server itself declared read-only: a write is repeated only because a deployment stated that repeating it is safe, never because it was left out of a list. That is the whole reason the retry decision is an allow-list rather than the inverse of `exclusiveTools`: an omission from a deny-list retries a write by default, which is the failure that cannot be taken back.

The two lists answer different questions and neither implies the other, so a deployment reads three fields as three independent facts: `policy` says whether this server's calls may overlap at all, `exclusiveTools` says which of them must keep their submission order, `retryTools` says which of them may be sent twice. A read-only tool whose order matters is in both lists — serial and retryable; a tool that writes is in neither, and one that writes while being idempotent by construction is in `retryTools` only. Both lists are judged against the server's own `tools/list` at discovery, so a `retryTools` typo fails that tool synchronization: the effect would have been fail-safe (the tool is simply never retried), and the deployment's statement that repeating that call is safe would have had no referent.

`idempotentHint` alone does not admit a tool. Overlap-safety and repeat-safety are different properties — the first is read from the server's annotations because a wrong answer costs throughput, the second only from read-only proof or an explicit deployment statement because a wrong answer costs a duplicate — so a server whose `idempotentHint` the deployment trusts says so by naming the tool in `retryTools`, which is the same fact recorded where the deployment owns it. `destructiveHint` is likewise not consulted: it warns about the operation's consequences, not about whether a second attempt is safe.

A refused tool outside the allow-list fails on its first attempt and reports the server's own error; a refused call inside it is re-sent, and a call canceled while waiting for its retry fails with the cancellation.

Each attempt takes its own queue slot and its own `toolCallTimeoutMs` window, because the SDK starts that timeout inside its own request: neither queue time nor backoff is charged to the call, and the total wall clock is bounded by `(attempts + 1) * toolCallTimeoutMs` plus the backoff. Each refused attempt is also an overload report, so a retrying call lowers the cap faster than a non-retrying one — deliberate, because a server refusing the same call three times is telling the client more than three independent calls each refused once. Retry attempts are server-side requests the model never sees: the call still produces exactly one result, or one error.

## Alternatives considered

**Declare every MCP tool concurrent.** The cheapest way to reach the workload's throughput, and correct for a deployment of read-only servers. It asserts safety on behalf of a server that never claimed it, so a server whose tools mutate shared state would be hit concurrently and the failure would appear as corrupted data rather than a tool error.

**Require configuration instead of reading annotations.** A deployment could name each concurrent server explicitly, and the mechanism would never trust third-party metadata. It also withholds concurrency from every server that already declares it correctly, which is the common case, and makes the classification a maintenance item per server. Reading annotations with an override keeps the default useful and the exception explicit.

**Bound calls with the existing harness-wide cap only.** `maxParallelToolCalls` and `maxParallelSubCalls` already limit what starts, so no per-server value is strictly needed. They are shared across all tools and servers, so one saturating server consumes the budget and the rest wait behind it; the bound would also change meaning whenever an unrelated deployment raised the global value.

**Classify and schedule inside the MCP client instead of declaring `isConcurrencySafe`.** The bridge could group sibling calls itself and decide which overlap. Grouping, barriers, abort draining, and model-order commits belong to the loop's scheduler, which sees one dispatch per call and would still treat an MCP call as exclusive against sibling native calls — an exclusive `bash` write could not be ordered before an MCP read. The client instead bounds capacity, which is what the scheduler's contract already assigns to providers.

**Hold exclusive tools on a lock of the bridge's own.** A per-server mutex around `tools/call` — a listed call waits for the server's in-flight calls to end and holds it alone — enforces the same non-overlap for every caller, including one that dispatches past the scheduler. It is strictly weaker where the deployment needs it most: it orders calls within one server and says nothing about the read of another server that produced the value being written, and it adds a second ordering authority inside `mcp-client` that can disagree with the loop's. The loop's exclusive classification already runs alone and already orders against every other call of the step, so listing a tool reuses the tested barrier and leaves the bridge owning only the capacity the scheduler delegates to providers.

**Reject an empty `exclusiveTools` list.** `ctx.tools.restrict({})` rejects an empty filter as almost always a materialized-empty-config bug, and a list that names nothing looks like the same mistake. It is not expressible here: Schemastery resolves a missing array key to `[]`, so the resolver receives one value for "omitted" and "empty" and would reject every server that simply does not use the option. A blank name stays a load-time error, and a name the server does not list fails discovery where the judgement is possible.

**Fail calls over the cap.** A rejection is a new error the model must interpret, it discards work the server could have done, and it forces deployments to choose cap values that never bind. Both effects push operators toward disabling the cap.

**Bound the queue's depth or wait time.** The caller-side pools already bound submissions, so a depth bound would reject calls the caller's own pool had accepted. A wait timeout reintroduces the spurious failure with a second knob to tune.

**Keep `mode: 'fixed'` as the default.** The cap then always equals what the operator wrote, which is a property a generic default can honestly have, and adaptivity becomes the exception a deployment asks for. It also makes `maxConcurrentCalls` mean the same thing in every deployment, at the cost of requiring a number that the third-party servers behind this work do not publish, cannot be asked for, and are not measured before a deployment points at them — so the default would be a guess whose too-high case degrades exactly as much as the adaptive cap does, and whose too-low case silently wastes the fan-out the deployment raised. Adaptive has no unbounded failure: it is bounded to `[1, maxConcurrentCalls]`, it never revokes a granted slot, and it needs only the refusals the client already receives as evidence that the server is not keeping up. The deployment that measured its server can still opt out with `mode: 'fixed'`, and for the same reason `retryAttempts` defaults to 0: a retry hides a failure the model could have reacted to and adds latency to every refused call, and repeating a call is a stronger claim than varying how many run at once.

**One list for both questions.** `exclusiveTools` already marks the calls where a second send is a second write, so retrying everything *not* listed needs no new field and no second thing to keep in sync. It is a deny-list, and its default is therefore the dangerous one: with the list empty — the state of every server that never configured it — every tool is retried, including the writes the deployment never thought about, and a single omitted name turns a refusal into a duplicate write. An allow-list fails in the direction that costs a failed call rather than a repeated side effect, so the repetition question gets its own list and the safety default is "nothing".

**Retry every tool that is not `exclusiveTools`.** Re-sending is only unsafe when the server received and acted on the first attempt, and a refusal is usually proof it did not. The client cannot prove that: a connection reset after the request was delivered is precisely the case where the server may have run the call, and an unlisted tool is exactly the case the client cannot judge — the deployment may simply never have considered it. Reading `readOnlyHint` and letting the deployment name the rest keeps the automatic case to tools that stated they are read-only.

**Persist or share the learned cap.** Writing the learned value to a file, or sharing it across replicas, would carry learning across restarts and stop independent instances from adding up past a server's capacity. Both need an owner and a storage format the harness does not have for a per-server heuristic, and a persisted value from a different deployment or a different server version is a stale guess that is harder to reason about than a restart. The state stays in the plugin instance and the README states the consequence.

**Count only explicit refusals, never timeouts.** A timeout is ambiguous — overload and a slow query look the same — so counting it can serialize a batch for no benefit. The ambiguity runs the other way too: an overloaded server that answers nothing within the timeout is the common failure the cap is for, and not counting it leaves the client at full concurrency hammering it. The judgement is a deployment value, `countTimeouts`, on by default with the over-downgrade documented rather than hidden.

## Verification

Unit (`tests/concurrency.spec.ts`: 48 tests). The fixture is a real `McpServer` over `InMemoryTransport.createLinkedPair()` whose handlers record their own peak overlap, so every number below is what the server observed rather than what the bridge believes.

- Classification: a `readOnlyHint` tool and an `idempotentHint` tool resolve to `parallel` through `ctx.tools.executionMode`; a tool with no annotations and a tool advertising `readOnlyHint: false, destructiveHint: true` resolve to `exclusive`; `policy: 'parallel'` and `policy: 'exclusive'` override in both directions; two servers keep their own policy; `exclusiveTools` excludes exactly the names it lists whatever the policy says, including a tool advertising `readOnlyHint`, and leaves every other tool of that server alone.
- Overlap: four default-policy calls peak at four handlers in flight; five calls under `maxConcurrentCalls: 2` peak at two and still return all five results with their own tags; three under a cap of one peak at one and enter the handler in submission order; two servers capped at one each peak at one while running together.
- Limiter: a signal aborted before dispatch takes no slot, a signal aborted while queued rejects with its own reason and leaves the slot to the next waiter, an abort after the grant does not free the slot twice, release is idempotent, and `close` rejects queued and later acquisitions while a granted slot keeps working.
- Learned cap: each overload report halves the cap (8 → 4 → 2) and ten reports stop at one; a drop while four slots are granted admits nothing new and the next call runs only after they are released, which is the no-revocation rule; one step per quiet window climbs 1 → 2 → 3 → 4, extra completions inside a window add nothing, the ceiling holds, and a refusal restarts the window (a 900 ms + 900 ms split with a 1000 ms window takes no step, a further 100 ms does); `mode: 'fixed'` ignores every report. The recovery window is a clock the test injects through `ToolConcurrencyInternals.now`, so no assertion depends on elapsed time.
- Retry safety: a tool is retryable when its annotations declare `readOnlyHint: true` or `retryTools` names it, and not otherwise — absent annotations, `readOnlyHint: false`, a non-boolean hint, and `idempotentHint: true` alone all leave it unrestried, while an empty `retryTools` with no read-only annotation retries nothing. The two lists stay independent: a tool in both is serial and retryable, a tool in `exclusiveTools` only is serial and never retried. The delay doubles per attempt and is symmetric around the base delay at `retryJitterRatio: 0.5`, exact at 0, and `waitBeforeRetry` reports an abort before and during the wait.
- Resolution and config: `resolveToolConcurrencyPolicy` rejects unknown keys, an unknown policy, an unknown mode, a cap that is not a positive integer, a blank `exclusiveTools` or `retryTools` entry, a `decreaseFactor` outside the open 0..1 interval, a non-positive `recoveryStep`, a `recoveryQuietMs` outside the timer range, a non-boolean `countTimeouts`, and out-of-range retry values, while an empty list resolves to naming nothing and an omitted block resolves to the documented defaults; `tests/apply.spec.ts` pins the Config schema's defaults (including `mode: 'adaptive'` and the two empty lists), partial merge, list passthrough, explicit values, and rejection of an invalid block; `tests/mcp-client.spec.ts` pins that discovery rejects a name from either list that the server does not report — one name, several names, both lists in one diagnostic, with the names it does report — that a re-sync which loses the name keeps the previous generation registered, and that a listed name the server does report syncs cleanly; `tests/reconnect.spec.ts` pins that disposal fails a call queued behind the cap and that the waiting call never reaches the server.
- Refusal classification (`tests/overload.spec.ts`: 10 tests): `StreamableHTTPError` 429/500/503 count and 400/401/403/404/405/422 and an unknown status do not; `McpError` `-32000` from either the transport or a JSON-RPC error response counts; `-32001` counts only with `countTimeouts`; a connection-lost or expired cause code counts through a wrapped `fetch failed`, from any depth up to the bound; a five-deep and a self-referential cause chain terminate without a signal; an aborted call is never a refusal even when it carries `-32000` or `-32001`; and a tool-level failure never counts.

Integration (`tests/exclusive-tools.spec.ts`: 6 tests). Snapshot: none — the classification, the learned cap, and the retry decision are not model-visible and results commit in model order, so a transcript matches the serial case and a snapshot would only add timing dependence. The 180-tool fan-out that motivated the change is verified by the owner against the deployed stack rather than by a repo test.

## Consequences

- Read-only MCP work now runs beside sibling tool calls, so a batch of queries to one server costs one round trip instead of one per call.
- The bridge trusts two hints a third-party server writes. A server that advertises `readOnlyHint` while mutating shared state now runs concurrently, and the deployment's answer is `toolConcurrency.policy: 'exclusive'` for that server or `exclusiveTools` for the tools that mutate. Reading the protocol's own metadata is the accepted risk; the previous serial behavior stays one config value away.
- A listed call is exclusive for the whole assistant step, so a step that pairs it with unrelated read-only calls to other servers loses that overlap. The list is therefore scoped to tools that write; a deployment wanting per-server-only serialization cannot get it from this field.
- `exclusiveTools` is validated against the server's own tool list at discovery, so renaming a tool on a third-party server fails that re-sync loudly until the configuration follows. That is deliberate: the alternative is a list that silently stops protecting a mutating tool.
- `maxConcurrentCalls` is a per-instance, per-deployment value: below the caller-side fan-out it turns a batch into waves, and above the server's capacity it stops protecting anything. The default of 10 equals the harness-wide step default rather than a measured server capacity, so a deployment with a known-slow server lowers it.
- A deployment that raises the caller-side pools without raising `maxConcurrentCalls` gets throttling it did not ask for; the queue is invisible except as latency.
- The bridge owns a FIFO slot queue of its own, but only for capacity: it never reorders, groups, or drops a call.
- Adaptive is the default, so a deployment that wants a throughput it can predict sets `mode: 'fixed'`. What it gets by default is a cap that follows what the server did earlier in the same process lifetime: a server that was overloaded at 08:00 serves a batch at one call at a time until the quiet windows restore the cap.
- The learned cap is per instance and per process: it is not persisted, not logged, and not shared between replicas, so several instances pointing at one server can still exceed what it tolerates. The README states this under known limitations; the fallback is a lower `maxConcurrentCalls` or `mode: 'fixed'`.
- `countTimeouts: true` means a slow server is treated as an overloaded one, so a batch against a server whose latency is expected can end up serialized with nothing gained. Lowering `toolCallTimeoutMs`, lowering `recoveryQuietMs`, or setting `countTimeouts: false` is the deployment's answer.
- An empty `retryTools` means a refused call to a tool that does not declare `readOnlyHint` is never re-sent, so a deployment that wants the retry budget for its writes has to name them, and a third-party server that never declares read-only annotations gets no automatic retry at all. That is the intended direction: the alternative fails by writing twice instead of by failing once.
- Retrying trusts the server's own `readOnlyHint`, which is wire data a third-party server controls, so a server that mislabels a writing tool as read-only has its refused calls repeated. There is no per-tool denial — the retry decision has no "never" — so the answer for a server whose annotations are wrong in that direction is `retryAttempts: 0`, which also disables the budget for the tools the deployment listed.
- A retried call can hide a failure the model would otherwise have seen, and each attempt costs up to `toolCallTimeoutMs` plus its backoff. Retry is off by default, and a tool outside the allow-list never retries at all.
- Retry attempts are server-side work: a batch of refused calls with `retryAttempts: 2` can put three times as many requests on an overloaded server within one call's lifetime, which is why each refused attempt also lowers the cap. The two mechanisms push in opposite directions on purpose, and the cap wins because the decrease is multiplicative and the recovery is additive.
