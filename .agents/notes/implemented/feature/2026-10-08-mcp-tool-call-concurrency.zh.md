# Agent Note: MCP tool-call concurrency from annotations, policy, an exclusive tool list, a retry allow-list, and a learned cap

Status: implemented

[English](2026-10-08-mcp-tool-call-concurrency.md) | 中文

## 问题

MCP 客户端把每个服务器的工具注册到 `ctx.tools` 时不声明 `isConcurrencySafe`，因此 agent loop 的调度器把每次 MCP 调用都判定为独占：一次只跑一个调用，每个调用都是一道顺序屏障。一个轮次里向同一服务器提二十个问题就要付二十次串行往返，而 MCP 恰好定义了回答这个问题的注解，两种受支持的传输也都能在一条连接上承载多个请求。在 MCP SDK 1.29.0 中，共享的 `Protocol.request()` 不加锁，stdio 传输对每条消息做一次序列化后调用一次 `stdin.write()`，Streamable HTTP 传输对每条消息发起一次独立 POST，服务器收到请求后不会等待上一个处理函数结束就开始处理，因此没有任何传输把第二个调用串行排在第一个之后。

相反的缺口是服务器的容量。harness 限制了「启动多少个调用」——每个 agent 步骤 `maxParallelToolCalls`、每个 `run_code` 程序 `maxParallelSubCalls`——但这些预算由所有已注册工具共享，保护的是 host 不被调用方压垮，而不是某个服务器不被扇出压垮。这项工作背后的部署在一个 case 会话中横跨十二个 `mcp-client` 实例、约 180 个工具，并把 `maxParallelSubCalls` 提到 32；没有按服务器计的边界，一次数据挖掘批次就能把几十个并发请求压到同一个服务器进程上。

该部署中的每个 MCP 服务器都是第三方：整个集群无法改动，因此无法让它们的工具声明 `readOnlyHint` 或 `idempotentHint`，注解这条路作为判定来源无法使用。部署方于是自行判定每个服务器，在自己的租户配置里设置 `toolConcurrency.policy: 'parallel'`，并承担其后果。这解决了容量与只读吞吐，却没有解决顺序：一个以只读工具为主的服务器仍然有少数写数据的工具，而 parallel 策略会让写入与产生其输入的读取重叠。这些工具必须在服务器毫不知情的前提下保持串行，因此部署需要一份客户端侧的「绝不重叠」工具名单——这样一个服务器可以跑 20 个并发调用，而其中五个写数据的工具保持串行。本记录记载的就是这一机制的实际实现。

上限存在之后仍有两个缺口。这个上限是部署方必须为一个既问不到也观察不到的服务器给出的数字：低到安全的取值浪费了抬高扇出所追求的吞吐，高到快速的取值则会遇到以工具失败的形式呈现给模型的拒绝。客户端其实已经在接收它需要的证据——拒绝就是它看到的失败——但它除了把拒绝当作错误结果之外丢弃了这份证据。其次，被拒的调用往往值得重发：过载的服务器会拒绝一批调用中的一个而服务其余调用，而多尝试一次并不改变模型的答案。harness 中没有任何东西会重试工具调用，而桥接层也不能简单加上重试，因为同一部署里存在「再试一次就是再写一次」的工具。哪些工具属于这一类只有部署方知道：一个从不声明 `readOnlyHint` 的第三方服务器问不出来，而一份「不重发」的黑名单本身就是错误的默认方向，因为名单里漏掉一个写工具就意味着这个写操作会被重复执行。

## 决策

`packages/mcp/mcp-client` 为它注册的每个工具声明并发性，允许部署按服务器重新判定该声明，允许部署点名必须保持串行的工具，把每个服务器的在途调用限制在一个会学出服务器承接意愿的可配置上限内，并且只在重复确实安全时才重发被拒的调用。

### 判定来自工具自身的注解

`createDefinition` 为每个 MCP 工具给出一个 `isConcurrencySafe` 闭包，其输入是该工具静态的注解与该服务器已解析的策略。注解缺失、为 false 或不是布尔值时判定为独占，因此声明始终存在且明确，而不是落到调度器的 fail-closed 兜底上。默认策略下，工具通过声明 `readOnlyHint: true` 或 `idempotentHint: true` 获得资格。不参考 `destructiveHint` 与 `openWorldHint`：它们提示的是操作在别的意义上的不安全，与两个调用能否重叠无关。

与那些安全性取决于所收路径或 query 的一等工具不同，该判定忽略调用的参数。MCP 输入 schema 不携带桥接层可检查的读/写区分，而 MCP 注解本身是工具级的，所以工具级的答案就是完整的答案。

### `toolConcurrency.policy` 重新判定整个服务器

两种传输都接受 `toolConcurrency { policy, maxConcurrentCalls, exclusiveTools, retryTools, mode, decreaseFactor, recoveryStep, recoveryQuietMs, countTimeouts, retryAttempts, retryBaseDelayMs, retryJitterRatio }`，带 Schemastery 默认值，并配有一个显式的解析步骤（`resolveToolConcurrencyPolicy`），因为程序化构造可以绕过 schema。`policy` 取三个值之一：

- `annotations`（默认）——按上文所述信任 `readOnlyHint` 与 `idempotentHint`。
- `parallel`——该服务器的所有工具都可重叠，用于注解缺失或有误、但工具实际上安全（只读或彼此独立）的服务器。
- `exclusive`——该服务器没有任何工具可以重叠，用于注解过于乐观、或工具之间共享协议无法描述的服务器。

该覆盖项存在的原因是运维者了解这些服务器，而桥接层无法证明任何关于它们的事实。它是按服务器的部署取值，因此服务器升级新增工具时会继承该判定，而不会悄悄逃逸。租户栈原样转发这一配置块，自己不声明默认值（[租户工具呈现与并发](../architecture/2026-10-08-tenant-tool-presentation-and-concurrency.md)）。

### `toolConcurrency.exclusiveTools` 让点名的工具保持串行

整体策略无法区分「以读为主、偶尔写」的服务器内部的工具，而这正是第三方场景：`policy: 'parallel'` 放行一切，`policy: 'exclusive'` 又放弃了部署抬高上限所要的吞吐。`exclusiveTools` 就是按工具给出的答案，而它刻意是部署输入而不是对服务器的读取：它列出该服务器自己的（原始）工具名称——不是模型调用的 `mcp__<server>__<name>` 形式——列入名单即判定为独占，与 `policy` 和该工具自称的注解无关，因此在写数据的工具上谎称 `readOnlyHint` 的服务器只需点名即可纠正。字段名直接说明它产生哪种判定（`ToolExecutionMode`，`packages/core/tools/src/index.ts:380`），而不是为同一事实再造一套词汇。

被列入名单的调用复用 loop 的独占判定，而不是在桥接层再造一个调度器。`createDefinition` 按服务器已解析的策略回答分类器，因此 `ctx.tools.executionMode` 返回 `exclusive`，随后由既有调度器接手：在原生步骤中，`packages/core/agent-loop/src/tool-calls.ts:88` 判定下一个调用，`:89` 把独占调用变成只含它一个的组，`:203` 在遇到会被重新判定为独占的调用时停止填充并行池，`:220` 在该组返回前排空在途工作，`:245` 只消费已启动的部分——于是被列入名单的调用单独运行；`run_code` 程序在自己的池内遵循同一规则（`packages/core/tools/src/code-mode.ts:353`，每次启动前在 `:532` 重新读取判定）。作用域是发起派发的那个步骤，而不是该服务器：发往其它服务器的同级调用同样要等，这正是「先读、再写回结果」的跨服务器顺序得以成立的原因，代价是一个被列入名单的调用会暂停同一步骤中无关的只读工作。其它 agent 与后续步骤各自独立派发，而被列入名单的调用启动时是独自运行的，因此不会因为同一服务器的上限而额外排队。

名单在名称首次存在的地方判定。配置在向服务器索要工具列表之前就已加载，所以没有任何加载期检查能看到这些名称；发现阶段也不能静默忽略它们。因此 `syncTools` 在其 `tools/list` 各页返回的名称上校验配置的名称，且位于获取阶段——该阶段的既有契约本就是「拒绝并让上一世代保持注册不变」：启动时的同步会让插件实例失败，并同时报出未知名称与服务器实际报告的名称；之后的重新同步（服务器升级改了工具名）被就地容纳并记录日志，而最后一个正常世代继续服务。空名单被接受为「不排除任何工具」：Schemastery 会把缺失的数组键物化为 `[]`，因此空名单与省略是同一个值、没有任何可供判定的指称对象；只有当「无法指称任何东西」本身可表达时才会被拒绝——空白条目在加载期失败（`resolveToolConcurrencyPolicy`），拼错的名称在发现阶段失败。

### 每个服务器保有自己的上限，超出上限的调用排队等待

`maxConcurrentCalls` 默认 10，只围绕 `tools/call` 请求本身生效：映射响应、图片准入与物化都在槽位释放之后进行，因为它们不会给服务器带来负载。该默认值等于 harness 全局的步骤默认值，因此上限恰好在一个部署抬高调用侧池子时开始生效——上述部署的十二个服务器各为 10，把一次 32 宽的扇出限制在每个服务器最多十个并发请求，同时调用方保有自身预算。

超出上限的调用按 FIFO 顺序等待而不是失败，理由有三：

- 这些调用都是模型主动发起的。上限限制的是一个服务器的负载，而拒绝一个服务器本来能处理的调用，会产生模型无法与服务器故障区分开的错误。
- SDK 的单次调用超时在 `request()` 内部才开始计时，因此排队时间不计入 `toolCallTimeoutMs`；[工具调用超时策略](../architecture/2026-07-07-tool-call-timeout-policy.md)只观察服务器侧时间。对 MCP 工具而言该策略本身是惰性的，因为它们不声明自己的 `timeoutMs`。
- 队列深度不需要自己的边界：调用侧的池子已经限定了最多能有多少调用在途，每个排队调用在那里都已被计入。

限流器按插件实例创建、由每一代共享，因此重连不会放宽上限。dispose 会关闭它并让仍在等待的调用失败——它们从未到达服务器——从而让 teardown 达到静止状态而不是把它们搁置，而已获槽位的调用请求仍在协议上，会经由传输失败。

### `toolConcurrency.mode` 从服务器自身的拒绝中学出上限

`toolConcurrency` 接受 `mode: 'adaptive'`（默认）或 `'fixed'`，以及下文规则所需的参数：`decreaseFactor`（0.5）、`recoveryStep`（1）、`recoveryQuietMs`（2000）、`countTimeouts`（true）、`retryAttempts`（0）、`retryBaseDelayMs`（200）、`retryJitterRatio`（0.2）。每个都是带默认常量的、经过校验的 Config 字段，绝不是写死的取值：某个服务器能承受多少、其延迟是否意味着过载，都是部署知识。规则本身是固定的，因为它是自适应的形态，而不是按部署给定的数字。

自适应是默认值，因为另一种默认值是一个没人实测过的数字，而仓库「公共默认值需要当前消费者证据」的规则在这里恰好由「不存在这种数字」这一证据满足：这项工作背后的十二个第三方服务器不公布容量、问不到容量，在部署指向它们之前也不会先做压测，因此 `maxConcurrentCalls: 10` 是一个带两种失败模式的猜测，而不是一个取值。猜得太高，产生的正是学到的上限会吸收的那些拒绝；猜得太低，就把抬高过的扇出变成多波等待而毫无收益。学出这个值没有可比拟的失败模式：生效上限始终落在 `[1, maxConcurrentCalls]` 内，已授予的槽位绝不收回，下调的下限是一次调用，因此这次搜索最坏的结果只是一批调用变慢，而不是服务器被弄坏或用不了。对已经实测过自己服务器的部署，`maxConcurrentCalls` 仍然充当上限，而当「吞吐随时间变化」本身就不受欢迎时，`mode: 'fixed'` 会在整条连接的生命周期内保持那个数字。

配置的 `maxConcurrentCalls` 成为起始值与最高上限。被拒的调用会把生效上限乘以 `decreaseFactor` 并以一为下限，因此在崩溃真实发生时乘性下调很快：八个并发调用打向一个拒绝一切的服务器，八次拒绝之后就是一次一个调用，而拒绝绝不会让调用停止发出。完成的调用会加回 `recoveryStep`，但仅当已有 `recoveryQuietMs` 没有拒绝、也没有更早的回升——因此回升是每个静默窗口一个槽位，从下限爬回上限至少需要 `(上限 - 1) * recoveryQuietMs`。加性回升刻意慢于乘性下调，这正是让上限停在服务器实际接受的附近、而不是在上方震荡的原因。

已经授予的槽位绝不会被收回：下调只改变接下来哪些等待中的调用获准进入，因此在途的调用会跑完并报告自己的结果。学到的取值按插件实例保存，不持久化也不记日志——README 直说这一点，而不做近似：重启、HMR 重载以及部署的每个副本都会从上限重新开始，因此相互独立的副本叠加起来仍可能超过单个服务器能承受的量。跨副本的协同限流不在范围内。

### 「被拒」是客户端已经看到的失败

`packages/mcp/mcp-client/src/overload.ts` 对 `callTool` 抛出的错误做判定，而不是发明一个信号，因此该判据跟随 SDK 与运行时实际产生的东西：

- HTTP 429 或任何 5xx 状态，读取 `StreamableHTTPError.code`；SDK 对任何非 2xx 的端点 POST 都会抛出该错误（`@modelcontextprotocol/sdk/client/streamableHttp.js:364`，类在 `:12`）。其余 4xx 说明请求本身有问题，而不是服务器负载高，因此不计入。
- 连接关闭，读取 `McpError` 的 `-32000`（`ConnectionClosed`）——SDK 在其传输关闭时构造该码（`shared/protocol.js:263-268`），当 JSON-RPC 错误响应携带该码时也会浮现它（`:394-400`、`:459`），过载路径以该码应答的服务器就是这样被识别的。
- 被拒绝或被重置的 TCP 连接，读取运行时 `TypeError: fetch failed` 的 `cause` 链（`ECONNREFUSED`、`ECONNRESET`、`EPIPE`、`EHOSTUNREACH`、`ENETUNREACH`、`UND_ERR_SOCKET`）。
- 触及 `toolCallTimeoutMs` 的调用，读取 `McpError` 的 `-32001`（`RequestTimeout`）或 `ETIMEDOUT`／`UND_ERR_*_TIMEOUT` 原因的 `cause`，且仅在 `countTimeouts` 为 true 时计入。SDK 对被取消的调用报告同一个 `-32001` 码（`shared/protocol.js:685-686`），因此判定由该调用自身的 abort 状态把关：被 harness 取消的调用绝不算被拒。

服务器为工具选择的 JSON-RPC 错误，以及工具层的 `{ isError: true }` 结果，都是协议层面的成功响应：它们让调用失败，但不会下调上限，工具自身的错误文本也原样到达模型。cause 链的遍历是有界的，因此自引用的链条会终止而不是把判定挂住。计入超时默认开启，因为无响应的服务器正是上限存在的场景；README 记载了它的代价——真正缓慢的服务器会被当作过载而下调。

### 自动重发是一份允许名单，且默认为空

`toolConcurrency.retryTools` 列出该服务器中允许在被拒后重发的原始工具名称，`retryAttempts` 则把这样的调用最多额外重发该次数，每个延迟为 `retryBaseDelayMs` 逐次翻倍，并按 `retryJitterRatio` 缩放，以打散被一起拒绝的批次。工具通过两条途径之一获得资格：它自己的注解声明 `readOnlyHint: true`，或部署方在 `retryTools` 中点名它。除此之外一律不重发，因此默认的空 `retryTools` 只会重发服务器自己声明为只读的工具：一个写操作被重复执行，只能是因为部署方明确说过重发它安全，绝不会是因为它没被列进某份名单。这正是重发判定采用允许名单而不是取 `exclusiveTools` 之反的原因：黑名单漏掉一项就默认重发一个写操作，而这个失败收不回来。

两份名单回答的是不同问题，谁也不蕴含谁，因此部署方读到的三个字段是三件独立的事实：`policy` 说明该服务器的调用能否重叠，`exclusiveTools` 说明其中哪些必须保持提交顺序，`retryTools` 说明其中哪些允许发两次。一个顺序重要的只读工具同时出现在两份名单里——串行且可重发；一个写工具哪份都不进；而一个按构造幂等的写工具只进 `retryTools`。两份名单都在发现阶段按服务器自己的 `tools/list` 判定，因此 `retryTools` 写错名字会让该次同步失败：其效果本来会是失败安全的（该工具只是永不重发），但部署方「重复此调用安全」的陈述将失去指称对象。

仅有 `idempotentHint` 不足以让工具获得资格。可重叠与可重复是两种不同的性质——前者读取服务器的注解，因为答错只损失吞吐；后者只依据只读证明或部署方的明确陈述，因为答错会产生重复执行——所以部署方若信任某服务器的 `idempotentHint`，就把该工具写进 `retryTools`，即把同一个事实记录在部署方拥有的地方。`destructiveHint` 同样不参考：它提示的是操作的后果，而不是第二次尝试是否安全。

不在允许名单内的被拒工具在首次尝试即失败并报告服务器自身的错误；名单内的被拒调用会被重发，而等待重发期间被取消的调用以该取消失败。

每次尝试各自占用队列槽位、各自拥有 `toolCallTimeoutMs` 时限，因为该超时由 SDK 在自己的请求内部启动：排队与退避都不计入该次调用，总耗时上限为 `(尝试次数 + 1) * toolCallTimeoutMs` 加上退避。每次被拒的尝试同样是一份过载报告，因此会重发的调用比不重发的调用更快下调上限——这是刻意的，因为服务器三次拒绝同一个调用，比三次独立调用各被拒一次传达了更多信息。重发尝试是模型不会看到的服务器侧请求：该调用仍然只产生一个结果，或一个错误。

## 备选方案

**把每个 MCP 工具都声明为可并发。** 这是达到该工作负载吞吐量最省事的方式，对由只读服务器组成的部署也是正确的。它替一个从未做出该声明的服务器断言了安全性，因此工具会改动共享状态的服务器将被并发访问，而失败会表现为数据损坏而不是工具错误。

**要求配置，而不是读取注解。** 部署可以逐个点名可并发的服务器，机制也就永不信任第三方元数据。它同时剥夺了每一个已经正确声明并发的服务器的并发能力——而这是常见情况——并把判定变成每个服务器的维护项。读取注解并提供覆盖项，让默认值保持可用，同时让例外保持明确。

**只用现有的 harness 全局上限来限制调用。** `maxParallelToolCalls` 与 `maxParallelSubCalls` 已经限制了启动量，因此按服务器计的取值并非严格必需。它们由所有工具和服务器共享，所以一个打满的服务器会吃掉预算、其余服务器排在它后面；而且只要无关的部署抬高全局取值，这个边界的含义就会改变。

**在 MCP 客户端内部自行判定与调度，而不是声明 `isConcurrencySafe`。** 桥接层可以自行对同级调用分组并决定哪些重叠。分组、屏障、中止排空与按模型顺序提交都属于 loop 的调度器，它每次调用只看到一次 dispatch，仍会把 MCP 调用相对于同级原生调用当作独占处理——独占的 `bash` 写入无法被排在 MCP 读取之前。客户端改为只限定容量，而调度器的契约本来就把容量控制交给 provider。

**让被点名的工具由桥接层自持的一把锁来串行。** 在 `tools/call` 外按服务器加互斥量——被列入名单的调用等待该服务器的在途调用结束，然后独自持有它——对包括绕过调度器直接派发的调用方在内的所有调用方都能强制同样的不重叠。在最需要它的地方它严格更弱：它只在一个服务器内部排序，对「产生待写值的另一个服务器的读取」毫无约束，并且在 `mcp-client` 内部引入第二个排序权威，可能和 loop 的判定相互矛盾。loop 的独占判定本就已经单独运行、并且已经相对于同一步骤的每个其它调用排序，所以点名一个工具即复用了经过验证的屏障，桥接层只需持有调度器委派给 provider 的容量。

**拒绝空的 `exclusiveTools` 名单。** `ctx.tools.restrict({})` 会把空过滤器当作「几乎总是配置被物化为空」的 bug 拒绝，而一个不点名任何工具的名单看起来正是同一种错误。但这里无法表达出这种区别：Schemastery 会把缺失的数组键解析为 `[]`，因此解析器对「省略」和「空」收到的是同一个值，拒绝它就会拒绝每一个只是没用到该选项的服务器。空白名称仍然是加载期错误，而服务器未列出的名称会在判定可行的发现阶段失败。

**让超出上限的调用失败。** 拒绝是模型必须解读的新错误，它丢弃了服务器本可完成的工作，并迫使部署选择永远不会生效的上限值。这两种效果都会把运维者推向关闭上限。

**限制队列深度或等待时间。** 调用侧的池子已经限定了提交量，所以深度边界会拒绝调用方自己的池已经接受的调用。等待超时则用第二个待调参数重新引入虚假失败。

**让 `mode: 'fixed'` 保持默认。** 这样上限始终等于运维者写下的数字，这是一个通用默认值可以诚实拥有的性质，自适应则变成部署主动要求的例外。它也让 `maxConcurrentCalls` 在每个部署里含义一致，代价是必须给出一个这项工作背后的第三方服务器不公布、问不到、在部署指向它们之前也不会实测的数字——于是这个默认值就是一个猜测，而它猜得太高时的退化程度与自适应上限完全相同，猜得太低时则白白浪费部署抬高过的扇出。自适应没有无界的失败模式：它被限制在 `[1, maxConcurrentCalls]` 内，绝不收回已授予的槽位，而且它需要的全部证据就是客户端本来就收到的那些拒绝，它们说明服务器跟不上。实测过自己服务器的部署仍可用 `mode: 'fixed'` 退出；同理，`retryAttempts` 默认 0——重发会掩盖模型本可应对的失败，并为每个被拒调用增加延迟，而重复一次调用是比「同时跑几个」更强的断言。

**一份名单兼管两个问题。** `exclusiveTools` 已经标出了「再发一次就是再写一次」的那些调用，因此「重发所有不在名单里的工具」既不需要新字段，也不需要维护第二份东西。它是一份黑名单，所以它的默认值恰恰是危险的那个：名单为空时——也就是每个从未配置过它的服务器的状态——所有工具都会被重发，包括部署方从未想过的那些写工具，而漏写一个名字就把一次拒绝变成一次重复写入。允许名单失手的方向是损失一次调用，而不是重复一次副作用，所以「重复」这个问题有了自己的名单，其安全默认值是「什么都不重发」。

**重发所有不在 `exclusiveTools` 里的工具。** 只有当服务器收到并执行了首次尝试时，重发才不安全，而被拒通常证明它没有。客户端无法证明这一点：请求已经送达之后连接被重置，正是服务器可能已经执行该调用的情形，而名单外的工具恰恰是客户端无法判定的情形——部署方可能压根没考虑过它。读取 `readOnlyHint` 并让部署方点名其余工具，把自动重发的范围限制在那些自称只读的工具上。

**持久化或共享学到的上限。** 把学到的值写入文件，或在副本之间共享，能让学习跨重启延续，也能阻止相互独立的实例叠加超过服务器的容量。两者都需要一个属于某人的所有者与存储格式，而 harness 并没有为按服务器的启发式值准备这种东西；何况来自不同部署或不同服务器版本的持久值是一个更难推理的过期猜测，还不如重启重来。状态留在插件实例内，README 说明其后果。

**只算显式的拒绝，绝不算超时。** 超时是模糊的——过载与慢查询看起来一样——所以计入它会毫无收益地把一批调用串行化。模糊性也在另一个方向：一个在超时内什么都不答的过载服务器，正是上限要应对的常见故障，而不计入它就让客户端以全并发持续捶打它。该判定是部署取值 `countTimeouts`，默认开启，并把过度下调写进文档而不是藏起来。

## 验证

单元测试（`tests/concurrency.spec.ts`：48 个用例）。测试夹具是基于 `InMemoryTransport.createLinkedPair()` 的真实 `McpServer`，其处理函数自行记录峰值重叠数，因此下文所有数字都是服务器观察到的事实，而不是桥接层的自述。

- 判定：声明 `readOnlyHint` 的工具与声明 `idempotentHint` 的工具经由 `ctx.tools.executionMode` 解析为 `parallel`；无注解的工具与声明 `readOnlyHint: false, destructiveHint: true` 的工具解析为 `exclusive`；`policy: 'parallel'` 与 `policy: 'exclusive'` 在两个方向上都能覆盖；两个服务器各自保有自己的策略；`exclusiveTools` 无论策略如何都恰好排除它点名的工具（包括声明了 `readOnlyHint` 的工具），而不动该服务器其余的工具。
- 重叠：默认策略下四个并发调用在处理函数中达到四个同时执行；`maxConcurrentCalls: 2` 下五个调用峰值为二，并且仍然返回全部五个结果、各自携带自己的 tag；上限为一时三个调用峰值也为一，并按提交顺序进入处理函数；两个各限一个的服务器同时运行时峰值都为一。
- 限流器：派发前就已中止的信号不占用槽位，排队期间被中止的信号以自身原因被拒绝并把槽位留给下一个等待者，获槽之后的中止不会二次释放槽位，release 是幂等的，`close` 会拒绝排队中与之后的获取，而已获槽位仍可正常工作。
- 学到的上限：每份过载报告把上限减半（8 → 4 → 2），十份报告停在一；在四个槽位已授予时下调不会放进任何新调用，且下一次调用只在这四个释放之后才运行，这就是「不收回已授予槽位」规则；每个静默窗口回升一步，1 → 2 → 3 → 4，窗口内的额外完成不带来任何增加，天花板始终成立，而一次拒绝会重启窗口（在 1000 毫秒窗口下 900 毫秒 + 900 毫秒不回升，再多 100 毫秒才回升）；`mode: 'fixed'` 忽略所有报告。回升窗口是测试通过 `ToolConcurrencyInternals.now` 注入的时钟，因此没有任何断言依赖实际耗时。
- 重发资格：工具在自身注解声明 `readOnlyHint: true`、或被 `retryTools` 点名时可重发，其余情况都不可——注解缺失、`readOnlyHint: false`、非布尔提示，以及仅有 `idempotentHint: true` 都让它不重发，而 `retryTools` 为空且没有只读注解就是什么都不重发。两份名单保持独立：同时出现在两份里的工具既串行又可重发，只在 `exclusiveTools` 里的工具则串行且永不重发。延迟逐次翻倍，在 `retryJitterRatio: 0.5` 时关于基础延迟对称，在 0 时精确；`waitBeforeRetry` 在等待前后都能报告中止。
- 解析与配置：`resolveToolConcurrencyPolicy` 拒绝未知键、未知策略、未知模式、不是正整数的上限、空白的 `exclusiveTools` 或 `retryTools` 条目、落在开区间 0..1 之外的 `decreaseFactor`、非正的 `recoveryStep`、超出定时器范围的 `recoveryQuietMs`、非布尔的 `countTimeouts`，以及越界的重发取值，而空名单解析为「不点名任何工具」、省略配置块解析为文档所述的默认值；`tests/apply.spec.ts` 固定 Config schema 的默认值（含 `mode: 'adaptive'` 与两份空名单）、部分合并、名单原样透传、显式取值与对非法配置块的拒绝；`tests/mcp-client.spec.ts` 固定发现阶段会拒绝两份名单中任一被服务器漏报的名称（单名、多名、两份名单出现在同一条诊断里，并报出服务器实际报告的名称）、重新同步丢失该名称时保留上一世代、以及服务器确实报告的名称可以正常同步；`tests/reconnect.spec.ts` 固定 dispose 会让排在上限之后的调用失败，且该等待中的调用永远不会到达服务器。
- 拒绝判定（`tests/overload.spec.ts`：10 个用例）：`StreamableHTTPError` 的 429／500／503 计入，400／401／403／404／405／422 与未知状态不计入；来自传输或来自 JSON-RPC 错误响应的 `McpError` `-32000` 都计入；`-32001` 仅在 `countTimeouts` 下计入；连接丢失或超时的 cause 码能穿过被包裹的 `fetch failed` 被识别，且在界内任意深度都有效；五层深以及自引用的 cause 链会终止且不产生信号；被中止的调用即使携带 `-32000` 或 `-32001` 也绝不算被拒；工具层失败绝不计入。

集成测试（`tests/exclusive-tools.spec.ts`：6 个用例）。该套件在标准测试依赖（`mountAgentLoopTestDependencies`）之上挂载真实 loop，并用脚本化的 `MockAdapter` 驱动，因此屏障是按两个真实 MCP 服务器在一个助手步骤中观察到的重叠量来测量的，而不是从判定推断：在 `maxConcurrentCalls: 20` 下五个发往名单内工具的调用峰值为一、按提交顺序进入服务器且每个结果都成功；同一服务器内四个未列入名单的调用峰值为四；四个发往声明 `readOnlyHint` 的名单内工具的调用峰值为一；一个同时包含 `read:mcp__a__read`、`mcp__b__write`、`mcp__a__read` 的步骤峰值为一且名单内调用居中执行，这就是本记录所称的跨服务器屏障，而一旦名单不点名该工具，同样三个调用的峰值就是三；无注解服务器的四个工具在 `policy: 'parallel'` 下峰值为四，即第三方主路径。

端到端测试（免 key，`tests/mcp-client.e2e.ts`：28 个用例）。在真实的 stdio 子进程上，五个并发只读调用在服务器内部达到五个同时执行；同样五个调用在 `maxConcurrentCalls: 2` 下峰值为二；在进程内的 Streamable HTTP 端点上，四个并发调用的峰值为四。另有三个用例驱动一个对最初的若干次 `tools/call` POST 应答 503 的真实端点，也就是产生真实 `StreamableHTTPError` 的路径：下一阶段八个调用在端点自身处理函数上的峰值降为一；在较短回升窗口下再一个阶段十二个调用会回升到配置上限四，且全程不超过它；而在 `retryAttempts: 2` 下，一个被 503 拒绝的只读调用会在第二次 POST 上被成功服务，而一个对重复执行不作任何声明的工具在被 503 拒绝后只发一次 POST 就把错误交给模型，两次请求都在端点侧计数。自适应套件（`tests/adaptive-cap.spec.ts`：12 个用例）在脚本化服务器之上通过真实注册表驱动同样的行为：面对始终拒绝的服务器，八个调用先峰值为八、随后为一，上限为一时停在下限；`mode: 'fixed'` 在两阶段峰值都为四；拒绝阶段在静默窗口内把峰值从 4 降到 1，随后在三个推进的窗口上依次为 2、3、4 且天花板成立；`countTimeouts: true` 时四次超时把上限降为一，为 `false` 时保持为四；被拒的只读工具在 `retryAttempts: 2` 下共到达三次并返回一个成功结果，`retryAttempts: 1` 把它限制为两次请求，一个对重复执行不作任何声明的非只读工具在预算为三时只到达一次并返回服务器的错误、而同一服务器的只读工具用满预算，把该工具写进 `retryTools` 即让它可重发，把只读工具同时写进 `exclusiveTools` 与 `retryTools` 后它仍然可重发且串行，预算为零时不论工具如何归类都只发一次，而在 30 秒退避期间被取消的调用以该取消返回并只有一次到达。快照：无——判定、学到的上限与重发判定都对模型不可见，结果按模型顺序提交，因此逐字记录与串行情形一致，快照只会引入时序依赖。促成这项改动的 180 工具扇出由所有者针对实际部署栈验证，而不由仓库测试验证。

## 后果

- 只读的 MCP 工作现在可以与同级工具调用并行，因此发往同一服务器的一批查询只需一次往返，而不是每次调用一次。
- 桥接层信任第三方服务器写下的两个提示。一个声称 `readOnlyHint` 却改动共享状态的服务器现在会被并发访问，部署的应对方式是为该服务器设置 `toolConcurrency.policy: 'exclusive'`，或把会改数据的工具写进 `exclusiveTools`。读取协议自身的元数据是已被接受的代价；此前的串行行为与一个配置值相距。
- 被列入名单的调用在整个助手步骤内独占，因此把它与发往其它服务器的无关只读调用放在同一步骤就会失去那部分重叠。名单因此只应写入会改数据的工具；想要「只在单服务器内串行」的部署无法从该字段得到。
- `exclusiveTools` 会在发现阶段按服务器自己的工具列表校验，因此第三方服务器改名会让该次重新同步大声失败，直到配置跟上。这是刻意的：另一种选择是名单悄悄不再保护一个会改数据的工具。
- `maxConcurrentCalls` 是按实例、按部署的取值：低于调用侧扇出时它把一批调用切成多波，高于服务器容量时它就不再保护任何东西。默认值 10 等于 harness 全局的步骤默认值，而不是实测的服务器容量，因此已知某服务器较慢的部署会调低它。
- 抬高了调用侧池子却没有抬高 `maxConcurrentCalls` 的部署会得到它并未要求的节流；除了表现为延迟之外，队列不可见。
- 桥接层拥有一个自己的 FIFO 槽位队列，但只用于容量：它从不重排、分组或丢弃调用。
- 自适应成为默认值，因此想要可预测吞吐的部署要自行设置 `mode: 'fixed'`。默认得到的是一个跟随服务器在同一进程生命周期中此前行为的上限：08:00 过载过的服务器会以一次一个调用服务一批请求，直到若干个静默窗口把上限恢复回来。
- 学到的上限按实例、按进程保存：不持久化、不记日志，也不在副本之间共享，因此指向同一服务器的多个实例叠加起来仍可能超过它能承受的量。README 在已知限制下写明这一点；替代做法是调低 `maxConcurrentCalls` 或使用 `mode: 'fixed'`。
- `countTimeouts: true` 意味着缓慢的服务器会被当作过载的服务器处理，因此面向一个延迟本就可预期的服务器的批次可能被串行化而毫无收益。调低 `toolCallTimeoutMs`、调低 `recoveryQuietMs`，或设置 `countTimeouts: false` 是部署的应对方式。
- `retryTools` 为空意味着对一个未声明 `readOnlyHint` 的工具的拒绝永远不会被重发，因此想要为写工具启用重发预算的部署必须点名它们，而一个从不声明只读注解的第三方服务器完全得不到自动重发。这正是预期的方向：另一种做法是以「写两次」失败，而不是以「失败一次」失败。
- 重发信任服务器自己给出的 `readOnlyHint`，而那是第三方服务器可控的线上数据，因此一个把写工具误标为只读的服务器，其被拒调用会被重复执行。这个判定没有逐工具的否决项——重发决定里没有「绝不」——所以对一个在该方向上注解有误的服务器，应对方式是 `retryAttempts: 0`，而这同时也会关掉部署方已点名的那些工具的重发预算。
- 被重发的调用可能掩盖模型本会看到的失败，而每次尝试都要花最多 `toolCallTimeoutMs` 加上其退避。重发默认关闭，而不在允许名单内的工具完全不重发。
- 重发尝试是服务器侧的工作：一批被拒的调用在 `retryAttempts: 2` 下，能在同一次调用的生命周期内向已经过载的服务器发出三倍请求，这也是每次被拒的尝试同样会下调上限的原因。两个机制刻意朝相反方向用力，而上限占上风，因为下调是乘性的、回升是加性的。
