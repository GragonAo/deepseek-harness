# Agent Note: 租户文件面可配置可写作用域与 DELETE

Status: implemented

[English](2026-08-13-tenant-file-face-writable-scopes.md) | 中文

## 问题

租户文件面（`packages/tenant/fs-http`，挂在 `/files`）允许调用方读任何作用域，但只允许写其中两个：`session` 与 `user`。这与它最初的消费者是一致的——案件的工作文件，属于某个会话或某个租户里的某个人。

一个按主体持有**跨案件**资产的业务面打破了这个假设。催生这次改动的是报告模板：同一套模板要在每个案件里都能用，所以它住在主体的用户全局目录里（沙箱 `/global`，宿主 `<usersRoot>/<subject>/work`），而经过鉴权的业务侧必须在产品界面上维护它——上传、覆盖、改名、删除。改动之前，文件面对那里的任何写都答`403 file-readonly`，并且任何作用域都没有删除能力。

这个面又不能对所有人敞开：`case`、`global` 与 `system` 分别由别的所有者写入（业务面、管理面与运维），一个从来不需要这项例外的部署，不该悄悄获得覆盖它们的能力。

## 决策

```yaml
tenant-fs-http:
  writableScopes: [session, user]   # default; a deployment may add global (or any other scope)
```

`writableScopes` 是一个经过校验的 `Config` 字段，默认 `[session, user]`。每个作用域根都携带一个由该集合决定的 `writable` 标志（`roots.ts` 里的 `DEFAULT_WRITABLE_SCOPES` 只是默认值，不是结论），所以点名一个作用域，它的 `PUT`/`DELETE` 就与 `user` 完全同权。不认识的作用域名会让插件加载失败，而不是被忽略；`writableScopes: []` 是一个合法的只读部署。

文件面还新增了 `DELETE /files/<scope>/<path>`：

- **权限跟随可写集合。** 写一片目录与从中删除是同一种权限；把它拆开，等于允许调用方删掉它无法替换的文件。
- **只删文件。** 目录答 `409 file-is-directory`。删一整棵树（以及它的内容是否随之消失）是业务决定，字节通道不替它决定。
- **文件本就不在答 `404`。** 这个面报告它看到的东西，而不是宣称删掉了什么；需要"删两次也一样"的调用方自己把 `404` 读成"已经不在了"（jeecg 桥就是这么做的）。
- **只给作用域的地址被拒**（`400`），与 `PUT` 一致。

既有的写语义不变：临时文件 + rename、ETag 形如 `"<size>-<mtimeNs>"`、`If-Match`/`If-None-Match`。

挂载这个面的租户宿主从 `tenant.config.yaml` 的 `files.writableScopes` 读同一份清单：部署在每一层各说一次它自己拥有的那份口径——文件面在装配期校验，租户应用只传部署写下的值。

这个面上的写权限只属于业务侧。沙箱的挂载策略是另一个设置（`caseReadOnly` / `usersReadOnly`，由容器provider 拥有）：在这里放开 `global`，**不会**让沙箱里的模型获得 `/global` 的写权限。

## 曾考虑的替代方案

**按资产类别加业务方法**（`file.template.upload`、`skill.install`、……）。这正是文件面要取代的形状。每个方法都要重新实现同一套列目录／读／条件写／ETag／大小限制，而每一份副本都会各自漂移：某个部署在一处修掉的问题，另一处拿不到；一个新的资产类别又要重付一遍全部成本。模板是目录里的字节，它不需要自己的术语表。

**永远可写的 `global`。** 更简单，但是错的：多租户部署的默认姿态是最小权限。不把那个目录交给业务侧的部署，不该处在一次配置失误就能覆盖它的位置。

**为跨案件资产另起一个存储面。** 一条并行的挂载、插件或路由去装"共享文件"，会把作用域根解析、ETag 约定与大小限制全部复制一遍——而两套东西终究会在"文件名里允许出现什么"上产生分歧。

**递归删除，或允许对目录 `DELETE`。** 直接拒绝而不是延后：一旦通道能删一棵树，每一次误发的`DELETE /files/user` 都是不可恢复的数据丢失，而真正需要它的调用方可以自己枚举并逐条删除。

**在同一个改动里支持 `Range`。** 范围之外；大文件仍然整份读。加条件删除或部分写，会在没有消费者的前提下成倍放大测试面。

## 后果

一个要把报告模板（或任何其他用户全局资产）置于业务侧控制之下的部署，现在必须在**两处**设置同一个作用域：这里的 `writableScopes`，以及业务侧自己的那份映射（jeecg 桥里的 `dsh.files.writable-scopes`）。两处默认都不含 `global`，所以半配置的部署会在第一次写时响亮失败——要么在本地得到一条可照做的错误信息，要么从宿主拿到 `403 file-readonly`——而不是看起来能用。

这个面现在离一次破坏性操作只差一次授权。这个风险被上面两条规则（只删文件、只在可写作用域）以及"权限与 `PUT` 相同"这一点限定住：能删掉一个文件的调用方，本来也能把它覆盖成零字节。

删除成功时应答报告的是已经不在了的那个地址，而不是一个版本；文件本来就不在答 `404`——所以缓存了 ETag 的客户端必须重新列目录，而不是把 `404` 理解成"从来没存在过"。

## 测试

`packages/tenant/fs-http/tests/fs-http.spec.ts` 两次启动该插件：一次用默认配置（`session`/`user`之外的写与删除答 `403`，且 `Allow` 头声明 `GET, HEAD, PUT, DELETE`）；一次带`writableScopes: ['user', 'global']`，在那里模板可以被写进 `global/报告模板/`、在其中被列出、并从中删除，而 `case` 与 `system` 保持只读。其他用例覆盖只给作用域的 `DELETE`（`400`）、文件不存在（`404`）、目标是目录（`409`），以及配置里写了不认识的作用域（加载被拒，并列出可用名字）。`packages/tenant/fs-http/tests/roots.spec.ts` 钉住标志本身：只有部署点名的作用域才是可写的。
