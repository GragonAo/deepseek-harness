# Agent Note: 写好的技能从目录发布，而不是从归档

Status: implemented

[English](2026-11-10-skill-publish-from-files.md) | 中文

这份决定里「安装」的那一半后来重新做过，见
[已写好的技能由管理平台安装，宿主只负责提交](2026-11-10-platform-owns-skill-install.md)：
这里描述的工具读目录、校验、**提交**，由平台完成安装。本文件保留传输方式这个决定，以及它的理由。

## Problem

写好了 skill 的 agent 只有一条安装路径：平台 MCP 服务上的 `upload_skill`，它的参数是一个 base64 编码的 zip。这次调用从头到尾都跟做事的模型作对。skill 的字节本来就在磁盘上，模型却要把它们重新推导一遍：先写文件，再压缩，再把 zip 转成 base64，最后把结果当成工具参数发出去——等于归档包 1.34 倍的 token，每次重试都要重付，且集中在一整条消息里；一个稍长的 skill 就能把这条消息顶过上下文上限，在那里被截断，调用直接失败。被截断的 base64 参数不是模型能修好的错误，那是死路。

这个形态是传输方式逼出来的，不是设计偏好：MCP 服务跑在自己的 pod 里、没有挂载工作区卷，读不到租户的文件，所以 base64 是把字节送进去的唯一办法。而文件所在的宿主侧，根本没有面向模型的入口。

同一个缺口还有两个较小的后果：没有任何东西告诉模型该怎么写一个别人真的愿意用的 skill，于是长篇生成物变成没人审过的整块文本交出去，中间也没有给用户留核对点；这次发布之后，也没有留下任何用户能看一眼的产物。

## Decision

新增包 `@deepseek-ai/dsh-tool-skill-publish` 里的 `skill_publish(path)`。参数是**目录**，不是内容。插件按调用会话的 `session.header.cwd` 解析该路径，用 `ctx.fs` 遍历它，用 `readSkillDocument` 校验文档，再把读到的文件直接压进提交正文——字节从不变成工具参数，也从不经过模型。

**提交就是工具做的全部事情。** `record` 指明管理平台的入库端点，而且是**必填**：一个说不出发布往哪入档的部署直接装载失败，因为发布一个谁也找不回来的东西，比不提供这个工具更糟。归档以 `multipart/form-data`（`subject` 取自请求范围内的账号、`origin`，以及作为 `file` 的 zip）送到平台的 `POST /dsh/inner/skill/ingest`，由它落存储、写记录、安装——宿主为什么不能自己装，见[安装那份 note](2026-11-10-platform-owns-skill-install.md)。

上限是经过校验的 `Config`（`maxFiles`、`maxFileBytes`、`maxTotalBytes`），不是常量，部署可以按现场抬高；缺省值只挡误写的大树。文档校验在发送之前跑，所以一份坏掉的 `SKILL.md` 是模型当场能改的对话错误，而不是归档出门之后的一次平台拒收。

拒绝原因会被翻译成模型下一步该做什么——目录不存在、给的是文件而不是目录、根目录没有 `SKILL.md`（并列出实际找到的文件）、`SKILL.md` 载不进来、超出上限、会话没有可入档的账号。提交失败会明说「什么都没发布」，并带上平台自己的原话：本部署的平台把所有响应都包成 `{ success, code, message, result }`，连拒收（包括令牌不对）也是 HTTP 200，所以 2xx 本身不算凭据。插件读信封，`success: false` 或 `result.ok: false` 一律按拒收处理——真实集群上跑过一轮才暴露出「回了 200 却什么都没入库」。共享令牌从 `record.token` 读，或——给那些把令牌当 Secret 下发的部署——从 `record.tokenEnv` 命名的环境变量读，只在装载时解析一次：变量不存在就让宿主起不来，而不是每次发布都失败。本栈走的是后一条：租户配置是挂在卷上的对象，所以它只写 `DSH_SKILL_INGEST_TOKEN` 这个名字，值由平台读的那同一份 Secret 注入。超时定在 30 秒而不是一次往返的量级，因为这一跳本来就不止往返：平台要把归档落进对象存储、再让宿主把技能装回去，才回话；宿主重启后的第一次发布就撞在 10 秒的期限上被判成「没入库」，而平台那边连请求记录都没有——这种假阴性会被模型当成真缺口转告用户。

指南以**系统层技能**（`deploy-kit/system-skills/skill-authoring`）的形式交付，而不是改提示词：它写的是共创流程（澄清、先定骨架、逐段落笔并在每段与用户核对、试跑、发布），属于它描述的那个技能家族，而且走现有的「系统技战法管理」启用流程即可安装，不需要重建镜像。

## Alternatives considered

**继续用 `upload_skill`、只把载荷压小。** 压得更狠或者分片传输，仍然把模型留在字节路径上，而那正是缺陷本身：字节还是得由模型发出，任何分片协议都要多几次调用外加一套重组协议。读目录是把这次传输取消掉，而不是把它优化得更好。

**把工作区挂进 MCP 服务 pod。** 那样执行器能读到文件，但同时也让一个 Spring 进程对每个租户的目录有写权限——base64 这条跳板存在的原因，正是 MCP 服务在技能层目录的信任域之外。宿主本来持有那些文件，读文件这部分就该在宿主里做。

**让工具收一个会话内 zip 文件的路径。** 那样模型还是得先把 zip 造出来，而文件已经可读之后，归档格式什么都换不来。要求 zip 还会招来“把父目录打包”的错误，而它的包装目录容错又取决于 zip 是怎么造的。

**跳过平台，直接装进技能层。** 这是第一版实现做的事，也正是[安装那份 note](2026-11-10-platform-owns-skill-install.md)要处理的那种不一致：模型能用、用户看不见，也管不了。

## Consequences

模型发布一次的成本变成一个路径加上结果那句话，与 skill 的大小无关；失败模式也从传输层问题（截断、超限）变成对话层问题（目录不对、文档不合规、超出上限），或者平台自己的拒收——绝不再是传输被截断。

`tool-skill-publish` 被编进租户组合清单，紧挨着 `tool-skill`，所以每个租户会话都拿得到它。它只依赖 `ctx.fs`、`ctx.tools` 和请求范围内的账号，完全不依赖安装 seam：`@deepseek-ai/dsh-skill-install` 回到它唯一的归档入口，于是「文件变成技能目录」没有第二份实现需要同步。

平台 MCP 工具 `upload_skill` 是**删掉**而不是停用：执行器、它背后的 Feign 客户端、以及它投递的 base64 入库端点都已从代码里移除，`V3.9.2.28__drop_upload_skill.sql` 删掉那一行工具记录——留着一行指向已不存在执行器的配置，比没有这一行更糟：它会出现在工具清单里，调用时抛出模型和运维都无法处置的查找错误。`mcp_server_platform` 这一组本身保留，作为以后平台级工具的挂载点。

一次发布对用户可见的记录是平台的那一份：`jzf_user` 行、它存下的归档、它的安装器写下的目录。用户在页面上看到的和模型能触发的，是同一条记录。

## Testing

`packages/skill/tool-skill-publish/tests/publish.spec.ts` 通过 `ctx.tools.execute` 驱动注册好的工具，对着一个替身入库端点：归档里的路径、共享令牌、取自 `runWithUser` 的账号、遍历的各类拒收、文档校验、两条上限、账号检查，以及平台的每一种结果（拒收信封、只在 `result` 里表达的拒收、非 2xx、不是该信封的响应体、被截断的响应体、不可达的端点、到期仍未回话），外加装载期对缺失或半配置目标的拒收。安装那份 note 从「谁安装」的角度描述了同一套测试。

`packages/skill/skill-install/tests/skill-install.spec.ts` 只继续覆盖归档路径：一次普通安装及其目录刷新、包装目录剥离与路径规整、目录条目与重复路径、越界路径、两条上限、载不进来的文档、未发布的层、replace/refuse 一对，以及一次中止后层内什么都没留下的调用。
