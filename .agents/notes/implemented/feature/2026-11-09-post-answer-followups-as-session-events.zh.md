# Agent Note：把「答完之后的追问」记成会话事件

Status: implemented

[English](2026-11-09-post-answer-followups-as-session-events.md) | 中文

## 问题

一个案件管理前端会在每条回答下面显示三个「用户最可能接着问」的问题。这个功能原本做在提示词里：系统指令要求主模型在每次回答末尾输出一个 `[hermes-followup]` 块，内容是 JSON 数组；前端从流式文本里解析这个标签，把它从渲染出的回答里隐藏，再画出这些 chips。

这套安排每一环都脆弱，而且产品侧看不见：

- 指令在部署的提示词里，解析器在前端代码里。任何一边改措辞，新回合就会静默失效，且不会报错。
- 标签是文本，所以它是碎片到达的。前端必须判断半个标签什么时候还是标签、什么时候是普通文字、失败的块要不要再等——这三个流式状态只因为把结构化数据写进了自然语言流才存在。
- 块在回答文本里，于是每一个别的读者都得剥掉它：分享导出、复制、历史重建，以及任何在别处显示这段回答的消费者。
- 主对话提示词为每次回答背了一条输出格式规则，每个回合都消耗指令 token（包括根本不会被追问的回合），而这条规则还会影响回答本身的写法。
- 一个回合的追问既不能换模型重算，也不能从日志重放；主模型不遵守指令时，追问就完全不存在。

## 决策

### 追问是一条日志事实，不是回答文本

新的 `@deepseek-ai/dsh-session-followups` 包监听 `reason.kind === 'completed'` 的 `turn/end`，对顶层会话让辅助模型给出该提供哪些问题。采纳的问题记成仅入日志的 `followup/suggested` 事件，携带回合号与问题列表；其前先是仅入日志的 `followup/llm-request`，记录那次辅助派发的精确内容。

这让追问与「澄清问题」「交付物声明」成为同一类东西：在回合之后产生、面向该回合、由渲染它的消费者折叠、且能从日志重建。提示词里不再有追问的输出格式规则，因此回答不被该功能塑形，也不为它花指令 token。派生的模型历史毫无变化，一个回合的追问永不影响下一次请求看到的内容。

### 生成器是函数插件，框定由部署提供

这个插件不拥有任何能力：它消费 `llm`，只贡献事件。它的 `instructions` 配置字段必填且没有库内默认值，因为「什么算有用的追问」——领域、语言、口吻——属于部署政策，与租户组合提供标题政策是同一个理由。路由默认取会话最后一条 `request/header` 的 provider/model，也就是产出该回答的模型；需要隔离辅助流量时，显式配置 `provider`/`model` 对。

两条限制保护回合本身。回答必须达到 `minAnswerBytes`，因此一句确认不花辅助调用；成帧后的提示必须放进 `maxInputBytes`，因此回答用二分法取能放下的最长前缀，而不是超限发送。任何失败——缺路由、传输错误、回复里出现工具调用、回复无法解析、超时、插件销毁——都只让该回合没有追问并写一条告警；它们都不能让一个已经完成的回合失败。

### 运行在结束该回合的提交之后启动

`session/event` 监听器运行在 `turn/end` 这次追加的发布过程里，而会话不能被重入追加。因此生成器在下一个微任务上启动：先让回合的提交返回，之后再追加这一批。插件跟踪在途运行，销毁时中止它们，并等它们落定后其 effect 才返回。

## 备选方案

**保留提示词标签、把协议写得更严。** 短期更省，而且那正是既有设计。否决理由：结构问题还在——前端解析器必须追着提示词里的生产者，半个标签必须被猜，回答文本的每个其他消费者仍得剥块。

**复用 `ask_user_question` 来出追问 chips。** 否决：这个工具会挂起回合直到用户作答或超时，于是每个回合都会阻塞；它的语义是用户必须解决的一问，而不是一个可选的下一步。

**在会话格式里加一种一等公民的「建议消息」。** 否决：为这点事实加太多面——追问是每回合的注解，不是带角色的消息，普通事件类型就能表达，且不必碰格式版本。

**让前端自己的服务端调模型出追问。** 否决：回合材料在 harness 已拥有的会话日志里；在 harness 之外再建一个模型客户端，既不能共享路由，也不能共享预算与日志。

## 后果

两条事件对不认识它们的构建都是「读取时必需」（`Session.append` 无法把事件标成 `ignorable`）。新增普通事件类型不提升 `SESSION_FORMAT_VERSION`；必须读旧日志的构建需要声明这两个类型。

追问只在回合 `turn/end` 提交之后存在，因此在回合仍运行时就渲染该回合的界面，会在事件到达时才出现 chips，而不是随最终文本一起出现。

部署必须提供 `instructions`；本包有意不提供默认措辞。

推理型 provider 会先把 `maxOutputTokens` 花在思考上，之后才输出正文。实测 `newapi` 上的 `deepseek-v4.1-flash`：一次追问生成在 1200 预算里用掉 676 个推理 token；预算为 256 时 finish 落到 `length`、正文为空，而空正文解析不出任何追问。指向这类模型的部署必须按「推理 + 答案」给预算——租户组合取 2048——并且解析为空时写一条带 finish 原因和正文字节数的警告，让「预算不够想完」落在日志里，而不是变成一个静默不生效的功能。

业务面改为从事件读取问题，而不是从回答文本。仍然解析旧标签的消费者必须对带事件的回合以事件为准，否则升级后的一次重新加载可能把同样三个问题显示两遍。

`packages/session/session-followups/tests/followups.spec.ts` 钉住事件顺序、派发前的请求记录、各跳过规则、路由解析、字节预算与二分截断、每种结束原因的失败、超时、销毁，以及「告警而不抛出」的路径；`tests/invariant.spec.ts` 钉住两条事件的持久化载荷规则，包括挂载时对既有日志的回放校验。
