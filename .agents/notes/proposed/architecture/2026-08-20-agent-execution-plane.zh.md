# Agent Note: Agent 层与执行层 —— 面向多租户遏制的容器绑定工具执行

Status: proposed

[English](2026-08-20-agent-execution-plane.md) | 中文

## 问题

模型发起的工具调用当下在 harness 进程内执行：agent 循环驱动 `ctx.tools.execute()`，注册的 `ToolDefinition.execute` 主体在 Cordis 上下文所在处运行 —— 与会话日志、目标状态、审批通道以及 harness 持有的每一项凭据并排。文件系统、子进程、shell、终端和 LSP 这几个 seam 使文件与进程具备可移植性，但工具的执行主体、参数构造、结果解析和后处理仍留在进程内。E2B 实现把可变化的编码世界移入远端沙箱，而工具主体仍留在宿主上。

三项既有决策已经点明这一扩展，只是尚未实现：

- 沙箱 seam 只限制同一世界子进程的**文件效果**，并声明容器、微 VM 和远端执行器不是它的后端 —— 它们"作为环境连贯组替换整个能力 seam 的服务提供方（`ctx.shell`、`ctx.fs`）"；"更多环境 —— 一个环境连贯能力组示例"是既定延期阶段。
- Code Mode 的运行时 seam 带有 `isolation` 描述符，其设计取值包含 `'container'`，并记载"需要硬多租户边界的部署需要 code 与 bash 都使用容器级后端"。
- 可移植执行世界决策确立 `ctx.fs` 与 `ctx.subprocess` 是 Bash、PTY 与 LSP 共用的同一个执行世界，且宿主保留 agent 循环、agent/会话状态、会话日志、LLM 调用、提示词、工具、授权、技能和 subagent 编排。

对多租户宿主而言，这还缺一条未建成的边界。Agent 层 —— 会话、记忆、日志、模型调用、编排 —— 必须同时承载大量租户，因此任何由租户指定的工具工作都不得在那里执行。注册工具当下是可信的同进程契约；废除这一假设正是本提案的意义所在。

## 提议

两条决策：

1. **一个执行层。** 文件系统、子进程（含 `spawnTerminal`）、shell、终端、LSP、代码运行时和工作流提供方作为**一个环境连贯组挂载在每个租户的容器内** —— 即沙箱 note 的"更多环境"阶段，落地为执行层。Agent 层保留会话日志与持久化、目标状态、agent 循环、模型传输、工具可见性注册表、工具调度管线（`tools/pre-execute` → guard → `tools/post-execute` → `tools/result`）、策略、审批、凭据和提示词组装。

2. **拆分的工具定义。** 工具的控制面投影 —— `name`、`description`、`parameters`、`output.schema`、`render`、`presentCall`、`presentResult`，纯数据与纯函数 —— 留在 Agent 层。其 `execute` 主体移到执行层。注册表在本地解析控制面投影，把 `name` + 无损 JSON 参数通过跨层调用转发给执行层进程，后者运行主体并回传无损 JSON 值与日志。

### 层边界

| 关注点 | Agent 层（宿主进程） | 执行层（每租户容器） |
|---|---|---|
| 会话日志、持久化、投影、标题、遥测 | 拥有 | 永不接触 |
| 目标状态、记忆 | 拥有 | 永不接触 |
| Agent 循环、编排、调度管线（`tools/*` 事件） | 拥有 | 永不接触 |
| 模型传输、提示词组装、工具可见性切换 | 拥有 | 永不接触 |
| 策略、审批、凭据、沙箱策略 | 拥有；把凭据注入容器，绝不经过模型可见参数 | 只接收注入的环境 |
| 工具控制面投影（`schema`、`render`、展示器） | 拥有 | 与提供方无关 |
| `execute` 主体 | 绝不运行 | 拥有 |
| `ctx.fs` / `ctx.subprocess` / `ctx.shell` / `ctx.terminals` / `ctx.lsp` 提供方 | 作为被路由的 seam 消费 | 拥有 |
| `run_code` / `workflow` 运行时 | 路由调用 | 拥有（`isolation: 'container'`） |
| 用户挂载的工具、工具脚本、环境、工作目录 | 声明挂载 | 拥有 |

**并非所有工具都迁移。** `todo`、`goal`、`session-query`、`ask-user`、`jobs`、`subagent-control` 和 `tool-cordis` 操作的是 Agent 层状态 —— 会话日志、目标域、审批通道、任务注册表和插件树。它们留在 Agent 层，因为迁移它们等于迁移 Agent 层本就拥有的记忆。只有**执行世界工具** —— `bash`、`pwsh`、`terminal`、文件系统工具、`glob`/`grep`、`lsp`、`web` 的带效果操作、`run_code`、`workflow` 以及用户挂载工具 —— 迁往执行层。这与沙箱 note 已在子进程受限工具与进程内工具之间划出的界线一致。

### 拆分工具定义

`defineTool` 把 `execute`、`render` 与展示器作为一个对象。拆分把两半分开，而不引入两个注册表：

- **控制面投影** —— 一切纯的部分：`name`、`description`、`parameters`、`output.schema`（受强制原始子集约束）、`render`、`presentCall`、`presentResult`、`finalizeContent`。由 `dsh-tools` 在 Agent 层编译，用于提示词组装、参数校验、输出校验和 UI 重放。
- **执行主体** —— `execute`。在 Agent 层声明；驻留并运行于执行层。

两种挂载形态并存：

- **第一方执行主体**（bash、fs、lsp、terminal…）：这些包已把所有外部效果路由经过 `ctx.fs`/`ctx.subprocess`；在容器内执行它们不改动逻辑，只移动其进程归属。
- **用户挂载工具**：一个工具即一个脚本加一份 schema 声明，按租户提交，对照工具 schema 子集解析，由执行层运行时经固定 ABI 运行 —— JSON 参数进，无损 JSON 值与日志出。Agent 层绝不执行该脚本。

### 跨层工具调用

一次调用 = Agent 层解析控制面投影、运行其调度管线，并把一个有界请求 —— `name`、无损 JSON 参数、调用身份、中止信号 —— 转发给执行层进程，后者运行主体并回传无损 JSON 值与有序日志。该机制复用两项已交付先例：

- Code Mode 的派发桥已把隔离基质里的工具意图经无损 JSON 参数、确定性调用 id 和 `tool/code-dispatch` 日志路由回注册表。执行层把这个方向反转：Agent 层把调用路由出去，执行层运行主体。
- `subagent-acp` 已运行每 child 独立进程，带 ACP RPC、凭证擦除、处置/宽限和生命周期拆除。执行层进程复用这套进程与生命周期脚手架。

日志遵守模型可见 ⟺ 已记录不变量：执行层的效果返回 Agent 层将要追加的事件，从而使 `tool/call` + `tool/result`（以及任何执行内部事件）仍能仅凭会话日志重建请求。

### 里程碑

- **M1 —— 执行世界下沉。** 把 `ctx.fs` / `ctx.subprocess` / `ctx.shell` / `ctx.terminals` / `ctx.lsp` 指向一个容器绑定提供方组；验证 bash、fs 搜索、LSP 和终端完全在容器内运行，而工具主体仍在宿主侧。这是"更多环境"阶段。
- **M2 —— 代码与工作流运行时下沉。** 交付 `isolation: 'container'` 的 `ctx.codeRuntime` 与容器工作流提供方，替换 worker 线程后端。
- **M3 —— 工具执行下沉。** 加入拆分工具定义与跨层调用；把第一方 `execute` 主体和用户工具挂载进执行层。M3 之后，任何由租户指定的工具工作都不在 Agent 层运行。已落地：`ToolExecutor` seam（`@deepseek-ai/dsh-tool-executor`）、进程内验证提供方（`@deepseek-ai/dsh-tool-executor-in-process`），以及经 `ctx.toolExecutor` 路由并保留直派回退的 `dispatchToolBody` 刀口；容器提供方与执行层镜像仍待做。
- **M4 —— 多租户化。** 租户身份与路由、每租户容器、凭据注入、网络策略、工作目录挂载、日志回流进每租户会话、容器生命周期与回收。

### 待决问题

每一项都受本提案尚未掌握的证据约束：

- **容器基质** —— Docker、Firecracker/微 VM、gVisor 还是 OCI 运行时；多租户隔离强度可能要求微 VM 或 gVisor，而非共享内核容器。
- **网络策略** —— `SandboxMode` 只声明文件效果，因此网络维度是独立词表，在其执行提供方处追加。
- **租户生命周期与路由** —— 每租户常驻容器还是按需启动加空闲回收；哪些调用字段承载租户身份。
- **凭据注入** —— Agent 层凭据如何到达容器环境，而不经过任何模型可见参数或日志。
- **流式与持久工具** —— 终端会话与流式 bash 输出以句柄跨层，复用子进程句柄契约；确切帧格式属于 M1/M2 工作。

## 考虑过的替代方案

**一个原地约束每个工具的通用 `ToolRuntime` 包装器。** 不予采纳，且已被沙箱 note 否决：进程内工具闭包持有 `ctx`，因此 `execve` 形态的包装器在机理上不成立。执行层把主体移出进程，而非包装它；两者不同。

**把整个 harness 移入容器。** 不予采纳，且已被可移植执行世界 note 否决：它把提供方工作与插件加载、凭据、模型传输、会话持久性和监督纠缠在一起。执行层在能力 seam 处切分，而非在 harness 的进程边界处。

**依赖 worker 线程后端作为隔离边界。** 不予采纳，且已被 code-mode note 记为刻意的非目标：worker 提供的是遏止而非安全边界，硬多租户边界需要 `isolation: 'container'`。

**保持工具执行在进程内，只沙箱化 OS 效果。** 这是现状，也恰是多租户无法接受的：模型指定的 `execute` 主体继续在 Agent 层、与会话记忆和凭据并排运行。作为目标不予采纳；仅 M1 呈现该形态，是中间态而非落点。

**经 bash 执行器运行用户工具。** 不予采纳：shell 字符串引号会退化结构化参数，丢弃注册表已强制的工具 schema 校验，并重新进入拆分本应避免的宿主侧 bash 消费方。带 JSON 帧的脚本 ABI 让用户工具与第一方工具遵从同一 schema 子集。

**每种能力一个独立容器，而非一个环境连贯组。** 不予采纳，且已被可移植执行世界 note 否决：文件与进程操作必须共享身份与状态，按工具拆分正是执行世界意在避免的两世界失败。

## 验收标准

- 每个执行世界工具调用都派发到执行层；Agent 层不为这些工具运行任何 `execute` 主体。
- 模型可见请求仅凭会话日志即可重建，包括跨层的 `tool/call`/`tool/result` 与执行内部事件；模型可见 ⟺ 已记录不变量在层边界处成立。
- 第一方 bash、fs、glob/grep、LSP 与终端经路由 seam 行为不变、与提供方无关、消费方零分叉 —— 与执行世界 seam 在本地与 E2B 提供方之间已给出的保证一致。
- `run_code` 与 `workflow` 在 `isolation: 'container'` 下运行，可经现有 seam 到达到，除运行时描述符外不改动 `dsh-tools` 的呈现。
- 用户挂载工具对照强制原始 JSON Schema 子集校验，只在执行层运行，且无法观察 Agent 层的会话、目标、审批或凭据状态。
- 凭据到达容器环境，且不出现于任何模型可见参数、工具结果或日志条目。
- 处置、取消与容器回收依防御模式达到停稳，匹配 `subagent-acp` 与工作流宿主已提供的生命周期脚手架。

## 风险

**信任模型变更。** `ctx.tools` 从可信同进程契约变为跨层边界。这是刻意的 —— 多租户要求把工具执行当作不可信边界 —— 但必须显式声明而非静默继承，且每个跨层的 Agent 层侧输入在边界处校验。

**高频工具的延迟。** 文件系统读取与编辑当下是微秒级进程内调用，将付出一次跨层往返。M1 让数据面下移而主体留本地，把回归限制住，直到 M3 决定多少主体逻辑下移。

**拆分定义漂移。** 工具的控制面投影与执行主体分布在两个层之后可能不一致（schema 与实收参数、render 与返回值）。注册表的参数/输出校验与纯 render 契约把不一致带到响亮失败，但两半从此需一起版本化，而非一个对象。

**日志重建完整性。** 执行层效果必须返回日志所需的每一个事件；漏掉一个事件就会静默破坏可重建性。跨层协议必须让漏事件状态不可表示，或使调用失败，而非追加一段不完整历史。

**生命周期与租户撤离。** 卡死的容器或挂起的执行主体不得拖住 Agent 层；取消、宽限与回收正是 `subagent-acp` 与工作流宿主今天解决的同一有界拆除问题，如今延伸到每租户容器。
