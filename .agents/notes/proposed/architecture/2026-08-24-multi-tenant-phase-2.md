# Agent Note: Multi-tenant phase 2 — full parity and ip+host container tool execution

Status: proposed

English | [中文](2026-08-24-multi-tenant-phase-2.zh.md)

## Problem

The slice shipped in [phase 1](../../implemented/architecture/2026-08-24-multi-tenant-slice.md) proves the isolation invariant end to end, but it is deliberately thin: one registered HTTP operation (`/v1/run`) runs a direct `mkdir`/`printf`/`append` script, not a real agent turn, and the container world speaks `docker exec -i` into a `tail -f /dev/null` shim that is never reaped. A production multi-tenant DSH must close four gaps the phase-1 note deferred:

1. **Parity** — a multi-tenant user must get the *identical* agent experience as the single-tenant headless agent: the same agent-loop, session/replay vocabulary, all model-facing tools (bash, fs, terminal, lsp, web, skills, subagent, workflow, todo), and durable per-turn session events. The current `tenant-demo` exercises none of that.
2. **Network reach to the container world** — the agent backend must talk to each tenant's tool-execution side over IP+host (a host-published address), not by shelling out to the Docker CLI. Only then can the agent plane be stateless and physically decoupled from a Docker daemon.
3. **Lazy, fast, stateless containers** — a tenant container must start only on the tenant's first tool call, boot quickly, and hold no durable execution state of its own: the workspace and tools arrive by mount, everything else is ephemeral.
4. **No-tool path** — a tenant request that needs no tool must complete entirely on the agent plane, never touching the container runtime.

## Proposal

Two independent, composable extensions to `packages/tenant/`:

### Stateless agent plane: full-parity HTTP carrier

Replace the single-operation `TenantHttpApi` surface with a tenant-auth carrier over the *existing* single-tenant HTTP surface — [`@deepseek-ai/dsh-host-apiproxy`](../../../../packages/host/apiproxy/README.md). The single-user DSH "全部逻辑" already ships as `ctx.apiProxy` → `toFetchHandler`: `POST /api/<method>` unary RPC across `session.create/prompt/history/list/fork/models/selectModel/rename/attachment/updateQueue/cancel`, `subagent.*`, `goal.*`, `settings.*`, `credentials.*`, `llm.*`, `workspace.*`, `skill`, `agent-preset.*` — plus the `GET /api/events.mux` SSE frame mux. `packages/tenant/agent-http` therefore does not mint a reduced `session/prompt` vocabulary; it wraps that exact surface:

- unary RPC — the bearer JWT → tenant resolve → `runWithTenant(tenant, () => toFetchHandler(ctx.apiProxy).fetch(request))`; the tenant-scoped providers (`session-persistence-postgres`, `subprocess-container`, `fs-container`, `container-docker`) resolve through `requireTenant()` inside that authority.
- mux SSE — the same `apiProxy.events.mux` iterator, re-entering `runWithTenant` per frame, so a tenant connection replays only frames it is authorized to see.

The carrier boots the host service stack the Web GUI composes (`packages/bundle/web-app` host plugins — settings, credentials, `llm-deepseek`, the agent spine, session persistence, compaction, projection, subagents, workflow, every model-facing tool, and `apiproxy` itself) with a provider swap that replaces the entire local execution-and-isolation world: `session-persistence-jsonl` → `session-persistence-postgres`, `subprocess` (`dsh-subprocess-local`) → `subprocess-container`, `fs-sandbox` → `fs-container`, `bash-sandbox` → `bash-local`, and `sandbox` (`dsh-sandbox-local`) → disabled. The sandbox rows are not incidental: the Web shell mounts the sandbox-wrapped variants — `bash-sandbox` (`SandboxBashExecutor` `static inject = ['subprocess','sandbox','sandboxPolicy']` wraps the local argv through `ctx.sandbox`) and `fs-sandbox` (`SandboxedFileSystem` extends `LocalFileSystem`, injects `sandboxPolicy`) — rather than the bare `bash-local`/`fs-local` of the headless prototype, so `ctx.fs`/`ctx.subprocess` are coupled to the host landlock/seatbelt executor. In the tenant composition the container IS the isolation boundary: the host `sandbox` is dropped, the bare `bash-local` runs on the container subprocess, and `sandbox-policy` + `approval` stay to resolve the tool layer's per-call workspace-write mode — pinned to the container-admissible `workspace-write` + `ask`, with `permission` (`dsh-permission-presets`) also disabled because its presets bundle a `danger-full-access` mode and read `ctx.shell.sandboxMode`, which a container executor does not expose. This seven-disable detach (beyond the original three) is expressed in the Loader-based `cordis.yml` and is boot-verified, since it is the one place the Web shell's execution world differs from the http-parity spine. No agent or session state lives in the HTTP process: `apiproxy` already resumes a cold session through `ctx.agents.resume`, so a replica can be killed and another resumed against the same Postgres.

The authority propagation is verified end to end (`tenant-demo/tests/agent-isolation.spec.ts`): the `AsyncLocalStorage` tenant survives into the agent-loop's tool-execution fiber — a scripted mock-LLM `bash` call reaches `requireTenant()` inside `DockerContainerRuntime.exec`, lazily `docker run`s the tool-exec container and routes the command over the published loopback port, while a no-tool turn issues zero container-runtime calls.

The carrier chain is also verified over the wire (`tenant-demo/tests/http-parity.spec.ts`): a bearer-JWT `session.create` + `session.prompt` through `agent-http.fetch` into the real `ApiProxyService`/`toFetchHandler` drives the real agent loop through a scripted mock-LLM `bash` call into the tenant container (lazy `docker run`, one `/exec`), and a no-tool prompt issues zero container-runtime calls. `composeAgent` falls back to the shared host composition when there is no agent-presets roster, so the gateway boots without `agent-presets`; the assembly is the `bundle/multi-tenant` profile bundle, and booting base + web-app + this bundle through the Loader as `['dsh-base','dsh-web-app','dsh-multi-tenant']` is now verified keyless (`tenant-demo/tests/multi-tenant-loader.spec.ts`).

The phase-1 slice e2e runs 4/4 on the target server (`192.168.138.130`, real Docker + Postgres) against a freshly built `dsh-tool-exec:latest`; that run caught the cold-start race in the container plane and now includes the bounded readiness wait. The full-parity agent-turn e2e remains to be assembled from the Loader-based `cordis.yml` and run there.

Cross-session visibility is scoped and verified (`agent-http/tests/agent-http.spec.ts`): `session.list`/`session.search` items and the session-scoped frames on both downlinks (`events.mux`, plus `host/session-added|removed|status|agent-error` and `host/archived-sessions-changed` on `events.host`) are filtered to the ambient tenant — a live session owned by another tenant is dropped, while a cold session (no live owner in the process, already tenant-bound by persistence) stays visible. The ownership directory is fed by `session/created` observed under the tenant's authority, so no session metadata needs to be added to the core session format. Host-plane frames without a session id (`host/workspace-*`, the `remote-event` allowlist) pass through verbatim as shared host composition.

The physical carrier route is also done and verified (`agent-http/tests/agent-http.spec.ts`): when a `webServer` is present, `AgentHttp` registers the `/api` prefix route through a self-owned node:http fetch bridge, so a real `dsh web` serves the multi-tenant API over HTTP with no separate adapter — a missing credential 401s while a valid bearer reaches `session.list` inside the resolved tenant. This replaces `client-connection`'s DNS-rebinding trust fence rather than layering beside it, so the two must not both mount the `/api` prefix in one composition.

Tenant records are now declarable in cordis.yml (`TenantRegistry.Config.tenants`, a `z` schema of `{ id,name,dataRoot,workspaceRoot,toolsRoot?,enabled?,network? }`), so the assembly registers its tenants at boot instead of through a hand-rolled bootstrap; each record mounts as an effect with a returning disposer (verified: HMR dispose removes it, a duplicate id fails loud with `DUPLICATE_TENANT`).

The swap is now a concrete profile bundle (`packages/bundle/multi-tenant`: `cordis.patch.yml` + manifest), composition-verified and boot-verified. The composition test (`multi-tenant/tests/multi-tenant.spec.ts`) post-composes it over base + web-app with the same `applyEntryPatches` the boot include makes and asserts zero skipped/name-mismatched patches, the seven single-user rows disabled (the six local rows plus `permission`), `sandbox-policy`/`approval` pinned to the container-admissible modes, and the eight tenant rows — `container-runtime`, `subprocess-container`, `bash-local`, `fs-container`, `session-persistence-postgres`, `tenant`, `tenant-auth-jwt`, `agent-http` — mounted with their exported names. The boot test (`tenant-demo/tests/multi-tenant-loader.spec.ts`) loads base + web-app + this bundle through the Loader keyless and headless (browser-surface rows disabled, tenant rows + deterministic seams pinned) and asserts each swapped provider resolved — it surfaced the two contracts that still needed the detach rather than the provider list: `permission` (disabled above) and the `workspace` registry's boot-time global `sessionPersistence.list()` sweep, which now reads an empty tenant scope (the Postgres store's `list()`/`listSnapshots()` return no rows outside a tenant, so the sweep indexes nothing instead of failing the boot). The `dsh.cordis-config` gate passes (each inserted row resolves from the bundle's own `dependencies`). The launcher now ships the profile as well: `apps/cli` depends on the bundle and `PROFILE_TEMPLATES` gains `multi-tenant` (`['dsh-base','dsh-web-app','dsh-multi-tenant']`), so `dsh --profile multi-tenant` heals the same single-anchor flat fallback the boot test exercises.

### Container tool-execution plane: ip+host service, lazy, stateless

Introduce a small per-tenant *tool-exec service* image (built by `container-docker/docker/Dockerfile` from the zero-dependency server `container-docker/src/tool-exec.ts`, a minimal Node HTTP process) exposing one primitive over HTTP+JSON on a single host-published port per tenant:

- `POST /exec` — `{ argv, cwd?, env?, stdin? }` → `{ exitCode, stdout, stderr }`; the filesystem plane rides the same endpoint by shelling out `stat`/`cat`/`find`/`base64` in the container, so no dedicated `/fs` surface is needed.

`DockerContainerRuntime` changes from `docker exec -i` to: lazily `docker run -d` the tool-exec image with the tenant workspace and tools bind-mounted and one host port published (`-p 127.0.0.1::8642`); the runtime waits for the `/exec` server to answer on that address — bounded, because `docker run -d` returns before the in-container Node has bound the port — then records that `ip:port`, and `ContainerSubprocessRuntime` and `ContainerFileSystem` both reach it through `ctx.containerRuntime.exec`. This is the "ip+host" interaction: the agent plane never runs the Docker CLI for a tool call; it reaches the container's tool-exec server at a host address. Every tool call still runs *inside* the tenant container with only the mounts as durable state; the container's own filesystem is discarded on reap.

Laziness and fast start fall out of the same mechanism: `ensure(tenant)` still fires on the first `exec`/`fs` resolution, but the image is a small prebuilt Node image (sub-second boot after the one-time pull); a per-tenant idle timeout reaps the container, and the mount-only state means restart is cheap. A tenant that never touches `ctx.fs`/`ctx.subprocess` never triggers `ensure`, so the no-tool path completes on the agent plane alone.

### Tenant-scoped settings, credentials, and memory

`settings-file` and `credentials-local` resolve under `Tenant.dataRoot` instead of the single `$DSH_HOME`; `storage-domain` routes `workspace`, `session_projcache`, `message-feedback`, and tenant memory domains at the `postgres` backend (per-tenant schema). This closes the "strictly keyed by tenantId" breadth phase 1 left open.

## Alternatives considered

- **Reuse `host/apiproxy` + `client/connection` wholesale** — now the chosen path: `ctx.apiProxy` already is the whole single-user surface, and `toFetchHandler` + the mux SSE are exactly the carrier vocabulary to tenant-wrap. Its browser roster trust (WebSocket downlinks, DNS-rebinding fence, loopback gating) lives in `client/connection`, which the multi-tenant carrier replaces with bearer auth + `runWithTenant`, so the RPC contract is inherited while the trust fence is swapped. The one inherited limitation is visibility: `apiproxy` broadcasts all in-process sessions on one shared ctx, so `agent-http` scopes `session.list`/`session.search` and the session-scoped frames on `events.mux`/`events.host` to the ambient tenant's sessions; host-plane frames (workspace snapshots, the `remote-event` allowlist) still pass through verbatim.
- **Keep `docker exec` and add idle reap only** — simplest, but keeps the agent plane coupled to a Docker CLI and cannot give a stateless backend that reaches containers by address. Rejected in favour of the ip+host tool-exec service.
- **One short-lived container per tool call** — strongest isolation but re-pays boot latency every call; the fast tool-exec service plus idle reap gives near-equivalent statelessness with amortised start. Chosen: per-tenant service, idle-reaped.
- **A host-level tool-exec gateway that spawns containers** — keeps the network hop but pushes Docker access into a separate gateway process; strictly more moving parts than publishing the in-container service directly. Rejected for now, revisited if many replicas must share one container pool.

## Acceptance criteria

- `agent-http` boots the Web-GUI host stack with the three provider swaps and serves the full `ctx.apiProxy` RPC surface plus the mux SSE, tenant-scoped; a real multi-turn coding task and a subagent/workflow task both run and persist tenant-keyed session events.
- The no-tool path is proven: a tenant prompt that needs no tool returns a completed turn with **zero** `containerRuntime`/Docker invocation (asserted, not asserted-by-absence-of-error).
- The tool-exec container starts only on first tool use, and `ContainerFileSystem` rejects a path outside `/workspace`/`/tools` through the executor.
- `settings`, `credentials`, and every configured storage domain resolve per tenant; a cross-tenant read is unrepresentable.
- The full parity e2e runs for real on 192.168.138.130 against Postgres and Docker.

## Progress

The bundle is boot-verified locally (Loader keyless) and the carrier chain is proven over the wire (`http-parity`); the production wiring (`apps/cli` dependency + `PROFILE_TEMPLATES`) and the seven-disable swap (`permission` disabled, `sandbox-policy`/`approval` pinned to the container-admissible modes) are in. The production `dsh --profile multi-tenant` boot now runs on 192.168.138.130 against real Docker/Postgres: a bearer-JWT `session.create`/`session.list` round-trip persists into per-tenant Postgres schemas (`tenant_acme_*`/`tenant_beta_*`) with cross-tenant isolation (acme=1/beta=0, then beta=1/acme=1) and 401 on missing or bad tokens. A real-LLM no-tool turn also completes over the same carrier (`session.prompt` → the agent loop → `deepseek-v4-flash` through the official endpoint, answer recorded as an `assistant/message` in the session history) — the no-tool path finishes on the agent plane without a container. A real-LLM tool-call turn additionally completes into a lazily started tenant container (bash tool → `subprocess-container` → `containerRuntime.exec` → the `dsh-tool-exec` container's `POST /exec`, output handed back to the model) — the tool path is proven for both an explicit `cwd` and now the **default no-cwd session**. Two container bugs surfaced and were fixed on the way: the tool-exec image's Debian-slim base lacked `bash` (the `bash-local` executor spawns `bash -c`) — now installed in the Dockerfile — and the gateway defaulted the session cwd to the Host `process.cwd()` (`/root/work/deepseek-harness`), which does not exist inside the container, so every tool spawn failed `spawn bash ENOENT` even with `bash` present. The gateway now takes a `cwd` config (`ApiProxyService.Config.cwd`, falling back to `process.cwd()`), and the multi-tenant bundle pins `api-gateway.cwd: /workspace`, matching the container's `tenant.workspaceRoot:/workspace` bind and the `fs-container.root: /workspace`. Tenant-scoped settings, credentials, durable storage, and the workspace registry then landed and were server-verified: `settings-file` resolves `<tenant.dataRoot>/settings.yaml` (the base service keys its snapshot per tenant, falling back to `$DSH_HOME/settings.yaml` outside a tenant), `credentials-local` resolves `<tenant.dataRoot>/.credentials.yaml`, and the bundle swaps `storage-json` → `storage-postgres` with `storage-domain` re-pointed to `postgres` while the workspace registry opens lazily per tenant and fails safe outside a tenant scope; on 192.168.138.130 a real LLM tool turn, acme/beta session isolation, per-tenant workspace lists, and per-tenant `kv_*` schemas all verified. Still open: `workspaceId` selects within the ambient tenant's registry (no per-tenant workspace id index), and two boot-time storage-domain consumers (`session-projection-cache`, `message-feedback`) are disabled in the headless profile until the domain layer defers per-tenant.

## Risks

- **SSE on a stateless replica** — a downlink tied to one replica breaks on failover; the carrier must make event replay (not liveness) the contract, so a client reconnects and replays. Proven by a reconnect test.
- **Tool-exec image build and port hygiene** — host-published ports must never be routable off-host and must be released on reap; tested by asserting the socket is gone after idle timeout.
- **Parity drift** — the carrier composition must be an explicit include of the headless spine so a single-tenant change reaches multi-tenant automatically; guarded by a keyless e2e that boots both and compares tool catalog + session event types.
