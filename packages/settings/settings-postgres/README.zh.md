# @deepseek-ai/dsh-settings-postgres

[English](README.md) | 中文

面向多租户承载层的 PostgreSQL 设置提供者。名为 `settings_doc` 的存储单元把每个命名空间分节以一条记录的形式存放在当前 (租户, 用户) 分区中 —— 租户的 schema 加主键内嵌的 `user_id` —— 因此租户的 `settings.yaml` 永不落到宿主机文件系统上：agent 平面不再持有宿主机侧受管理的配置文件，任何租户或用户也都读不到其他租户或用户的文档。

写路径沿用与文件提供者相同的无关联契约 —— `load()` 提供整份文档、`persist()` 存储一个合并后的分节 —— 只是介质不同。

## 配置

无需配置。提供者解析存储中枢上已注册的 `postgres` 后端；`storage-postgres` 条目上的 `connectionString` 由部署侧提供。

## 行为

- **按 (租户, 用户) 键控。** 任何 (租户, 用户) 作用域之外，`load()` 在不访问 Postgres 的情况下提供空文档，构成请求安全的失败关闭语义；在作用域内，读写都在调用入口解析当前租户与用户。每份文档位于租户自己的 schema（`tenant_<id>_<hash>`）加主键内嵌的 `user_id` 中，因此同一租户的两个用户各持独立的文档。
- **一个单元、一张表。** `settings_doc` 单元声明单张 `section` 表，键为命名空间名、值为原始分节；未使用 `hasGlobal`。
- **(租户, 用户) 单元懒加载。** (租户, 用户) 的单元句柄在首次写入时打开并对本进程生命周期复用，随后在释放时关闭。
- **新鲜度由基类读路径决定。** 与每个 `SettingsProvider` 一致，`load()` 在首次发布时执行，并在每个 (租户, 用户) 首次写入时再次执行；只读请求在看到该作用域文档前得到默认值（或由其他提供者侧的加载动作暴露）。这点与 `settings-file` 一致，并非 Postgres 介质的缺陷。

## 模型体验

通过 `ctx.settings` 的消费者间接生效：本提供者只存储并发布命名空间分节，模型层面的影响由各消费者自身的界面文档说明。

#### KV 缓存影响

无直接失效；相关的请求前缀变化由消费方插件负责。

## 已知限制与后续工作

- **介质不热更新。** 没有文件监视器，因此其他进程直接在 Postgres 中修改的分节，要等到本进程下一次写入或重启才会被观察到；写入是 settings 接缝暴露的唯一持久化路径。
- **先读后写得到默认值。** 租户已持久化的文档在本进程每次首次写入时懒加载，与基类提供者契约一致；让读取按需加载需要把 `SettingsProvider` 的读路径从同步拓宽为异步，属于接缝级改动，此处暂缓。
