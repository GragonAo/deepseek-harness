# `@deepseek-ai/dsh-multi-tenant`

English | [中文](README.zh.md)

The multi-tenant dsh backend as a profile bundle: [`cordis.patch.yml`](cordis.patch.yml) is a patch layer over [`dsh-base`](../base/README.md) + [`dsh-web-app`](../web-app/README.md) that swaps the shared, locally-sandboxed execution world for the tenant container runtime and mounts the tenant carrier. Thirteen single-user rows are disabled: `session-persistence-jsonl`, `storage-json`, `settings`, `credentials`, `code-runtime` (the host worker-thread runtime), `subprocess`, `fs-sandbox`, `bash-sandbox`, `sandbox`, `permission`, `connection` (now that [`agent-http`](../../tenant/agent-http/README.md) owns `/api`), `message-feedback`, and `session-projection-cache` (both preload a storage domain at init, which the tenant-keyed backend cannot serve outside a tenant scope). Nineteen rows mount in their place: `container-runtime` (`dsh-container-docker`), `subprocess-container`, `bash-local`, `fs-container` (`root: /workspace`), `code-runtime-container`, `workflow-container`, `session-persistence-postgres`, `storage-postgres`, `tenant-admin-postgres`, `settings-postgres`, `credentials-postgres`, `tenant`, `tenant-admin`, `tenant-auth-jwt`, `skill-tier` (`dsh-skill-tier`), `tools-tier` (`dsh-tools-tier`), `tools-manifest` (`dsh-tools-manifest`), `settings-tier` (`dsh-settings-tier`), and `agent-http`. Five existing rows re-pin a value: `storage-domain` (`backend: postgres`); `sandbox-policy` (`mode: workspace-write`) and `approval` (`policy: ask`), because the tool layer still resolves each call's mode through them; `api-gateway` (`cwd: /workspace`), so sessions without an explicit workspace resolve to the container workspace rather than the Host process cwd; and `tools` (its `mode` defaults to `both`, so a tenant keeps the native tool surface plus the Code Mode `run_code` tool — which runs in the tenant container through `code-runtime-container` — while `DSH_TOOLS_MODE` still overrides). The local `sandbox` executor is replaced by the tenant container as the isolation boundary, and `permission` is disabled because its presets bundle a `danger-full-access` mode and a `shell.sandboxMode` the container executor does not expose — the container always confines to the tenant workspace. The `container-runtime` row reads its `usersRoot` from `DSH_USERS_ROOT`; [`dsh-container-docker`](../../tenant/container-docker/README.md) mounts the per-(tenant, user) execution world — the subject's `/workspace`, the case's shared `/shared`, the subject's `/global` (when `usersRoot` is set), and tooling at `/tools:ro`. The package has no runtime API; the profile composer resolves the patch through the `dsh.bundle.patch` manifest field.

Tenant records, per-member tier/user roots (`DSH_USERS_ROOT`), the tenant-administration archive root (`DSH_ARCHIVE_ROOT`), Postgres coordinates (`DSH_POSTGRES_URL`), and auth material (`DSH_OIDC_ISSUER`/`DSH_OIDC_SECRET`) deliberately stay in the deployment's own profile `cordis.patch.yml` (or env): this layer only expresses the provider swap, and an absent value fails loud at load because the tenant providers' config fields are required.

This layer does set one deployment-shaped value itself: `container-runtime`'s `pythonRoot` points at `/opt/.dsh/pyenv`, the single host Python runtime mounted read-only into every sandbox at that same absolute path. The tool-exec image carries no interpreter, so that directory is the sandbox's only Python — one relocatable build holding interpreter, standard library, and packages, which an operator updates in place to move every sandbox to a new version or a new dependency ([mount semantics](../../tenant/container-docker/README.md)). The provider reads that directory in the host process, so a deployment that runs the harness in its own container has to make that path visible inside that container too — by mounting the host directory itself, or its parent at the same path. [`docker/docker-compose.multi-tenant.yml`](../../../docker/docker-compose.multi-tenant.yml) mounts the directory explicitly, because it mounts no parent of it, and a `pythonRoot` the host process cannot read fails the load instead of configuring nothing. A fresh deployment therefore creates `/opt/.dsh/pyenv` before its first start, and that directory has to hold an environment rather than merely exist: a host without it, or with one holding none of `bin`, `pyvenv.cfg`, and `lib/python3.<minor>/site-packages`, refuses to start rather than running sandboxes with no interpreter. That refusal, not an operator remembering the order, is what keeps the empty directory Docker creates for a missing bind-mount source from passing as a configured environment.

**A deployment patch that targets the `container-runtime` row replaces that row's whole `config` object.** Patch semantics assign each key of the patch entry onto the entry, so `config` is overwritten rather than merged; a deployment adding `systemRoot` (or any other field) to that row must restate `usersRoot`, `pythonRoot`, and the bounds alongside it. Whatever it omits falls back to its schema default, which for `usersRoot` and `pythonRoot` is no value at all — a silently unmounted environment rather than a load failure. `dsh --profile multi-tenant --dump-config` prints the composed tree, which is how to check the effective row after any layer is added.

## Model Experience

Indirectly, through the inserted rows: `agent-http` verifies a bearer token and scopes the gateway request to one `(tenant, user)`, and the container providers run every tool call inside that `(tenant, user)`'s container (mounted at `/workspace` with `/shared` and `/global`). The `tools.mode` pin adds the Code Mode `run_code` tool (plus its `tools:sdk` prompt section) to the standard, single-user native tool surface, with its programs executing in the tenant container. This bundle contributes no further model-visible text of its own.

#### KV Cache effect

None directly; each inserted row's package owns its effect.

## Known Limitations and Deferred Work

- **The swap is boot-verified through the Loader, not a real agent turn** — `tenant-demo/tests/multi-tenant-loader.spec.ts` boots base + web-app + this bundle through the Loader (browser-surface rows disabled, tenant rows pinned, deterministic seams hemmed) and asserts each swapped provider resolved; the real-LLM + real-Docker/Postgres closed-loop turn remains the server step.
- **The workspace registry is (tenant, user)-keyed and starts empty in a scope** — it opens each partition's KV domain lazily, so the synchronous `list()`/`get()` projections return empty on first access until an asynchronous method opens that (tenant, user) partition ([`@deepseek-ai/dsh-workspace`](../../workspace/workspace/README.md)).
- **The two carriers are mutually exclusive** — a profile must not also mount `dsh-client-connection`, or `agent-http` and `connection` both register the `/api` prefix and fail the load on a duplicate route.
- **Message feedback and the session-projection cache are disabled** — both bootstrap by preloading their storage domain at init, but the tenant-keyed Postgres backend has no ambient tenant outside a request, so that preload throws `NO_TENANT_IN_SCOPE`. Re-enabling either needs a tenant-scoped (per-request) preload.
- **Tenant provisioning stays in the deployment layer** — the `tenant` row boots with zero records; the profile's patch must supply `Config.tenants`.
