# @deepseek-ai/dsh-llm-providers-postgres

[English](README.md) | 中文

多租户载体的 PostgreSQL 提供方注册表。一个按租户共享的存储单元 `llm_providers` 把每个管理员维护的提供方路由作为一条记录存放于当前租户 schema —— 主键内不含 `user_id`，因此同一租户的所有用户读取同一份注册表，且不涉及宿主侧配置文件。这是提供方管理的持久面：管理界面写入这里的记录，路由消费方读取它们，所以通过 API 新增的提供方在下一个请求就生效，无需重启。

## 配置

无配置。本存储解析存储 hub 上已注册的 `postgres` 后端；部署在 `storage-postgres` 条目上提供该后端的 `connectionString`。

## 行为

- **按租户隔离，而非按用户。** `llm_providers` 单元声明 `shared: true`，记录落在租户的 `kv_case_record` 表，主键内没有 `user_id`。同一租户的两个用户看到同一份注册表；另一个租户的 schema 存自己的。
- **无租户上下文时安全返回空。** 没有当前租户时 `list()` 返回空列表且不访问 Postgres —— 这正好让配置层成为唯一的提供方来源。
- **一个单元、一张表。** `provider` 表把提供方 id 映射到其记录；不使用 `hasGlobal`。
- **在存储边界上校验。** `upsert()` 写入前执行 `assertProviderRecord`；`list()` 逐行复核并跳过不可用记录并告警，因此一条损坏记录不会连带拖垮健康路由。
- **写入即通知。** 每次成功的 `upsert()`/`remove()` 在持久化之后发出 seam 的变更通知，这是消费方能在进程内重新解析路由的依据。

## 模型体验

通过路由消费方间接体现：本存储提供的记录决定请求落到哪个端点、如何认证。记录的 `baseURL` 与 `models` 收窄选择器可选项，`apiKey` 用于认证该次调用而不再依赖环境变量。

#### KV 缓存影响

不直接触发失效；当解析出的路由集变化时，请求前缀的变化由路由消费方负责。

## 已知限制与待办

- **没有跨进程失效。** 进程之间没有通知通道，另一个副本写入的记录要在本进程下次写入或下次租户内读取时才会被观察到，而不是立即生效。
- **路由拓扑是进程级的。** 路由消费方按进程注册路由而不是按租户，因此两个租户若给同一个路由 id 配了不同端点，共享的是最后解析出的那一套。凭据不受影响：请求按自己的租户记录取 key。
- **凭据按原样存储。** 记录在租户 schema 内携带提供方 API Key，与现有 Postgres 凭据/设置文档的姿态一致；静态加密属于部署层事项，本包不实现。
