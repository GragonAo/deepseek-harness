# @deepseek-ai/dsh-llm-providers-postgres

[English](README.md) | 中文

多租户载体的 PostgreSQL 模型厂商注册表。一个共享存储单元 `llm_providers` 把每个管理员维护的厂商路由作为一条记录，并且**在任何租户作用域之外打开**，于是记录落在存储后端的 `dsh_system` schema 里：整个部署的所有租户读同一份注册表，且不涉及宿主侧配置文件。这是厂商管理的持久面：管理界面写入这里的记录，路由消费方读取它们，所以通过 API 新增的厂商在下一个请求就生效，无需重启。

## 配置

无配置。本存储解析存储 hub 上已注册的 `postgres` 后端；部署在 `storage-postgres` 条目上提供该后端的 `connectionString`。

## 行为

- **部署级，不按用户也不按租户。** 单元在激活时（此处没有任何租户上下文）打开一次并声明 `shared: true`；这样打开的 shared 单元在其整个生命周期内都走后端的 `dsh_system` schema，因此在某个请求的租户作用域内发出的写入同样落进这一份注册表。表内既没有 `user_id`，也没有租户维度。
- **一个单元、一张表。** `provider` 表把厂商 id 映射到其记录；不使用 `hasGlobal`。
- **在存储边界上校验。** `upsert()` 写入前执行 `assertProviderRecord`；读取路径逐行复核并跳过不可用记录并告警，因此一条损坏记录不会连带拖垮健康路由。
- **写入即通知。** 每次成功的 `upsert()`/`remove()` 在持久化之后发出 seam 的变更通知，这是消费方能在进程内重新解析路由的依据。

## 模型体验

通过路由消费方间接体现：本存储提供的记录决定请求落到哪个端点、如何认证。记录的 `baseURL` 与 `models` 收窄选择器可选项，`apiKey` 用于认证该次调用而不再依赖环境变量。

#### KV 缓存影响

不直接触发失效；当解析出的路由集变化时，请求前缀的变化由路由消费方负责。

## 已知限制与待办

- **没有跨进程失效。** 进程之间没有通知通道，另一个副本写入的记录要在本进程下次写入或下次读取时才会被观察到，而不是立即生效。
- **一个库一份注册表。** 共用同一个 PostgreSQL 库的两个部署会共用厂商路由；要分开就需要在单元上加部署键，并有一条从传输配置读它的解析路径。
- **凭据按原样存储。** 记录在 schema 内携带厂商 API Key，与现有 Postgres 凭据/设置文档的姿态一致；静态加密属于部署层事项，本包不实现。
