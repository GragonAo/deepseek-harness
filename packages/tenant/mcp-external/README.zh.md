# @deepseek-ai/dsh-mcp-external

把一个会话有权使用的外部 MCP 服务器挂进这个会话的 agent——会话开始时挂一次，运行中的会话底下登记表变了再挂一次。

登记表（[`dsh-mcp-servers`](../../mcp/mcp-servers/README.md)）说*用户能用哪些*；本插件决定*什么时候用上*，以及一条存下来的记录怎么变成一个活的工具命名空间。它自己不提供任何东西：ctx 上没有服务，没有 RPC 方法，也没有设置项。它全部的表面积就是它做的那次挂载。

## 为什么按 agent 挂，而不是按宿主挂

每个 agent 在 `agent.ctx` 里拿到自己的 [`dsh-mcp-client`](../../mcp/mcp-client/README.md) 实例，一个生效的服务器一个实例，挂载名由登记表推导得出。这个作用域选择正是本特性是「加法」的原因：核心工具登记表本来就按「就近作用域优先」解析名字，所以挂在 agent 作用域里的服务器只对该 agent 可见，别人看不到，共享的宿主上下文也不必知道租户或用户的存在。

它同时也收住了失败面。启动失败的服务器会被记日志并跳过（`failOnStartupError: false`）；会话照样带着启动成功的那些服务器和基础工具打开。一个连不上的第三方地址，永远不该让用户失去这次对话。

## 生命周期

1. `agent/created`——从环境作用域解析调用方用户，读出生效集合，把每个服务器挂进 `agent.ctx`。挂载并行进行，各自有各自的失败路径。
2. `agent/pre-step`（第一步）——最多等 `firstStepWaitMs` 让这些挂载落定，于是打开会话的这一轮看到的是外部工具，而不是和它们抢跑。
3. `agent/pre-step`（登记表写入之后的任意一步）——重新核对：连上新增的、重连变过的、断开没了的，其余的都不动。这一步的请求在这之后才组装，所以它已经带上新的工具清单。
4. `agent/disposed`——把该会话从跟踪表里去掉；它的挂载都是作用域注册，随 agent 一起消失。

这份等待对预算是诚实的：到时候还没落定的一律继续跑着，这一轮不等它。半挂载状态下的 `/mcp` 式检查，比晚一秒开始的这一轮更糟。

## 热更新

登记、修改、停用或删除一个服务器，在**每个运行中会话的下一步**生效，不用重启，也不用新开一个对话。`McpServerStore.subscribe` 在每次持久写入之后触发；插件把它跟踪的每个会话标记为过期，下一次 `agent/pre-step` 就在组装请求之前重新核对。

有两个刻意选择让这件事不只是「快」，还是「安全」：

- **锚在步骤边界上，而不是锚在写入上。** 工具不能从模型正在流式调用的那次调用底下消失，所以进行中的那一步保留它开始时的工具清单，改动落到下一步。
- **比对指纹，而不是比对名字。** 只有当它依赖的东西变了——地址、请求头、超时、并发——才重建挂载。改一个无关的服务器不会惊动它，加第二个服务器也不会重连第一个。

代价是带改动的那一步会有一次提示词前缀失效（工具清单属于前缀）；另一个选择——永不刷新的工具清单——就是让会话用不上用户刚配好的东西。

## 配置

```yaml
- name: '@deepseek-ai/dsh-mcp-external'
  config:
    firstStepWaitMs: 5000      # how long the first pre-step waits for mounts
    maxServersPerAgent: 16     # cap on servers mounted into one agent
    toolCallTimeoutMs: 60000   # default per-tool-call timeout when a row sets none
```

保存一个服务器，会在运行中会话的下一步到达；送达靠的就是上面那段重新核对，而已经在流式的那一步保留它开始时的清单。

## 模型体验

间接触达：通过 dsh-mcp-client——本插件按服务器把它挂在 agent 作用域里。

#### KV 缓存影响

工具定义位于提示词前缀里，所以每一个带挂载改动的步骤都要重新构建一次前缀。没有改动的步骤复用前缀，工具结果只按自身大小花代价。

## 已知限制与推迟项

- **不能在某一步中间换掉。** 改动落到下一个步骤边界；模型正在调用的工具不会被抽走。因此一轮的最后一步仍在用上一份清单。
- **重挂就是整条重连。** 客户端没有原地换地址或换凭据的办法，所以一次修改要花一次握手和一次工具同步。改一个正在被某轮使用的服务器，意味着那一轮后续的步骤看到一个先空后满的新清单。
- **每个 agent、每个服务器各一条连接。** 一个用户的十个 agent 就是到同一地址的十条连接。跨 agent 复用推迟了；它需要先定「一个 agent 里的工具调用能看到另一个 agent 的什么」这套策略。
- **挂载失败的服务器只在下一次登记表写入时才重试。** 会话开始时连不上的服务器不会每一步都重试——那等于把网络超时摆到每一轮前面。再存一次（或者碰一下任意一行）就重试。
- **`toolConcurrency` 是按服务器、按客户端实例计的。** `maxConcurrentCalls` 拦的是一个 agent 的调用，不是整个部署的——要给上游服务设限，得把 agent 数量算进去。
- **用户不能停用系统服务器。** 两份清单都只做加法。
